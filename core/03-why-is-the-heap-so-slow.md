# 堆为什么这么慢（The Heap）

> 视频来源：Core Dumped -《WHY IS THE HEAP SO SLOW?》
> https://www.youtube.com/watch?v=ioJkA7Mw2-U

## 0. 这一期在讲什么

上一期（[栈为什么这么快](02-why-is-the-stack-so-fast.md)）讲清楚了栈快在哪里，也留下了两条硬限制：

| 限制 | 具体表现 |
| --- | --- |
| 数据必须紧凑排列 | 数组想加元素，就会覆盖后面还在用的值，所以尺寸必须编译期确定 |
| 容量有上限 | 通常只有几 MB，塞太大的数据直接 stack overflow |

本期讲这两条限制的解法：**堆（heap）**。

堆是一块被很多人畏惧的内存区域，但它存在是因为**必须存在**。

先说结论，作者在片尾自己承认标题是钓鱼：

> 说「堆慢」是非常有误导性的。
> 慢的是**在堆上分配内存这个过程**，而不是访问堆内存本身。

所以这一期真正要回答的是：分配过程里到底慢在哪。

答案要从「系统调用」讲起。

---

## 1. 前置：系统调用（system call）

### 1.1 程序不能直接碰硬件

出于历史原因，主要是安全，我们的程序**不允许直接访问计算机硬件**。

这就是操作系统存在的意义：它是中间人。
程序需要硬件资源时，由操作系统负责分配。

```text
   我们的程序
       │  「我要往屏幕上写两个字」
       ▼
  ┌──────────┐
  │ 操作系统 │  ← 唯一有权碰硬件的角色
  └──────────┘
       │
       ▼
     硬件
```

### 1.2 一个 hello world 背后发生了什么

你以为 hello world 是最简单的程序，但把这两个词显示到屏幕上，底层做的事情多得惊人。

以 C 的 `printf` 为例：

```c
printf("Hello, %s!\n", name);
```

```text
printf(...)
   │
   ├─ 1. 按格式说明符（format specifier）格式化字符串
   │       └─ 函数名末尾那个 f 就是 "formatted" 的意思
   │
   ├─ 2. 把格式化好的字符串交给下层函数
   │       （具体链路取决于标准库实现）
   │
   └─ 3. 最终交给 write()，它是一个系统调用的包装
           │
           ▼
     系统调用：请操作系统把这些字符输出到标准输出流（通常是终端）
```

**系统调用就是操作系统提供的 API**，我们用它来请求那些只有操作系统才能做的服务。

### 1.3 系统调用为什么贵：上下文切换

程序被执行起来之后有了新名字：**进程（process）**。

进程永远处于某个状态，在很低的层面上，这个状态是由 **CPU 通过它的寄存器（register）** 保存的：程序计数器（program counter）等等。

> 不熟悉寄存器的话，把它想成「CPU 内置的变量」，是硬件在电路层面表示变量的方式。
> 有些寄存器是通用的，有些是专用的。

因为寄存器里的值随进程运行不断改变，所以可以说：**寄存器作为一个整体，承载了进程的状态。**

现在问题来了。
进程发起系统调用时，请求交给了操作系统，而操作系统本身也是软件，它**也需要用 CPU** 来服务这个请求。

但操作系统不能直接开用 CPU，因为那意味着要改写进程正在使用的寄存器，也就是破坏它的状态。

```text
      进程 A 正在跑
      ┌─────────────────────┐
      │ 寄存器 = A 的状态   │
      └─────────────────────┘
              │
              │ 发起系统调用
              ▼
      ① 保存 A 的状态到内存        <- 花时间
         （这份快照叫「执行上下文 execution context」）
              │
      ② 操作系统占用 CPU，处理系统调用   <- 花时间
              │
      ③ 从内存恢复 A 的状态         <- 花时间
              ▼
      进程 A 继续跑
```

保存当前进程的状态、再载入另一个进程的状态以便它继续执行，这个过程叫 **上下文切换（context switch）**。

上下文切换会产生**开销（overhead）**，因为保存和恢复执行上下文本身要耗时间和资源。
注意，除了上下文切换的成本，操作系统处理系统调用本身也要时间，**开销还要更多**。

### 1.4 和内存有什么关系

关键就在这一句：

> 进程每次需要向操作系统申请内存，都需要一次系统调用。

上一期说「栈快的原因之一是所有内存在程序启动时就预分配好了，不需要运行时临时向操作系统要内存」，当时没法解释申请内存为什么贵。
现在你知道了：它要一次系统调用，以及随之而来的全部开销。

## 2. 进程的内存布局（memory layout）

进程用到的内存要分区。

| 区域 | 存什么 | 大小 |
| --- | --- | --- |
| 文本段（text segment） | 编译后的二进制机器码，纯指令 | 固定 |
| 数据段（data segment） | 已初始化和未初始化的全局变量、静态变量 | 固定 |
| 栈（stack） | 上一期的主角 | **固定** |
| 堆（heap） | 本期主角 | **可动态扩展** |

```text
   高地址
  ┌──────────────────────┐
  │        栈 stack      │ │ 向下增长
  ├──────────────────────┤ ▼
  │                      │
  │      （未使用）      │
  │                      │
  ├──────────────────────┤ ▲
  │        堆 heap       │ │ 通过系统调用向上扩展
  ├──────────────────────┤
  │   数据段 data        │  全局 / 静态
  ├──────────────────────┤
  │   文本段 text        │  机器码
  └──────────────────────┘
   低地址
```

有一点别搞混：**栈的大小从来不变**，变的是栈上存放的数据量。

而堆不一样，**堆的大小可以通过系统调用动态调整**。

为了让动画好懂，作者接下来只画一个简化模型：一条栈、一条堆。

## 3. 关键细节：操作系统给的是「一块（chunk）」

非常重要的一点：

> 通过系统调用申请内存时，操作系统**不会**恰好返回你需要的那个字节数，
> 它返回的是**一整块（chunk）内存**。

```text
   我说：给我 4 个字节
   操作系统给我：

   ┌────┬────┬────┬────┬────┬────┬────┬────┐
   │    │    │    │    │    │    │    │    │   一整块 chunk
   └────┴────┴────┴────┴────┴────┴────┴────┘
   └── 我要的 ──┘└──── 多给的，但归我管 ────┘
```

这个行为后面会带来两个后果，一好一坏，都会讲到。

而「想申请多少块就申请多少块」这件事，让堆上可分配的内存**几乎是无限的**，这正好用来解决栈的限制。

---

## 4. 解决限制一：栈放不下的大数据

利用一个事实：**内存的每一个字节都可以通过地址访问**。

地址本质上是数值，可以用整数表示，而整数**大小固定、编译期已知**。

于是策略变成：

```text
   数据本身  ->  放到堆上（多大都行）
   栈上只放  ->  那块数据在堆里的地址
```

```text
        栈                            堆
  ┌───────────────┐          ┌────┬────┬────┬────┐
  │ ptr ──────────┼─────────►│ 图 │ 片 │ 数 │ 据 │
  └───────────────┘          └────┴────┴────┴────┘
   固定 8 字节                   任意大小
```

表示内存地址的数值，在低级语言里通称 **指针（pointer）**，这个词相当自解释。

还有一点很重要：

> 指针**只**表示一个内存地址，它不携带所指数据的长度或大小信息。

所以「堆里哪些子区域被占用了、哪些是空的」，得**我们自己管**。

```text
   存入一个值之后：

   ┌─────────┬──────────────┬──────────┐
   │  已占用 │    空闲      │   空闲   │
   └─────────┴──────────────┴──────────┘
        1 块已用          2 块可用
```

### 4.1 好消息：不是每次都要系统调用

这里就是「操作系统返回整块」的正面作用。

如果之前分配剩下的空间还够用，直接把值写进去就行，**不需要额外的系统调用**。

```text
   ┌─────────┬────────┬──────┬──────┐
   │  已占用 │ 已占用 │ 空闲 │ 空闲 │
   └─────────┴────────┴──────┴──────┘
        2 块已用        3 块可用
   ← 第二个值是写进剩余空间的，零系统调用
```

## 5. 坏消息：外部碎片（external fragmentation）

现在要存一个数组：10 个 8 位无符号整数，共 **10 字节**。

```text
   堆的当前状态（数字是字节数）：

   ┌──────┬─────────┬──────┬─────────┬──────┐
   │ 空 5 │  已用   │ 空 4 │  已用   │ 空 6 │
   └──────┴─────────┴──────┴─────────┴──────┘

   总空闲 = 5 + 4 + 6 = 15 字节   >   需要的 10 字节
   但没有任何一段连续空间 ≥ 10 字节
                 ↓
            数组放不进去
```

空闲总量够、但不连续导致放不下，这就是 **外部碎片（external fragmentation）**。

此时唯一的出路是**再向操作系统申请一块新的 chunk**，代价就是一次系统调用。

碎片可以通过「数据尽量紧凑」来避免。
上面这个例子里，如果一开始就把值排整齐，就完全不需要那次系统调用：

```text
   紧凑排列：
   ┌─────────┬─────────┬────────────────┐
   │  已用   │  已用   │     空 15      │  ← 10 字节数组直接放得下
   └─────────┴─────────┴────────────────┘
```

---

## 6. 为什么堆的碎片躲不掉（本期核心）

看上去只要「尽量挨着放」就能避免碎片。
**但对堆来说不成立。**

这一节是理解栈和堆根本差异的关键。

### 6.1 栈：碎片不可能发生

```text
   栈的规则：只有最后压入的值能被弹出

   push A B C           pop 只能从 C 开始
   ┌───┬───┬───┐        ┌───┬───┬───┐
   │ A │ B │ C │        │ A │ B │   │
   └───┴───┴───┘        └───┴───┴───┘
                        永远不会在中间挖洞
```

这种**可预测的行为**保证了数据永远是紧凑的，所以**栈上不可能产生碎片**。

### 6.2 堆：问题出在不可预测

堆的麻烦在于它的**不可预测性**。
就算你努力把值挨着存，**也无法确定这些值会以什么顺序被释放**。

作者用一个服务器场景说明。

**场景设定：**

- 服务器接收客户端发来的图片，加黑白滤镜后返回。
- 设计为并发处理多个客户端。
- 开发时不确定客户端会发多大的图片，为避免大图撑爆栈，决定**每张收到的图片都存在堆上**。

**运行过程：**

```text
   ① 6 个客户端同时发请求，服务器开 6 个工作线程
      每个线程把收到的图片紧凑地存在堆上

   ┌──────┬────┬─────────┬───┬────────┬──────┐
   │  1   │ 2  │    3    │ 4 │   5    │  6   │   ← 一开始非常整齐
   └──────┴────┴─────────┴───┴────────┴──────┘

   ② 图片大小不同 -> 处理时间不同
      小图先处理完，响应发回客户端，那块内存不再需要，被释放

   ┌──────┬────┬─────────┬───┬────────┬──────┐
   │  1   │    │    3    │   │   5    │      │
   └──────┴────┴─────────┴───┴────────┴──────┘
           空闲            空闲          空闲
           └──── 洞出现在中间，而且到处都是 ────┘
```

结论：

> 堆上任何一个值都可能在**任意时刻**被移除，
> 这让「像栈那样以可预测的方式组织数据」变得不可能。
> **堆上的碎片几乎是必然的。**

### 6.3 既然洞躲不掉，那就利用它

既然明白了堆里到处都是洞，合理的做法就是**尽可能利用这些洞**。

每次要在堆上分配空间时，先检查有没有哪个洞足够大。
如果有，就能**绕开一次系统调用的开销**。

---

## 7. 挑哪个洞：三种分配策略

| 策略 | 做法 | 特点 |
| --- | --- | --- |
| first fit（首次适配） | 选第一个装得下的洞 | 一般**更快**，但不擅长减少碎片 |
| best fit（最佳适配） | 选装得下的洞里**最小**的 | 特定场景能减少碎片，但速度不如 first fit |
| worst fit（最坏适配） | 选装得下的洞里**最大**的 | 同上，特定场景能减少碎片，速度较慢 |

```text
   要放 4 字节：

   ┌──────┬─────┬──────┬─────┬─────────┐
   │ 空 4 │ 已用│ 空 6 │ 已用│  空 12  │
   └──────┴─────┴──────┴─────┴─────────┘
      ▲             ▲              ▲
      │             │              │
   first fit     （不选）       worst fit
   best fit
   （这里正好都是第一个）
```

要注意：**这三种策略没有一种能避免碎片。**
选哪个取决于多种因素，本质是各种因素之间的**权衡（trade-off）**。

## 8. 把前面的内容收成两个函数：alloc 和 free

### 8.1 alloc(n)

```text
   alloc(n)   n = 要存的值占多少字节
     │
     ├─ 1. 用前面某种策略，在堆里找一块 ≥ n 字节的空闲子区域
     │
     ├─ 2. 找不到 -> 发起系统调用，向操作系统要更多内存   <- 昂贵
     │
     ├─ 3. 更新管理堆状态的数据结构
     │
     └─ 4. 返回指向那块区域的指针
```

### 8.2 free(ptr)

```text
   free(ptr)   ptr = 之前拿到的指针
     │
     ├─ 1. 在表里找到这块区域
     │
     ├─ 2. 标记为可用
     │
     └─ 3. 如果相邻的子区域也是空闲的，把它们【合并】
              ┌──────┬──────┐        ┌─────────────┐
              │ 空 4 │ 空 6 │   ->   │    空 10    │
              └──────┴──────┘        └─────────────┘
              合并能让大的分配请求更可能命中现有空间
```

### 8.3 好消息：这些你不用自己写

如果觉得信息量太大，好消息是**这些通常不需要你亲手做**。

以 C 为例，这一整套都已经在标准库里实现好了：

```c
#include <stdlib.h>

int *arr = malloc(10 * sizeof(int));  // alloc
// ... 使用 ...
free(arr);                            // free
```

引入库、调用函数，就这样。

至此，**栈的第一个限制解决了**：值太大放不进栈，就放堆上，栈里只保留一个指向它的引用。

## 9. 解决限制二：动态大小的值

还剩一个问题没解决：**动态尺寸**。

因为栈上一切都是紧凑排列的，值无法在不覆盖其他值的前提下增长或收缩。

### 9.1 「先取出来、改大小、再放回去」行不行

评论区有人问过：为什么不能把需要的数据取出来，调整目标值的大小，再把数据推回去？

确实可以，但想一下代价：

```text
   ① 需要额外内存临时存放取出的数据   -> 可能又要一次系统调用
   ② 就算不需要系统调用，
      在内存里搬来搬去本身就要时间     -> 额外耗时

   到这一步，栈就不再「快」了。
```

### 9.2 搞笑的是：堆本身也解决不了这个问题

把数组存到堆上，添加元素时**照样**可能覆盖旁边的值，和栈上的情况一样。

```text
        堆
   ┌────┬────┬────┬────┬────────┐
   │ 1  │ 2  │ 3  │ 4  │ 别人的 │
   └────┴────┴────┴────┴────────┘
                    ▲
                 想加第 5 个元素 -> 撞上别人的数据
```

**真正的解法是数据结构。**

### 9.3 最简单的方案：链表（linked list）

因为指针**大小固定且编译期已知**，它可以作为自定义类型的成员使用。

```text
        栈                              堆（节点散落各处）
  ┌───────────────┐
  │ head ─────────┼──►┌──────┬──────┐
  └───────────────┘   │ 元素 │ next─┼──┐
                      └──────┴──────┘  │
        （中间可能隔着别人的数据）      │
                      ┌──────┬──────┐◄─┘
                      │ 元素 │ next─┼──┐
                      └──────┴──────┘  │
                      ┌──────┬──────┐◄─┘
                      │ 元素 │ NULL │  ← 最后一个节点
                      └──────┴──────┘
```

添加元素的做法：

```text
   ① 在堆上为新节点分配内存
   ② 让当前最后一个节点的 next 指向新节点
   ③ 新节点成为新的最后一个节点
```

问题解决了。
链表**不需要大片连续内存**，实际上它正好**利用了堆上遍布的那些洞**。

### 9.4 链表的代价

链表也有缺点，其中之一：

> 节点散落在堆的各个角落，导致**缓存命中率（cache hit）下降**。

这正好呼应上一期讲的局部性（locality）。

如果我们想要列表保持紧凑，需要的是 **array list**，在低级语言里通常叫 **vector**。

array list 的实现值得单开一期，本期不展开。

## 10. 回到标题：堆到底为什么被恐惧

### 10.1 管理复杂

```text
   栈的分配                          堆的分配
   ─────────────────                ─────────────────
   读栈指针                          遍历空闲区域表，找合适的洞  <- 耗时
   加上大小                          可能找不到够大的洞
   写入                                └─ 发起系统调用           <- 显著性能惩罚
                                     更新管理结构
   （靠一个栈指针，非常直白）        返回指针
```

搜索堆里可用的子区域是个**耗时的过程**。
最坏情况下没有任何一个洞够大，只能通过系统调用申请内存，付出显著的性能代价。

**本质上，堆上过于频繁的分配会大幅拖慢程序。**

### 10.2 容易出错

除此之外，因为堆的性质，**手动操作堆非常容易出错**。

在 C 这类语言里，围绕手动内存管理有一整个世界的常见错误，
而高级语言开发者看不到这个世界，因为垃圾回收器（garbage collector）在保护他们。

这些错误留给后续一期（作者预告会配动画详细讲）。

> 如果你用得负责任，堆可以是你最好的盟友。
>
> 当你听到有人说「堆很慢」，那是非常有误导性的。
> 所以是的，我把你钓过来了。
>
> **慢的是「在堆上分配内存」这整个过程。**
> 但一旦拿到了那块内存，只要你足够聪明、记得缓存这类概念、选对数据结构，
> **访问堆内存可以和访问栈一样快。**

## 13. 核心总结

```text
堆为什么被说成「慢」
│
├── 前置：系统调用为什么贵
│   ├── 程序不能直接碰硬件，操作系统是中间人
│   ├── printf -> 格式化 -> ... -> write() -> 系统调用
│   ├── 进程状态由 CPU 寄存器承载
│   ├── 操作系统要用 CPU，就得先保存进程状态 = 上下文切换
│   ├── 上下文切换有开销：保存 + 恢复都要时间
│   └── 处理系统调用本身还有额外开销
│       └── 关键：每次向操作系统要内存 = 一次系统调用
│
├── 内存布局
│   ├── text（机器码）/ data（全局静态）/ stack -> 大小固定
│   ├── 栈的大小从不变，变的是栈上的数据量
│   └── heap -> 唯一可通过系统调用动态扩展的区域
│
├── 关键机制：操作系统返回的是「一整块 chunk」
│   ├── 好处：剩余空间够用时，写进去即可，零系统调用
│   └── 坏处：块内乱放 -> 外部碎片
│       └── 15 字节空闲但不连续，10 字节数组照样放不下 -> 被迫系统调用
│
├── 堆的碎片为什么躲不掉（核心差异）
│   ├── 栈：只能弹出最后压入的 -> 可预测 -> 碎片不可能出现
│   └── 堆：任何值可在任意时刻释放 -> 不可预测 -> 洞必然出现
│       └── 服务器 6 线程处理不同大小图片，小图先释放 -> 中间到处是洞
│
├── 既然有洞就用洞：三种策略
│   ├── first fit  更快，减碎片能力弱
│   ├── best fit   特定场景减碎片，较慢
│   ├── worst fit  同上
│   └── 都不能避免碎片，全是 trade-off
│
├── 抽象成两个函数（C 标准库已实现）
│   ├── alloc(n)：找洞 -> 找不到就系统调用 -> 更新结构 -> 返回指针
│   └── free(ptr)：标记可用 -> 相邻空闲区域合并
│
├── 解决栈的两个限制
│   ├── 放不下大数据 -> 数据放堆，栈上只存固定大小的指针
│   │   └── 指针只有地址，不含长度信息，占用情况得自己管
│   └── 动态大小 -> 堆本身也不解决，要靠数据结构
│       ├── 链表：节点散落，利用洞，但缓存命中率差
│       └── array list / vector：保持紧凑，单开一期
│
└── 为什么被恐惧
    ├── 管理复杂：搜索空闲区耗时，最坏情况被迫系统调用
    ├── 过度分配会大幅拖慢程序
    └── 手动管理极易出错（GC 帮高级语言开发者挡掉了这个世界）
```

一句话：

> 堆不慢，**在堆上分配内存**才慢。
> 慢的根源是它必须应付「任意时刻、任意顺序释放」带来的不可预测性：
> 先要在一堆洞里搜，搜不到还得付一次系统调用加上下文切换的钱。
> 而一旦这块内存到手，只要数据结构选得对、对缓存友好，读写它和栈一样快。
