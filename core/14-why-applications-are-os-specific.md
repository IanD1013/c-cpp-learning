# 为什么应用程序是「操作系统专属」的

> 视频来源：Core Dumped -《Why Applications Are Operating-System Specific》
> https://www.youtube.com/watch?v=eP_P4KOjwhs

## 0. 这一期在讲什么

把一个 Windows 上的可执行文件（executable file）拷到 Mac 上，它跑不起来。

如果问为什么，大多数人的回答是：**因为 CPU 架构不同**，Mac 用 ARM，多数 Windows 机器用 Intel x86。

这个回答合理，但**不是全部真相**。作者给了两个反例：

```text
反例 1：时间维度
  2019 年，几乎所有 Mac 还在用 Intel 处理器
  → 同样是 x86，Windows 的 .exe 照样跑不了

反例 2：同一台机器
  作者自己的电脑上同时装了 Linux 和 Windows
  → 同一颗 CPU，但 Linux 上跑不了 Windows 程序
```

所以结论是：**应用程序不只是架构专属（architecture specific），它同时还是操作系统专属（operating system specific）**。

这一期就是要回答：既然编译出来的就是 CPU 能直接执行的机器指令，同一颗 CPU 上为什么换个操作系统就不行了？

作者还特意加了一句立场：**如果这个限制不存在，世界会好很多。**

---

## 1. 前置：用户态、内核态与系统调用

问一个计算机专业毕业生这个问题，多半会先听到三个字：**系统调用（system call）**。

这一段是快速回顾，完整内容在前面的 [内核态与用户态](10-kernel-and-user-mode.md) 一期。

### 为什么 CPU 要分两种模式

通用操作系统要同时跑多个进程，就必须**共享硬件资源**，其中最重要的一个是 CPU。

共享带来安全风险：任何一个进程理论上都可能利用 CPU 绕过操作系统，夺取整个系统的控制权。

为防止这一点，CPU 提供两种基本模式：

| 模式 | 别名 | 能执行的指令 | 谁在这个模式下运行 |
| --- | --- | --- | --- |
| 内核态（kernel mode） | 特权模式（privileged mode） | 指令集里的**全部**指令 | 操作系统 |
| 用户态（user mode） | - | 一个**受限子集** | 用户程序 |

内核态能做的事包括：操作 IO 设备、控制 CPU 定时器、控制内存管理单元（MMU）等硬件部件。

用户态能做的事：搬运和复制数据、做数学运算、判断条件、跑循环。
很有用，但**碰不到硬件**。

```text
┌──────────────────────────────────────────┐
│ 用户态：搬数据 / 算术 / 条件 / 循环        │  ← 你的程序在这里
├──────────────────────────────────────────┤
│ 内核态：IO 设备 / CPU 定时器 / MMU / …    │  ← 操作系统在这里
└──────────────────────────────────────────┘
       操作系统用特权指令守住这条线，
       保证没有用户程序能擅自跨过去
```

### 于是需要一个「代办」机制

这条分界线对安全至关重要，但立刻带来一个问题：
哪怕是「读一个文件」这种小事，或者「通过网络发一条消息」这种大事，用户程序**都需要访问硬件**。

解法很直接：**用户程序自己不能操作硬件，那就请操作系统代劳**。

```text
用户程序                        操作系统
   │
   │  「帮我打开这个文件并写入」
   ├───────────────────────────────►
   │                              ├─ 在磁盘上定位文件
   │                              ├─ 执行写入
   │  ◄───────────────────────────┤
   │        返回结果
```

**这就是系统调用**：系统调用为操作系统提供的服务提供了一套接口（interface）。

它们通常以 C 或 C++ 函数的形式暴露出来，大致可以分成六大类。

而**每个操作系统都提供自己独有的那一套系统调用**。兼容性问题就是从这里开始的。

---

## 2. 程序对系统调用的依赖有多深

作者强调：实际当中，绝大多数程序**极度依赖**系统调用。
你此刻用来看这个视频的程序，每分钟都在向操作系统发出**成千上万次**请求。

这一点可以自己验证。Linux 上执行：

```bash
cat /proc/<PID>/status
```

把 `<PID>` 换成你关心的那个进程的进程号，输出里会有一个字段：

```text
voluntary_ctxt_switches:     12345
        ↑
   进程主动放弃 CPU 的次数，
   也就是它通过系统调用请求操作系统服务的次数
```

这个数字**不小**。

于是核心问题浮出水面：

> 用户程序对系统调用的依赖如此之深，只要另一个操作系统没有**以完全相同的方式**实现它们，程序就直接跑不了。

---

## 3. 第一层障碍：系统调用集合本身就不同

而且问题**不只是名字不一样**。
即使两个操作系统的系统调用存在「对应关系」，它们的**功能也可能差别巨大**。

作者给的例子是「创建一个新进程」。

### Windows：`CreateProcess`

```text
CreateProcess(可执行文件的路径, ...)
        │
        └──► 直接创建一个运行该程序的新进程
```

一步到位，很直观。

### Unix：`fork` 不是你以为的那样

不熟悉系统编程的人会以为 Unix 的对应物 `fork` 也是「创建一个新进程」。

它确实创建新进程，但**不是任意进程**：它创建的是**调用者自己的一个克隆**，唯一的区别是新进程有一个不同的进程 ID。

所以 Unix 上要真正运行另一个程序，还需要额外的步骤：`fork` 之后，子进程必须再调用 `exec` 这类系统调用，用目标可执行文件的内容**替换掉自己的 text 段**。

```text
Windows                      Unix
────────────────────         ─────────────────────────────
CreateProcess(path)          fork()          → 克隆自己
                             └─ 子进程 exec(path)
                                             → 用目标程序替换 text 段
一次系统调用                  两次系统调用
```

> 作者说这个话题很有意思，值得单独出一期，让大家在评论区留言。属于**本期范围之外**。

### 后果

这类设计决策造成的差异是根本性的：
**同一件事，在一个平台上是一次系统调用，在另一个平台上要好几次。**

于是编译成机器码之后，两个平台会生成**不同的指令序列**，哪怕它们是给同一个 CPU 架构编译的。

那些多出来的指令，拿到另一个操作系统上**毫无意义**，结果就是未定义行为（undefined behavior），最终崩溃。

## 4. 第二层障碍：系统调用是怎么被「触发」和「识别」的

假设两个操作系统连系统调用的集合都完全一样，问题还没完。

### 触发：中断

程序要向操作系统请求服务时，会触发一个**中断（interrupt）**。
这个中断让 CPU 切换到内核态，并把控制权交给操作系统。

在 x86-64 这类架构上，专门有一条指令用于此目的：`syscall`。

### 识别：系统调用号 + 系统调用表

操作系统拿到控制权之后，怎么知道请求的是哪一个系统调用？参数又是怎么从用户程序传过去的？

通用做法是：**给每个系统调用关联一个唯一的编号**。

```text
用户程序                              操作系统
   │
   ├─ 把系统调用号写入某个寄存器
   │      ┌─────────────┐
   │      │ reg = 1     │
   │      └─────────────┘
   ├─ 执行 syscall 指令  ──────────►  切到内核态
   │                                  │
   │                                  ├─ 读那个寄存器 → 拿到 1
   │                                  ├─ 查 sys_call_table
   │                                  │     0 → read
   │                                  │     1 → write   ← 命中
   │                                  │     2 → open
   │                                  │    ...
   │                                  └─ 执行对应的内核函数
```

在 Linux 内核源码里可以直接查到每个系统调用对应的编号，它们放在**架构相关的文件**里（例如 x86-64 的 `arch/x86/entry/syscalls/syscall_64.tbl`）。
翻一下这些文件也能看出 Linux 支持的系统调用**有多少个**，前面讨论过的那些只是最常用的一小撮。

### 后果

> 如果两个操作系统提供的系统调用不同，或者用的不是同一张表，那么**完全相同的机器码，在两边请求到的会是完全不同的服务**。

## 5. 第三层障碍：ABI，那些「更小的细节」

作者接下来用一串反问逐层收紧，每一层都假设上一层已经解决：

### 假设两边用完全相同的系统调用表，够了吗

**不够。**

如果其中一个操作系统用**不同的寄存器**来存放系统调用号，程序在那个 OS 上就会崩溃：
操作系统读了错误的寄存器 → 识别出错误的系统调用 → 未定义行为。

### 假设两边读同一个寄存器，够了吗

**还是不够。**

很多系统调用需要**参数**，而参数怎么传，取决于操作系统：

| 传参方式 | 说明 |
| --- | --- |
| 全放寄存器 | 参数少时的常见做法 |
| 写到特定内存区域 | 参数多时 |
| 两者结合 | 实际系统多半是这种 |

Linux 的规则是：**参数少于六个时必须放在寄存器里；超过六个，多出来的写到内存**。

（补充背景：x86-64 Linux 上，系统调用号放 `rax`，六个参数依次放 `rdi`、`rsi`、`rdx`、`r10`、`r8`、`r9`。）

于是又一种失配出现了：

```text
程序（为 OS-A 编译）              OS-B 的期望
────────────────────             ────────────────────
参数写进了寄存器          ✗       到内存里去取参数
参数写进了内存            ✗       到寄存器里去取参数
```

程序在技术上**确实能在另一个 OS 上执行**（毕竟是同一颗 CPU 的指令），但行为不可预测。

### 还有更细的

即便都用内存传参，也还有：

```text
参数放内存 → 放哪块内存？
             ├── 用栈（stack）？
             └── 还是某个专门约定的内存位置？

参数里有指针 → 地址宽度（address width）是多少？
             └── 32 位还是 64 位，直接决定读出来的地址对不对
```

### 这一整套约定有个名字：ABI

**应用程序二进制接口（Application Binary Interface, ABI）**。

```text
API                                ABI
─────────────────────────          ────────────────────────────────
在「应用层」定义函数                在「二进制层」定义组件如何交互
函数名、参数、返回值                寄存器约定、传参方式、地址宽度、
                                   调用约定、数据布局
面向源代码                          面向特定的「操作系统 + 架构」组合
```

**ABI 是绑定到具体操作系统和具体架构的**。这也正是「同 CPU 不同 OS 跑不了」的核心原因之一。

而以上这些，**还只是系统调用这一个方面**。

## 6. 第四层障碍：可执行文件格式

就算前面所有问题都解决了，还有别的低层细节会导致不兼容，其中最重要的一个是**可执行文件格式（executable file format）**。

编译器把源代码翻译完之后产出的可执行文件，**里面不只有指令**：

```text
可执行文件 = 指令 + 数据 + 元数据（metadata）
                          ↑
              操作系统靠它把程序加载起来并执行
```

问题在于：在这一大堆 0 和 1 里，**每一部分到底在什么位置？**

```text
布局 A                布局 B                布局 C
┌──────────┐         ┌──────────┐         ┌──────────┐
│ 头部      │         │ 指令      │         │ 头部      │
├──────────┤         ├──────────┤         ├──────────┤
│ 指令      │         │ 头部      │         │ 数据      │
├──────────┤         ├──────────┤         ├──────────┤
│ 数据      │         │ 数据      │         │ 指令      │
└──────────┘         └──────────┘         └──────────┘
       ↑ 到底是哪一种？每个操作系统有自己的规定
```

这套结构保证可执行文件能被操作系统正确加载和运行，同时还要支撑链接（linking）、调试（debugging）、动态库（dynamic library）等各种特性。

两个具体格式：

| 操作系统 | 格式 | 全称 |
| --- | --- | --- |
| Linux | ELF | Executable and Linkable Format |
| Windows | PE | Portable Executable |

作者把深入了解这两个格式作为**推荐延伸阅读**，本期不展开。

## 7. 第五层：运行时环境（runtime environment）

还有一个作者想到的原因：**有些语言不直接编译成机器码**，而是跑在**虚拟机（virtual machine）或解释器（interpreter）**上。

```text
编译到机器码的语言                 依赖运行时的语言
────────────────────              ─────────────────────────
源代码                             源代码
  ↓ 编译                            ↓ 编译/解释
机器码（绑死 OS + 架构）             字节码 / 直接解释
  ↓                                 ↓
CPU 直接执行                        虚拟机 / 解释器
                                     ↓
                                   CPU 执行
                        只要目标机器装了这个虚拟机，
                        同一份代码就能跨平台运行
```

这带来一个讽刺的对照：

> 虚拟机和解释器的设计目的，**恰恰就是绕开本期讨论的这一整套兼容性问题**。

但它自己又引入了新的失败模式。现代应用往往是**模块化**构建的：

```text
一个应用
├── 模块 A  → 编译成机器码   ✓
├── 模块 B  → 编译成机器码   ✓
└── 模块 C  → 依赖某个运行时  ← 目标机器上没装这个运行时
                              ↓
                    整个应用可能都跑不起来
```

作者的态度：他不反对需要运行时的语言，但**也许我们该停止用它们来写系统的关键组件**。
（紧接着自嘲：话说回来，我们现在都在服务器上跑 JavaScript 了，好像也没什么资格抱怨。）

## 9. 核心总结

同一颗 CPU 上，程序换个操作系统就跑不了，障碍是**层层叠加**的。
每一层都要求「完全一致」，只要有一层不同，程序就崩。

```text
为什么应用程序是操作系统专属的
│
├── 根源：用户态 / 内核态的隔离
│   └── 用户程序碰不到硬件 → 必须靠系统调用请操作系统代劳
│       └── 而程序对系统调用的依赖极深（每分钟数千次请求）
│
├── 第 1 层：系统调用集合不同
│   ├── 名字不同
│   └── 语义也不同：CreateProcess 一步 vs fork + exec 两步
│       └── → 编译出的指令序列不同 → 多出的指令在对面无意义 → 崩溃
│
├── 第 2 层：调用机制不同
│   ├── 触发：中断（x86-64 上是 syscall 指令）
│   ├── 识别：系统调用号 + sys_call_table
│   └── → 表不同 → 同一份机器码请求到完全不同的服务
│
├── 第 3 层：ABI 不同（即使表相同）
│   ├── 系统调用号放哪个寄存器
│   ├── 参数放寄存器还是内存（Linux：≤6 个走寄存器，超出写内存）
│   ├── 走内存的话，用栈还是特定位置
│   └── 指针参数的地址宽度
│
├── 第 4 层：可执行文件格式不同
│   ├── 文件里有指令 + 数据 + 元数据
│   ├── 各部分的布局规则由操作系统规定
│   └── Linux 用 ELF，Windows 用 PE
│
└── 第 5 层：运行时环境
    ├── 虚拟机 / 解释器本来是用来绕开上面这些问题的
    └── 但模块化应用里只要有一个模块的运行时缺失，整个应用就可能跑不起来
```

> 「同一颗 CPU」只保证指令能被**执行**，不保证它们有**意义**。
> 意义是操作系统给的：哪个号对应哪个服务、参数从哪儿取、文件怎么加载。
> 这套约定叫 ABI，它绑死在「操作系统 + 架构」这一对上，所以程序也就跟着绑死了。
