# CPU 调度：让你的电脑在满载时依然流畅

## 0. 这一期在讲什么

跑 benchmark 的时候看着 CPU 占用飙到 100%，是件挺爽的事。

但有个现象值得想一想：**CPU 明明已经跑满了，系统却没有卡死**。

鼠标还能动，音乐还在放，浏览器还能滚。

原因是通用操作系统（general purpose operating system）把**响应时间（response time）**放在了很高的优先级上，保证交互式应用在重载下依然跟手。

做到这件事的组件，就是这一期的主角：**CPU 调度器（CPU scheduler）**。

这一期会从最朴素的「先来先服务」一路推到现代系统用的「多级反馈队列」，每一步都是**上一步被某个具体问题打败**之后的产物。

前置知识主要是进程和上下文切换，见 [一个程序不是一个进程](08-a-program-is-not-a-process.md)、[进程：计算机科学最成功的想法](09-processes-the-most-successful-idea-in-computer-science.md) 和 [内核态与用户态](10-kernel-and-user-mode.md)。

## 1. 什么叫「把 CPU 分配给一个进程」

在设计调度算法之前，得先把这句话的物理含义搞清楚。

### 1.1 text section 与程序计数器

程序被执行时变成进程，操作系统为它保留一块内存。

这块内存里有一段叫 **text section（代码段）**，存放该程序的可执行指令。

每个进程都有自己**独立的** text section。

CPU 里有个特殊寄存器叫**地址寄存器（address register）**，也就是**程序计数器（program counter，PC）**，它指向下一条要执行的指令。

```text
                      CPU
              ┌──────────────────┐
              │  程序计数器 PC    │
              │  ┌────────────┐  │
              │  │  0x4005a8  │──┼────┐
              │  └────────────┘  │    │
              └──────────────────┘    │
                                      ▼
  进程 A 的内存块                进程 B 的内存块
  ┌───────────────┐            ┌───────────────┐
  │ text section  │            │ text section  │
  │  mov ...      │            │  add ...      │  ◄── PC 指在这里
  │  call ...     │            │  cmp ...      │      = CPU 被分配给了 B
  └───────────────┘            └───────────────┘
  │ data / heap   │            │ data / heap   │
  │ stack         │            │ stack         │
  └───────────────┘            └───────────────┘
```

所以「**CPU 被分配给某个进程**」的准确含义是：**程序计数器指向了那个进程的 text section**，CPU 正在执行它的指令。

把 CPU 重新分配给另一个进程，就是操作系统去改这个寄存器，让它指向新进程的代码。

这个动作不是简单改一个寄存器就完事，它属于一个更复杂的操作：**上下文切换（context switch）**。

### 1.2 进程不是对象，PCB 才是抓手

这是个容易忽略但很关键的点：

**进程不是传统计算机科学意义上的具体实体**，它不是对象，也不是某个结构体的实例。

进程是**计算机运行时所处的一种上下文（context）**。

那操作系统怎么管理一个「上下文」？答案是用一个结构体去**代表**它：**进程控制块（Process Control Block，PCB）**。

| 项 | 说明 |
| --- | --- |
| 它是什么 | 进程的**表示**，不是进程本身 |
| 里面存什么 | 状态、程序计数器、各寄存器的值、以及其他管理数据 |
| 什么时候创建 | 每次创建进程时，操作系统生成一个 PCB 来追踪它 |

**后面所有图里画的「进程方块」，进队列的其实都是 PCB，不是进程。**

这不是咬文嚼字：正因为进程本身没法当作数据结构的元素，调度才必须围绕 PCB 来做。

## 2. 第一版调度器：先来先服务（FCFS）

最简单的 CPU 调度算法是**先来先服务（First Come First Served，FCFS）**。

规则一句话：**CPU 分配给第一个请求它的进程**。

实现用一个 **FIFO 队列**就够了：先进的先出，天然符合语义。

```text
  新进程创建 → PCB 入队尾
                                   ┌──► CPU 空闲时，取队头分配
  队尾                      队头    │
  ┌────┬────┬────┬────┬────┐      │
  │ P5 │ P4 │ P3 │ P2 │ P1 │──────┘
  └────┴────┴────┴────┴────┘
         就绪队列（ready queue，FIFO）
```

听起来很简单，对吧？

但这一版藏着一个致命的隐含假设：**一个进程必须等前一个进程执行完毕，才能拿到 CPU**。

这个假设带来两个问题。

### 问题一：不是所有进程都会终止

服务器、后台服务这类程序被设计成**永远运行**。

一旦把 CPU 分给一个不会结束的进程，后面所有进程就会**无限期等待**。

### 问题二：进程并不连续占用 CPU

一个任务跑了 2 分钟，**不代表它把 CPU 占满了 2 分钟**。

执行过程中有大量时间是在**等别的东西**。

这第二个问题，是整个 CPU 调度理论的基石，值得单独一节。

## 3. CPU 突发与 IO 突发

### 3.1 作者的例子：分块复制文件

程序打开两个文本文件，一个有内容，一个是空的，目的是把内容复制过去。

为了不占用大量内存，它**分块复制**，比如一次 8 字节。

```c
while ((n = read(src_fd, buf, 8)) > 0) {
    write(dst_fd, buf, n);
}
```

我们关心的就是循环里这两行。

如果观察计算机实际执行的指令，直觉上会以为是这样连续跑完的：

```text
天真的想象（指令连续执行）

  read  ████
  write ████
  read  ████
  write ████
  ─────────────────────────────────► 时间
```

但真实情况完全不同：

```text
真实情况

  read  ██          ██          ██
        └─ 等磁盘 ─┘└─ 等磁盘 ─┘
  write      ██          ██
             └─ 等磁盘 ─┘
  ────────────────────────────────► 时间
```

读写文件要操作硬件（这里是磁盘），必须**陷入操作系统**，也就是走 **IO 操作**。

IO 操作的代价通常很高，完成时间**取决于 IO 硬件的能力，而不是 CPU 的速度**。

在 IO 完成之前，后面那些指令**根本没法执行**。

顺便把数字算出来：按 8 字节一块复制一个 1 MB 的文件，需要

```text
1,048,576 ÷ 8 = 131,072 次 read
              + 131,072 次 write
              = 262,144 次系统调用
```

二十多万次「陷入内核 -> 等硬件 -> 回到用户态」。

这期间 CPU 如果傻等，浪费的时间是天文数字。

### 3.2 两种突发（burst）

把一个程序的 CPU 使用情况按时间画出来，会看到大量的**空隙**。

这些空隙不是例外，而是**常态**，至少在冯·诺依曼架构（von Neumann architecture）的系统上是这样，而它占了现代计算机的 99% 以上。

| 名称 | 含义 |
| --- | --- |
| **CPU 突发（CPU burst）** | 程序正在使用 CPU 的那段时间 |
| **IO 突发（IO burst）** | 程序在等待 IO 操作完成的那段时间 |

每个进程的执行都是这样的交替结构：

```text
  CPU burst ─► IO burst ─► CPU burst ─► IO burst ─► … ─► CPU burst
  ▲                                                         │
  └── 总是以 CPU burst 开始                                  ▼
                                              以一个请求终止执行的
                                              系统调用收尾
```

### 3.3 突发时长的分布：整期最重要的一张图

CPU 突发的时长已经被测量了几十年。

虽然不同进程、不同系统会有差异，但它们遵循一个**可预测的分布**：

```text
  频
  数
   │
   │ █
   │ █
   │ █ █
   │ █ █ █
   │ █ █ █ █
   │ █ █ █ █ █ ▄
   │ █ █ █ █ █ █ ▄ ▄ ▁ ▁ ▁ ▁ ▁ ▁ ▁ ▁ ▁
   └──────────────────────────────────────► CPU 突发时长
     短                                   长
     ↑                                    ↑
  绝大多数突发都很短              长突发很少，但概率永远不为 0
```

这张图说明：**大多数进程有大量的短 CPU 突发，只有少量的长 CPU 突发**。

推论：**进程把相当多的时间花在等 IO 上**。

如果调度算法不考虑这个行为，会浪费掉巨量的 CPU 时间。

**所以，当一个进程进入 IO 突发时，CPU 理想情况下应该被分配给另一个进程 - 一个同样不在等 IO 的进程。**

CPU 调度的主要目标之一，就是**让 CPU 尽可能忙**（CPU utilization，CPU 利用率），让进程在共享 CPU 的同时尽可能快地跑完。

### 3.4 修正后的分配粒度

于是第 2 节那个「跑到进程终止为止」的假设必须改掉：

> 调度器分配 CPU 的粒度，不是**一个进程**，而是**一次 CPU 突发**。

另外注意一个细节：一个进程的 CPU 突发，**从来不会紧接着上一个突发立刻开始**，中间总有一小段额外的开销（后面第 5 节的 dispatcher）。

## 4. 进程的一生：状态模型

按「一次突发」为粒度调度，实现就复杂了：现在必须承认进程可以处于**不同状态**。

```text
                  ┌─────────┐
                  │   new   │  程序刚启动，可执行文件还在装载进内存
                  └────┬────┘
                       │ 装载完成、资源分配完毕
                       ▼
        ┌─────────►┌─────────┐
        │          │  ready  │  准备好执行了，但在等 CPU
        │          └────┬────┘
        │               │ 调度器分配 CPU（dispatch）
        │               ▼
        │          ┌─────────┐          ┌────────────┐
        │          │ running │─────────►│ terminated │
        │          └────┬────┘  exit()  └────────────┘
        │               │
        │               │ 发起系统调用（IO 请求 / 等事件）
        │               ▼
        │          ┌─────────┐
        └──────────│ waiting │  等 IO 完成或等事件发生
       IO 完成      └─────────┘
```

| 状态 | 含义 |
| --- | --- |
| **new** | 程序刚被启动，可执行文件还在往内存里装 |
| **ready** | 已就绪，只差 CPU 时间 |
| **running** | 正在占用 CPU |
| **waiting** | 在等 IO 完成或等某个事件 |
| **terminated** | 已终止 |

几个关键点：

**IO 调用不只是要资源。**
它也可能只是**单纯地等一件事发生**，比如等用户敲一个键、等一个网络请求进来。
两种情况都会让进程进入 waiting。

**IO 完成了也不会立刻恢复执行。**
因为它等待期间，CPU 多半已经分配给别人了。
所以它只能回到 **ready**，重新排队等自己的轮次。

**大部分时间里，进程就在 ready / running / waiting 三个状态间循环。**
像 Web 服务器这类进程被设计成永不终止，会无限地转在这个环里。

**这些名字是任意的，各系统叫法不同，但状态本身所有系统都有。**
有些系统划分得更细，比如区分「已完全终止」和「正在终止中」（exit 之后操作系统还要释放内存等资源）。

### 为什么队列是 CPU 调度的基础数据结构

这个状态模型解释了这件事：

**除了 running，其他所有状态的进程本质上都在「等」。**

任何时刻可能有**几百个**进程在等，用队列管理它们的执行顺序既符合逻辑又高效。

反过来说：**一个处理器核心在任意时刻只能有一个进程在运行**，所以 running 状态**不需要队列**，队列只对等待中的进程有意义。

## 5. 分派器（dispatcher）：真正动手的那个

调度器决定「谁该跑」，但**执行这个决定**的是另一个组件：**分派器（dispatcher）**。

它只有一个目的：**把 CPU 分配给就绪队列队头的进程**，也就是执行上下文切换。

### 一次完整的切换流程

虽然 running 的进程不在任何队列里，但系统**始终保留一个指向它 PCB 的引用**，这是整个流程能跑起来的前提。

```text
  发生中断（IO 请求 / 定时器）
        │
        ▼
  ① 把 CPU 当前状态保存进 running 进程的 PCB   ──► 以后才能恢复
  ② 把该 PCB 放进 waiting 队列
  ③ 从 ready 队列头取出下一个 PCB
  ④ 标记它为新的 running 进程
  ⑤ 恢复它之前保存的 CPU 状态（寄存器 + 程序计数器）
  ⑥ 如果处理器支持，切换回用户态
  ⑦ 重新分配 CPU，进程从被中断的地方继续
```

### 调度器 vs 分派器

```text
  调度器（scheduler）                 分派器（dispatcher）
  ────────────────────                ────────────────────
  按某个调度策略管理就绪队列           执行调度器做出的决定
  决定「下一个该谁用 CPU」             实际完成上下文切换
  = 决策                              = 执行
```

### 分派延迟（dispatch latency）

第 3.4 节说的那段灰色开销，就是它。

上下文切换本身**也要 CPU 去执行**，所以这些额外的 CPU 突发是**不可避免**的。

> **分派延迟（dispatch latency）**：分派器停下一个进程、启动另一个进程所花的时间。

因为每次上下文切换都要调用分派器，它必须**尽可能快**。

正因如此，**分派器是操作系统里被优化得最狠的组件之一**。

由于它是隐式发生的，画图时通常不把它画在进程之间。

### 甘特图（Gantt chart）

顺带一提，这类展示每个进程起止时间的条形图，是**甘特图**的一个变体。

```text
  P1 ████████
  P2         ██████
  P3               ████████████
  P4                           ███
  ──┴───┴───┴───┴───┴───┴───┴───┴──► 时间
```

## 6. FCFS 的真实实现，以及它输在哪

有了状态模型和分派器，FCFS 的真正实现是：

**用一个 FIFO 队列作为就绪队列，一旦当前进程发起 IO 请求，CPU 立刻分配给队头的进程。**

### 名字其实不准

「先来先服务」有歧义，因为调度器管理的**不是整个进程，而是进程的下一次 CPU 突发**。

更准确的名字应该是「**先到的 CPU 突发先服务**」。

但书和资料都叫 FCFS，就沿用这个约定。

### IO 密集型 vs CPU 密集型

回到 3.3 那张分布图：长 CPU 突发虽然罕见，但**概率永远不为零**。

| 类型 | 特征 | 性能瓶颈在哪 |
| --- | --- | --- |
| **IO 密集型（IO-bound）** | 大量短 CPU 突发，最常见 | 换更快的 IO 子系统会明显变快 |
| **CPU 密集型（CPU-bound）** | 大量长 CPU 突发 | 换更快的 IO **没用**，只吃 CPU 速度 |

### 护航效应（convoy effect）

假设有 **1 个 CPU 密集型进程**和**若干 IO 密集型进程**，在 FCFS 下会发生什么：

```text
阶段 ①  CPU 密集型进程拿到 CPU，长时间占着
        ┌──────────────────────────────────┐
  CPU   │         CPU-bound 进程            │
        └──────────────────────────────────┘
  IO 设备  ░░░░░░░░░░░ 全部空闲 ░░░░░░░░░░░░
  ready 队列  [io][io][io][io]  ← IO 都做完了，全堵在这里等 CPU

阶段 ②  CPU 密集型进程终于结束突发，去做 IO
  CPU   ████████  ← IO 密集型进程们冲上来，但突发极短，一闪而过
  ready 队列  （空了）

阶段 ③  IO 密集型进程全部回到 IO 队列，CPU 没人可调度
        ┌──────────────────────────────────┐
  CPU   │           ░░░ 空闲 ░░░            │  ← CPU 白白浪费
        └──────────────────────────────────┘

阶段 ④  CPU 密集型进程做完 IO，回到 ready 队列，又拿到 CPU
        → 回到阶段 ①，所有 IO 进程继续排队干等
```

这就是**护航效应（convoy effect）**：所有进程排着队等那一个大块头让出 CPU。

结果是 **CPU 利用率和设备利用率双双降低**，比让短进程先走要差得多。

```text
  FCFS 下：CPU 忙 → IO 闲 → IO 忙 → CPU 闲 → …  （两边轮流浪费）
  理想情况：CPU 和 IO 设备同时都在干活
```

那就让短的先走呗 - 这正是下一个算法。

## 7. 最短作业优先（SJF）

**最短作业优先（Shortest Job First，SJF）**：把 CPU 分配给**下一次 CPU 突发最短**的进程。

两个进程突发长度相同时，用 FCFS 作为**平局判定（tiebreaker）**。

同样地，更准确的名字是「最短的下一次 CPU 突发优先」，因为它看的是**下一次突发**而非进程总长度。但约定俗成叫 SJF。

实现用**优先队列（priority queue）**，优先级由「下一次 CPU 突发长度」决定。

这让短突发的进程能**插队超过**那些吃 CPU 的进程，从而缓解护航效应。

### 7.1 为什么它是可证明最优的

SJF **可证明是最优的**：它给出一组进程的**最小平均等待时间（average waiting time）**。

用作者的例子：4 个进程几乎同时到达，第一个的下一次 CPU 突发要 **2 分钟**，其余三个各只要**几毫秒**。

```text
FCFS（长的先到，排在前面）
  P1(长) ████████████████████████████████  120,000 ms
  P2                                     ██
  P3                                       ██
  P4                                         ██
  P2/P3/P4 各等了约 120 秒 ←── 灾难

SJF（短的先走）
  P2 ██
  P3   ██
  P4     ██
  P1(长)   ████████████████████████████████
  P2/P3/P4 几乎不用等；P1 只晚开始几毫秒 ←── 对它毫无影响
```

核心洞察：

> **把一个短进程挪到长进程前面，短进程减少的等待时间，远大于长进程增加的等待时间。**
> 所以平均等待时间必然下降。

为什么要死磕平均等待时间？

因为它代表的是**进程已经准备好运行、却因为排队而跑不了的时间** - 纯粹的浪费。

### 7.2 致命问题：没法完美实现

SJF 有一个无法回避的问题：**除非能预见未来，否则没法知道下一次 CPU 突发的确切长度**。

一个直觉方案是：用程序计数器看看下一个系统调用在哪，算出中间有多少指令。

**不可靠**，因为当前指令和下一个系统调用之间可能有**循环和函数调用**，执行时间根本算不出来。

而且执行路径还可能依赖外部输入。作者的例子：

```c
void shout(void) {
    char *s = read_user_input();   // 长度未知
    for (int i = 0; s[i]; i++)     // 迭代次数取决于用户输入
        s[i] = toupper(s[i]);
    printf("%s\n", s);
}
```

迭代多少次，取决于用户输入多长。

**编译期和运行前都无从得知。**

### 7.3 指数平均预测

既然算不出来，那就**估**：假设下一次突发的长度和之前的差不多。

用**过去 CPU 突发的指数平均（exponential average）**来预测：

```text
  τ(n+1) = α · t(n) + (1 - α) · τ(n)
```

| 符号 | 含义 |
| --- | --- |
| `t(n)` | 第 n 次 CPU 突发的**实际观测值** |
| `τ(n)` | 第 n 次的**预测值**（上一轮算出来的） |
| `τ(n+1)` | 我们要求的：**下一次**突发的预测值 |
| `α` | 权重参数，`0 ≤ α ≤ 1` |

**每个进程的预测只依赖它自己的历史，其他进程不影响它。**

### 递归展开：为什么不用存历史

`τ(n)` 本身就是上一次的预测，所以可以递归展开：

```text
  τ(n+1) = α·t(n) + (1-α)·τ(n)
         = α·t(n) + (1-α)·[ α·t(n-1) + (1-α)·τ(n-1) ]
         = α·t(n) + (1-α)α·t(n-1) + (1-α)²·τ(n-1)
         = α·t(n) + (1-α)α·t(n-1) + (1-α)²α·t(n-2) + (1-α)³·τ(n-2)
         = …
         = α·t(n) + (1-α)α·t(n-1) + … + (1-α)ⁿα·t(0) + (1-α)ⁿ⁺¹·τ(0)
```

这说明 **`τ(n)` 这一项本身就把进程的全部历史带着走了**。

所以我们**不需要存一个可能上千条的突发时长列表，只需要保留最近一次的预测值**。

一个浮点数，搞定。

### α 的含义

| α 取值 | 效果 |
| --- | --- |
| `α = 0` | `τ(n+1) = τ(n)`，**完全忽略最近一次突发**，只靠历史 |
| `α = 1` | `τ(n+1) = t(n)`，**只看最近一次突发**，完全忽略历史 |
| `α = 1/2` | 常用选择，近期与历史**等权** |

注意：「等权」**不等于所有历史突发权重相同**。

展开式里每一项都带着 `α(1-α)^k`，因为 `0 < 1-α < 1`，`(1-α)^k` 是**指数衰减**的：

```text
  α = 1/2 时，各次突发在预测里的权重

  t(n)    ████████████████  1/2
  t(n-1)  ████████          1/4
  t(n-2)  ████              1/8
  t(n-3)  ██                1/16
  t(n-4)  █                 1/32
  …                         → 0
```

**越老的突发影响越小**，这符合直觉：老的执行模式对预测未来的参考价值本来就低。

### 初始值怎么办

进程刚创建时没有任何历史数据，`τ(0)` 通常取一个**常数**，由操作系统定义，或者取**全系统平均值**。

作者的例子：初始值取 **100 毫秒**，跑几轮之后预测值落在 **72 毫秒**左右 - 明显更贴近近期的突发，而不是最老的那个初始猜测。

把预测值和实测值放在一起看，**虽然不完美，但是个相当不错的近似**。

## 8. 抢占式 vs 非抢占式

还有一个分派器必须做的决定没讨论。

场景：进程 A 进入就绪队列并开始运行，紧接着进程 B 也进了就绪队列，此时 A 还在跑。

**如果 A 剩余的 CPU 突发比 B 的下一次突发还长，要不要打断 A，把 CPU 让给 B？**

| 类型 | 行为 |
| --- | --- |
| **抢占式（preemptive）** | 允许操作系统中断正在运行的进程 |
| **非抢占式（non-preemptive）** | 绝不打断正在运行的进程，新来的短进程必须等它跑完当前突发并主动释放 CPU |

这不是一个无关紧要的选择：**SJF 是抢占式还是非抢占式，会直接改变进程的执行顺序。**

### 为什么现代系统默认抢占式

考虑一个非抢占式系统：一个下次突发极长的进程排到了队头并被选中。

系统非抢占，所以**除非它主动释放 CPU，否则没法中断它**。

那要是它**永远不释放**呢？

```c
while (1) {
    x = x + 1;     // 没有任何系统调用
}
```

**死循环在计算机科学里并不罕见。**

只要循环里没有系统调用，这个进程**永远不会把 CPU 控制权交还给操作系统**。

这在把**并发（concurrency）**当作核心特性的通用系统里是致命的。

并发的本质是让 CPU 在进程之间**极快地轮换**，制造出「所有进程同时在跑」的**错觉**（细节见 [并发不是你想的那样](05-concurrency-is-not-what-you-think.md)）。

而在非抢占式系统里，只要一个 CPU 密集型进程长期占着 CPU，**从用户视角看，其他所有进程都冻住了**。

更糟的是：**非抢占式系统依赖进程自觉**在合理时间内交还控制权。

**恶意软件完全可以利用这一点：故意不调用任何系统调用，独占 CPU 时间。**

### 饥饿（starvation）

> **饥饿（starvation）**：调度策略导致某个进程在就绪队列里**无限期等待**。

它「饿」的是 CPU 时间。

注意：**连 CPU 密集型进程自己也会挨饿**。

在 SJF 里，一个预测突发很长的进程可能被源源不断到来的短突发**永远压在队列里**。

它唯一的出头机会是「就绪队列里没有别的进程」，而在有几百个进程竞争 CPU 的真实系统里，这基本不会发生。

> **关键结论：饥饿不是「进程突发长短」的问题，而是「调度策略本身」的后果。**

SJF 在 CPU 利用率和等待时间上确实高效，但通用操作系统还需要**别的调度标准**。

## 9. 轮转调度（Round Robin）

抢占式调度的典型代表是**轮转（Round Robin，RR）**。

RR 和 FCFS 很像：**同样用 FIFO 队列作为就绪队列，但加上了抢占**。

定义一个小的时间单位叫**时间片（time quantum / time slice）**，作者的动画里用的是 **100 毫秒**。

### 流程

```text
  新进程 → 加入就绪队列尾部

  调度器取队头进程
        │
        ├─► 设置定时器，一个时间片后中断
        └─► 分派该进程
                │
      ┌─────────┴──────────┐
      ▼                    ▼
  情况 A                情况 B
  CPU 突发 < 时间片      CPU 突发 > 时间片
  进程自己主动           定时器到点触发中断
  释放 CPU               强制上下文切换
      │                    │
      ▼                    ▼
  调度器取下一个        该进程被放回队列尾部
                        调度器取下一个
```

这套流程**对每一个被分派的进程一视同仁**，保证**没有任何进程能长期或无限期霸占 CPU**，从而防止饥饿。

### 一个硬件前提

非常重要的一点：**定时器是一个物理设备**，通常嵌在 CPU 电路里。

这意味着：**抢占式调度只有在硬件支持的前提下才可能实现**。

### 被抢占 ≠ 进入 waiting

```text
  主动发起 IO   →  running → waiting → ready
  被时间片抢占  →  running → ready          ← 不经过 waiting！
```

因为它**没有请求 IO**，没什么好等的，直接回 ready 等下一个时间片。

### 公平性的量化保证

如果队列里有 `n` 个进程，时间片为 `q`：

| 保证 | 公式 |
| --- | --- |
| 每个进程获得的 CPU 份额 | `1/n` |
| 每次拿到的连续时长 | 至多 `q` |
| 进入就绪队列后的最长等待 | `(n-1) × q` |

举个具体数：`n = 5`，`q = 100 ms`，那么任一进程最多等 `4 × 100 = 400 ms` 就能轮到自己。

**要「公平分配 CPU 时间」，RR 是理想选择。**

### 9.1 时间片大小：两头都是坑

RR 保证了公平，但**等待时间未必最优**，而这完全取决于时间片怎么选。

```text
时间片太大                              时间片太小
──────────────────                     ──────────────────
多数进程还没被抢占                       进程被频繁打断
就先进入 IO 突发了                       上下文切换次数暴涨
  ↓                                       ↓
RR 退化成 FCFS                          CPU 大部分时间在切换
（抢占形同虚设）                          而不是在执行
                                          ↓
                                        进程完成时间反而变长
```

**上下文切换时间是纯开销（pure overhead）**，切换期间系统不做任何有用的工作。

```text
  时间片 = 1000 ms，切换开销 1 ms
  ████████████████████████████████████████│  有效率 ≈ 99.9%
                                          └ 切换

  时间片 = 10 ms，切换开销 1 ms
  ██████████│██████████│██████████│         有效率 ≈ 91%
            └          └          └ 切换

  时间片 = 1 ms，切换开销 1 ms
  █│█│█│█│█│█│█│█│█│█│█│█│█│█│█│█│█│        有效率 ≈ 50%
   └ └ └ └ └ …                              CPU 忙，但没在干活
```

> **如果时间片比平均上下文切换时间还小，CPU 会一直很忙 - 忙着切换，而不是执行。**
> **CPU 利用率拉满，但没做有用功，这个利用率就是没意义的。**

### 9.2 三个新的调度标准

讨论时间片就绕不开几个新指标。

| 指标 | 定义 |
| --- | --- |
| **周转时间（turnaround time）** | 从进程创建到完成的**总时间** = 在就绪队列等待 + 在 CPU 上执行 + 做 IO 操作 |
| **吞吐量（throughput）** | 单位时间内完成的进程数 |
| **响应时间（response time）** | 从提交请求到**产生第一个响应**的时间，**不是**完成执行的总时间 |

关于时间片和周转时间的关系：

**平均周转时间不会随时间片增大而单调改善。**

但总体上有一条经验规律：

> **如果大多数进程能在一个时间片内跑完它的下一次 CPU 突发，平均周转时间就能改善**，因为上下文切换只在必要时才发生。

关于响应时间为什么单列一项：

周转时间**并不总是衡量调度效果的最佳标准**，因为：

* 一个进程常常在**执行完成之前**就开始产出输出了；
* 有些进程**根本不会终止**（服务器、后台服务）。

**响应时间直接决定了用户期待的那种「流畅感」，尤其是在多任务的时候。**

### 9.3 RR 的天花板

RR 是实现并发最简单的方式之一：每个进程拿固定时间片，轮着来，转得够快就像在同时执行。

但**所有处理器都有速度上限**。

```text
  并发进程数 ↑
      │
      │  RR 每轮一圈要花 n × q
      ▼
  每个进程等待更久 → 平均响应时间 ↑ → 「同时执行」的错觉破灭
```

「那把时间片调小不就行了？」

9.1 已经说过，调太小会导致上下文切换爆炸，同样糟糕。

作者给了**三条出路**：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 1. 提升处理器速度 | 上下文切换更快，于是能用更小的时间片而不拖累周转时间 | **需要换硬件** |
| 2. 使用多处理器 | 进程真正并行，分担负载 | **需要换硬件** |
| 3. **更聪明的调度器** | 纯软件即可实现 | 本期剩下的内容 |

## 10. 优先级调度

想想你电脑上正在跑的东西：一边打游戏一边直播，还开着 Outlook、Gmail 客户端、文件管理器，外加一堆后台应用。

东西多到 RR 让你的游戏开始**掉帧**。

问题来了：**这些进程真的都需要同样多的 CPU 时间吗？**

大概率不需要。

> 邮件通知晚半秒送达，真的有关系吗？

如果能**把高优先级正确地分给该得到它的进程**，就能大幅提升整体响应性，**不用升级 CPU，也不用加核心**。

但作者也提醒：**不是所有后台进程都无关紧要**，比如操作系统服务就是关键的。

**难点在于「正确识别」哪些进程需要高优先级。**

### 实现

用**优先队列**，每个进程被赋予一个表示优先级的**整数值**。

| 系统差异 | 说明 |
| --- | --- |
| 取值范围 | 有的系统 `0 ~ 255`，有的 `0 ~ 32,000`（需要更细粒度时） |
| 方向 | 数字小 = 优先级高，还是反过来，**也因系统而异** |

**优先级调度常和 RR 组合使用**：优先级决定谁先跑，RR 保证**同优先级的进程之间公平**。

### 老问题：饥饿

优先级调度有个固有问题：**饥饿**。

在重载系统里，源源不断到来的高优先级进程会让低优先级进程**永远拿不到 CPU**。

听着耳熟？因为 **SJF 本质上就是一种优先级调度** - 它的优先级是「预测的下一次 CPU 突发」的**倒数**。

### IBM 7094 的故事

作者讲了个段子：

```text
1962 年   IBM 7094 发布
          NASA 和美国空军用它跑科学与军事计算
1967 年   有人提交了一个低优先级进程
1973 年   机器关停，人们发现：
          那个 1967 年的进程，一次都没跑过
```

饿了 **6 年**。

### 老化（aging）

解决低优先级进程被无限阻塞的办法叫**老化（aging）**：

> **逐渐提升那些在系统里等了很久的进程的优先级。**

作者的例子：优先级范围 `127`（最低）到 `0`（最高）。

```text
  每隔 1 秒，把等待中的进程优先级 +1（数值 -1）

  t=0s    优先级 127  ░░░░░░░░░░ 最低
  t=30s   优先级 97   ░░░░░░░
  t=60s   优先级 67   ░░░░░
  …
  t=127s  优先级 0    ██████████ 全系统最高 → 必然被执行
```

哪怕初始优先级是最低的 127，**最多 127 秒后它也会变成系统里优先级最高的进程**，从而被执行。

## 11. 多级队列调度

优先级 + RR 混合时，**所有进程可以放在同一个队列里**。

但这样有个实现问题：取决于队列怎么管理，**可能需要一次 O(n) 搜索**才能找到优先级最高的进程。

实践中更简单的做法是：**每个不同的优先级各开一个队列**。

这就是**多级队列调度（multilevel queue scheduling）**。

```text
  优先级 0（最高） ┌────┬────┬────┐
                  │ P1 │ P2 │    │
                  └────┴────┴────┘
  优先级 1        ┌────┬────┬────┐
                  │ P3 │    │    │
                  └────┴────┴────┘
  优先级 2        ┌────┬────┬────┐
                  │ P4 │ P5 │ P6 │
                  └────┴────┴────┘
  优先级 3（最低） ┌────┬────┬────┐
                  │ P7 │    │    │
                  └────┴────┴────┘
```

### 队列之间也需要调度

有了多个队列，就必须决定**队列之间**怎么调度。两种方式：

**方式 A：绝对优先级**

每个队列对所有更低优先级的队列拥有**绝对优先权**。

调度器只需要：**分派最高优先级的非空队列的队头进程**。

缺点显而易见：**低优先级队列会饿死**。

**方式 B：在队列间做时间片轮转**

以 RR 的方式轮转各个队列，但**按队列优先级决定一轮里连续分派多少个进程**。

```text
  轮转一圈：
  优先级 0 队列 ──► 连发 4 个进程
  优先级 1 队列 ──► 连发 3 个进程
  优先级 2 队列 ──► 连发 2 个进程
  优先级 3 队列 ──► 连发 1 个进程
  └──────────────── 回到优先级 0，循环
```

高优先级依然占便宜，但低优先级**总能分到一点**。

### 它的真正价值

多级队列常被用来**按进程类型**把进程分到不同队列里，这样能更好地调度**有不同响应时间需求**的进程。

它甚至允许**每个队列用不同的调度算法**：

```text
  前台队列（foreground）  ──► Round Robin      （交互式，要响应快）
  后台队列（background）  ──► FCFS             （批处理，不在乎延迟）
```

> **这基本上就是我们对通用调度器的期待：给交互式进程优先权，但不至于把低优先级的饿死。**

## 12. 多级反馈队列调度

还有最后一个问题要解决。

在典型的多级队列调度里，**进程进入系统时被永久分配到某个队列**。

好处是**开销低**，坏处是**不灵活** - 因为**进程在生命周期里的行为不是一成不变的**。

作者的例子：你的邮件客户端。

```text
  大部分时间：安静地在后台跑，偶尔查一下新邮件   → IO 密集，低优先级就够
  你点开它的那一刻：菜单、按钮、表单都要立刻响应  → 需要高优先级
```

**一个进程的 CPU 使用模式，以及由此推出的响应时间需求，是会动态变化的。**

**多级反馈队列（multilevel feedback queue）**就是为适应这种动态变化而设计的。

### 工作方式

```text
  所有进程从最高优先级队列开始

  Q0  时间片 = 8 ms   ┌────┬────┐
      ▲               │ P1 │ P2 │
      │ 突发比上层时   └────┴────┘
      │ 间片还短，升级       │ 一个时间片没跑完 → 降级
      │                      ▼
  Q1  时间片 = 16 ms  ┌────┬────┐
      ▲               │ P3 │    │
      │               └────┴────┘
      │                      │ 还是没跑完 → 继续降级
      │                      ▼
  Q2  时间片 = 32 ms  ┌────┬────┐
                      │ P4 │ P5 │
                      └────┴────┘
```

规则：

1. **每个进程都从最高优先级队列开始。**
2. 如果进程在**一个时间片内**跑完了它的 CPU 突发，做完 IO 后**仍然回到该队列**。
3. 如果进程需要的 CPU 时间**超过了时间片**，把它**降到更低优先级的队列**。
4. **越低优先级的队列，时间片越大。**
5. 表现得像 IO 密集型的进程（在高优先级队列分配的时间片内就完成突发）可以**升回去**。

效果是**自动的行为分类**：

```text
  短 CPU 突发的进程  ──► 倾向于留在高优先级队列
  CPU 密集型的进程   ──► 逐渐沉到低优先级队列
```

**系统根据行为自动调整进程优先级，不需要任何人工配置。**

### 它有无数种变体

作者原话是「有各种颜色和口味」。

不只是**每个队列用什么调度算法**可以不同，**决定何时升降级的判据**也可以不同。

例如：与其只看最近一次观测到的 CPU 突发来调整优先级，系统可以用**基于历史数据的预测**（就是 7.3 那个指数平均），这样能**避免因为个别异常突发（特别短或特别长）而产生不必要的队列切换**。

### 12.1 「这不是在惩罚 CPU 密集型进程吗？」

如果你一直在认真看，可能会有这个疑问：

> 我们仅仅因为一个进程需要更多 CPU 就降它的级，这不是和「给重要进程更高优先级」的初衷相悖吗？
> 老化确实能防饥饿，但一旦某个进程被识别为 CPU 密集型，它**终究还是会被降级**。

作者说这个问题不上一节 40 分钟的进程分析课很难讲清楚，但可以给出**两个关键事实**：

**事实一：IO 密集型和交互式进程不是一回事，但两者都以极短的 CPU 突发为特征。**

也就是说，降级机制筛选出的「高优先级常客」，恰好覆盖了我们真正在意的交互式进程。

**事实二：现代处理器极快。**

```text
  打开任务管理器 → 看到几百个进程在跑
  打开资源监视器 → 它们加起来占用不到 10% 的 CPU 时间
```

两个事实合起来揭示了一件事：

> **大部分时间里，高优先级队列其实是空的。**

所以一个进程沉到最低优先级队列，**并没有听上去那么惨** - 在不依靠老化的情况下被分派，其实比我们想象的更有可能。

### 12.2 回到开头那个现象

现在可以解释视频开头的场景了：

```text
  系统重载（渲染视频 / 跑 benchmark）
  CPU 占用 100%
        │
        ├─► 桌面依然流畅
        ├─► 音乐继续播放
        └─► 浏览器依然响应

  为什么？
  调度器优先服务日常的交互式任务（短突发，待在高优先级队列），
  而那些不频繁的 CPU 重载进程，只拿高优先级进程用剩下的 CPU 周期。
```

把多级队列和多级反馈队列并排放，**哪个更像「通用」的？** 答案很明显。

## 14. 最后的两点澄清

作者在结尾特意补了两个「本期为了讲清楚而做的简化」。

### 14.1 现代系统调度的是线程，不是进程

```text
  一个 CPU 密集型应用
  ┌──────────────────────────────────────┐
  │  线程 A：管理用户界面                 │ ──► 短突发 → 留在高优先级队列
  │  线程 B：执行繁重计算                 │ ──► 长突发 → 沉到低优先级队列
  └──────────────────────────────────────┘
        两个线程的优先级彼此独立
```

这带来了**单个应用内部的并发**：一个线程处理界面，另一个做后台计算。

配合多级反馈队列，**一个吃 CPU 的应用，它的界面依然可以保持流畅** - 因为管 UI 的线程能独立于计算线程维持高优先级。

线程相关内容见 [为什么单核处理器也需要线程](12-why-are-threads-needed-on-single-core-processors.md) 和 [多核处理器上的线程](13-threads-on-multicore-systems.md)。

### 14.2 本期画的 IO 队列是简化的

视频里为了清晰，把 IO 队列画成了 FIFO 队列。

**真实的 IO 子系统要复杂得多：进入 IO 队列的进程，完成顺序可能和到达顺序不同。**

道理和 CPU 调度一样：

> 就像 FCFS 对 CPU 调度低效一样，它对 IO 设备也不是好选择。
> 一个要用显卡的进程，凭什么排在一个正在用磁盘的进程后面？

但这些细节属于操作系统的**另一个组件：IO 调度器（IO scheduler）**，不在本期范围内。

## 15. 核心总结

整条演进路线，每一步都是被上一步的具体缺陷逼出来的：

```text
CPU 调度的演进
│
├── 事实基础：进程不连续使用 CPU
│   ├── CPU burst 和 IO burst 交替出现
│   ├── 突发时长分布：大量短突发 + 少量长突发
│   └── → 调度粒度是「一次 CPU 突发」，不是「一个进程」
│
├── ① FCFS（FIFO 队列）
│   ├── 优点：最简单
│   └── 败于：护航效应 → CPU 和 IO 设备轮流空闲
│
├── ② SJF（优先队列，优先级 = 下次突发长度）
│   ├── 优点：可证明的最小平均等待时间
│   ├── 麻烦：未来不可知 → 指数平均预测 τ(n+1) = α·t(n) + (1-α)·τ(n)
│   │         递归展开 → 只需存一个数，老数据指数衰减
│   └── 败于：饥饿（长突发进程可能永远等不到）
│
├── ③ Round Robin（FIFO + 抢占 + 时间片）
│   ├── 前提：硬件定时器（抢占必须有硬件支持）
│   ├── 保证：n 个进程时，等待至多 (n-1)q，各得 1/n
│   ├── 时间片太大 → 退化成 FCFS
│   ├── 时间片太小 → 上下文切换开销吃掉一切
│   └── 败于：进程数一多，平均响应时间崩溃
│
├── ④ 优先级调度（整数优先级 + 优先队列）
│   ├── 洞察：不是所有进程都需要同样多的 CPU
│   ├── 常与 RR 组合（同优先级内部公平）
│   ├── 饥饿 → 老化（aging）：等得久就逐步升优先级
│   └── 败于：同一队列里找最高优先级可能要 O(n)
│
├── ⑤ 多级队列（每个优先级一个队列）
│   ├── 队列间调度：绝对优先 或 加权轮转
│   ├── 每个队列可用不同算法（前台 RR / 后台 FCFS）
│   └── 败于：进程被永久绑定队列，而进程行为会变
│
└── ⑥ 多级反馈队列
    ├── 全部从最高优先级队列起步
    ├── 一个时间片内跑完 → 留下 / 升级
    ├── 跑不完 → 降级（低优先级队列时间片更大）
    ├── → 自动把进程分为「交互式」和「CPU 密集型」
    └── 降级不残酷：现代 CPU 极快，高优先级队列大部分时间是空的

调度标准（贯穿全程的取舍）
├── CPU 利用率（CPU utilization）
├── 吞吐量（throughput）
├── 周转时间（turnaround time）
├── 等待时间（waiting time）
└── 响应时间（response time）  ← 通用系统最看重的那个
```

> CPU 调度的全部难题，可以浓缩成一句话：**CPU 只有一个，而「谁更该用它」这个问题没有唯一正确答案。**
> 从 FCFS 到多级反馈队列，算法一路变复杂，优化的目标却始终没变 - 不是让某个程序跑得最快，而是让**人**觉得这台机器一直在听自己的。
> 所以当 CPU 跑满 100%、你的桌面依然跟手时，那不是因为 CPU 还有余力，而是因为**调度器判断你比那个 benchmark 更重要**。
