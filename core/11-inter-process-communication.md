# 进程间通信（IPC）：共享内存还是发消息

> 视频来源：Core Dumped -《IPC: To Share Memory Or To Send Messages》
> https://www.youtube.com/watch?v=Y2mDwW2pMv4

## 0. 这一期在讲什么

作者开场展示了一张分形图（fractal），但它不是图片，而是一个**由两个进程协作渲染出来的程序**：

```text
┌───────────────────────────┐                 ┌───────────────────────────┐
│  进程 A（Rust）            │                 │  进程 B（TypeScript）      │
│                           │   ① 算完像素     │                           │
│  数学计算：算出每个像素     │   ② 触发事件     │  监听事件                  │
│  的颜色                    │ ─────────────►  │  收到数组                  │
│  结果写进一个数组           │   把数组当作     │  交给绘图函数              │
│                           │   「消息」发出    │  画到 HTML canvas 上       │
└───────────────────────────┘                 └───────────────────────────┘
```

这种**模块化（modular）**的应用之所以能存在，靠的就是进程间通信（inter-process communication，IPC）。

前一期我们学到：程序被加载进内存开始执行后，会换一个名字叫**进程（process）**。
但进程不只是「装进内存的可执行代码」，它还包括：

| 进程包含的东西 | 说明 |
| --- | --- |
| 可执行代码 | 加载进内存的程序本体 |
| CPU 状态（CPU state） | 寄存器、程序计数器等 |
| 内存区域 | 操作系统分配给它的地址空间 |
| 打开的文件列表 | 一组文件描述符 |
| 其他资源 | IO 设备等 |

所以进程不是程序，而是**程序运行所处的整个上下文（context）**。

本期回答的问题是：**默认彼此隔离的进程，怎么交换信息？**

## 1. 问题：隔离带来的副作用

隔离是好事，但它带来一个严重的缺点。

现实中有大量场景需要进程和别的进程**合作**。
如果进程被完全隔离，它们根本无法协作。

于是进程可以按「是否与其他进程合作」分成两类：

```text
进程
├── 独立进程（independent process）
└── 合作进程（cooperating process）
```

两个共享数据的进程显然是合作进程。
但需要让进程合作的理由不止「共享数据」一条：

| 理由 | 含义 |
| --- | --- |
| 计算加速（computational speed up） | 在支持并行的系统上，把复杂任务切成小任务同时执行，缩短总耗时 |
| 模块化（modularity） | 把系统功能拆到不同进程里，用模块化的方式搭系统 |

注意这两种情况都有同一个前提：**进程必须有办法协调彼此的活动**，否则无法正确工作。

合作进程需要一套 IPC 机制来收发数据。
而 IPC 有两种基本模型：

```text
                     进程间通信
                          │
          ┌───────────────┴───────────────┐
          ▼                               ▼
   共享内存                          消息传递
（shared memory）                （message passing）
   直接共享一块地址空间              地址空间保持隔离，靠内核转发消息
```

## 2. 共享内存：把隔离主动拆掉

### 2.1 原本的隔离是怎么来的

系统里跑多个进程时，操作系统给每一个都分配一块独立的内存，这就是进程的**地址空间（address space）**。

操作系统通过**特权指令（privileged instructions）**这套机制来强制隔离：

```text
进程 A 试图读/写 进程 B 的地址空间
              │
              ▼
   操作系统立即中断并终止进程 A
              │
              ▼
   隔离策略得以执行，数据安全得到保障
```

所以想让两个（或更多）进程共享一块内存，**操作系统要求它们双方同意解除这条限制**。

### 2.2 建立与挂载

典型流程是这样的：

```text
① 进程 A 用系统调用创建共享内存区
   -> 这块区域驻留在「创建者」的地址空间里

┌──────────────────────┐        ┌──────────────────────┐
│ 进程 A 地址空间       │        │ 进程 B 地址空间       │
│  ┌────────────────┐  │        │                      │
│  │  共享内存区     │  │        │                      │
│  └────────────────┘  │        │                      │
└──────────────────────┘        └──────────────────────┘

② 想通过这块区域通信的进程，也要用系统调用
   把它「挂载（attach）」到自己的地址空间

┌──────────────────────┐        ┌──────────────────────┐
│ 进程 A 地址空间       │        │ 进程 B 地址空间       │
│  ┌────────────────┐  │        │  ┌────────────────┐  │
│  │  共享内存区     │◄─┼────────┼─►│  同一块物理内存 │  │
│  └────────────────┘  │        │  └────────────────┘  │
└──────────────────────┘        └──────────────────────┘

③ 建立完成后，双方直接读写这块区域即可通信
```

### 2.3 关键细节：操作系统撒手不管

这是本节最重要的一点。

**共享内存区一旦被操作系统授予，操作系统就不再管进程拿它做什么了。**

具体来说：

* 数据以什么结构组织，
* 数据写在共享区里的哪个具体位置，

**完全由进程自己决定，操作系统不参与。**

### 2.4 出错的三种方式（生产者-消费者例子）

考虑一个**生产者-消费者（producer-consumer）**模型：
生产者进程产生数据，消费者进程读取数据。
假设共享区里是一个数组，生产者往里写**8 位有符号数（8-bit signed）**。

**错误一：符号解释不一致。**
如果消费者把这些字节读成 8 位无符号数，它看到的是**完全相同的比特**，但含义变了：

```text
共享区里的同一个字节
┌──────────┐
│ 11111111 │
└──────────┘
     │
     ├─ 生产者的本意：i8  ->   -1
     └─ 消费者的解读：u8  ->  255
```

| 字节 | 按 i8 解读 | 按 u8 解读 |
| --- | --- | --- |
| `00000001` | 1 | 1 |
| `01111111` | 127 | 127 |
| `10000000` | -128 | 128 |
| `11111111` | -1 | 255 |

注意前两行是一致的，后两行完全对不上。
这意味着 bug 只在某些数值出现时才暴露，非常难查。

**错误二：数据宽度不一致。**
如果消费者期望的是别的类型，比如 32 位无符号整数，那它会把 4 个字节吞成 1 个数：

```text
生产者写入（4 个 i8）
┌──────┬──────┬──────┬──────┐
│  1   │  2   │  3   │  4   │
└──────┴──────┴──────┴──────┘
   │       │      │      │
   └───────┴──────┴──────┘
             │
             ▼
  消费者按 u32 读取，得到 1 个巨大的数
  （4 个元素被吃掉，后续所有读取全部错位）
```

**错误三：读错地址。**
即使类型对上了，只要消费者从错误的地址开始读，一样是误读（misinterpretation）：

```text
共享区
        ┌────┬────┬────┬────┬────┐
地址：   │ +0 │ +1 │ +2 │ +3 │ +4 │
        └────┴────┴────┴────┴────┘
          ▲         ▲
          │         └─ 消费者从这里开始读（错）
          └─ 生产者从这里开始写（对）
```

结论：

> 消费者必须**精确地**知道数据是怎么组织的、写在什么位置。
> 不遵守这些约定，结果是一个或两个进程失败，或者更糟：**未定义行为（undefined behavior）**。

### 2.5 还有竞态条件

进程还要自己负责**不在同一时刻写同一个位置**，否则会遇到**竞态条件（race condition）**。

作者说这个问题会在后续讲**线程同步（thread synchronization）**的一期里展开，本期不深入。

所以共享内存的责任分配是这样的：

```text
操作系统负责                 进程自己负责
──────────────────          ──────────────────
创建共享区                    数据结构约定
处理挂载请求                  写入位置约定
（此后不再介入）               类型与宽度一致
                            读写时序（避免竞态）
                            出错后的一切后果
```

## 3. 谁在用共享内存：Chromium

你可能注意到，用 Chrome 时**即使只开一个标签页，也会创建多个进程**。

任何基于 Chromium 的浏览器都是模块化系统的完美例子，而它依赖 IPC。

动机很直接：动态网页里常有 JavaScript，而 JavaScript 可能带 bug，bug 可能把浏览器搞崩。

Chromium 用**共享内存**方案，把任务分给三类进程：

| 进程类型 | 职责 | 数量 |
| --- | --- | --- |
| 浏览器进程（browser） | 管理用户界面和 IO 操作 | Chrome 启动时只创建一次 |
| 渲染进程（renderer） | 处理网页内容：HTML、JavaScript、图片 | 每个打开的标签页一个 |
| 插件进程（plug-in） | 管理具体插件，如 Flash、QuickTime、PDF 阅读器 | 按插件 |

```text
        ┌──────────────────────────┐
        │   browser 进程（唯一）    │
        │   UI + IO                │
        └───────────┬──────────────┘
                    │ 共享内存
     ┌──────────────┼──────────────┬──────────────┐
     ▼              ▼              ▼              ▼
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│renderer  │  │renderer  │  │renderer  │  │plug-in   │
│ tab 1    │  │ tab 2    │  │ tab 3 ✗  │  │ PDF      │
└──────────┘  └──────────┘  └──────────┘  └──────────┘
                                  │
                                  └─ 崩溃只带走这一个渲染进程
                                     其他标签页不受影响
```

这种隔离保证了：**某个标签页崩溃时，只有它的渲染进程挂掉**，其他标签页照常运行。

其他使用共享内存的系统还有：

* 仿真软件（simulation software）
* 游戏引擎（game engines）
* 数据库管理系统（DBMS）
* 深度学习框架（deep learning frameworks）

## 4. 消息传递：让操作系统当中间人

共享内存并不总是最好的选择，因为它**容易出错**，而且把**过多的责任压在程序员身上**，未必人人都愿意承担。

另一种做法是：操作系统提供一套机制，让进程在**不共享地址空间**的前提下通信并同步动作。

```text
共享内存                          消息传递
──────────────────               ──────────────────
拆掉隔离，直接读写共享区            隔离保持不变
数据在进程地址空间里                进程发送/接收消息，数据由内核搬运
```

常见的消息传递机制：**管道（pipes）**、**套接字（sockets）**、**远程过程调用（remote procedure calls，RPC）**。

这些机制的具体实现超出本期范围，但总体概念如下。

### 4.1 链接其实是逻辑路径

假设有两个进程 A 和 B，A 想给 B 发消息：

```text
① A 发起系统调用，请求操作系统与 B 建立一条「链接（link）」
② 这条链接是消息传输的「逻辑路径（logical pathway）」
```

注意「**逻辑**」这个词。
实际发生的是：**操作系统内核在自己的地址空间里创建了一个队列（queue）**。
这个队列就是 A 发、B 收的**邮箱（mailbox）**。

```text
   用户地址空间                内核地址空间                用户地址空间
┌────────────────┐   ┌──────────────────────────┐   ┌────────────────┐
│                │   │                          │   │                │
│   进程 A       │   │   邮箱（队列）            │   │   进程 B       │
│                │──►│  ┌────┬────┬────┬────┐   │──►│                │
│                │   │  │ m1 │ m2 │ m3 │ …  │   │   │                │
│                │   │  └────┴────┴────┴────┘   │   │                │
└────────────────┘   └──────────────────────────┘   └────────────────┘
                        进程碰不到这块地方
```

### 4.2 队列的行为可以调

队列的行为依通信需求而变：

| 需求 | 队列形态 |
| --- | --- |
| 异步（asynchronous）而非同步（synchronous）通信 | 发送方不等接收方 |
| 想限制邮箱能存的消息数 | 带缓冲的队列（buffered queue） |
| 全双工（full duplex）通信 | **一个邮箱用两个队列实现** |

全双工的样子：

```text
┌──────────┐    队列 1：A -> B    ┌──────────┐
│          │ ──────────────────► │          │
│  进程 A  │                      │  进程 B  │
│          │ ◄────────────────── │          │
└──────────┘    队列 2：B -> A    └──────────┘

两个方向同时发送，互不冲突
```

### 4.3 矛盾点：邮箱在内核里，进程碰不到

有人应该已经发现不对劲了：既然邮箱位于操作系统的地址空间，进程本来就不该能访问它。

确实如此。**进程不能直接读写邮箱。**

所以操作系统必须为至少两个操作提供系统调用：`send` 和 `receive`。

```text
进程 A 要发消息：
  「我要把这条消息放进和 B 共享的邮箱，
    但我没法直接访问它，请你帮我处理。」
                │
                ▼
   邮箱在内核地址空间里，操作系统可以把消息复制进邮箱

进程 B 要收消息：
  「我没法直接读和 A 共享的邮箱，
    麻烦你看看有没有我的消息？」
                │
                ▼
   如果有消息，操作系统把它作为函数的返回值返回给 B
```

作者提醒：如果不太明白为什么这里非得用系统调用，建议回看本系列前面几期（尤其是内核态与用户态那一期）。

## 5. Mach 与「端口」

最早引入**共享邮箱**这一想法的操作系统之一是 **Mach**。
它的衍生系统构成了一些现代系统的基础，包括 **iOS** 和 **macOS**。

Mach 的术语：

| 通用叫法 | Mach 的叫法 |
| --- | --- |
| 进程（process） | 任务（task） |
| 邮箱（mailbox） | **端口（port）** |

有一点很重要：

> **消息是发给端口的，不是直接发给进程的。**

这个区分之所以重要，有两个原因：

1. 两个进程之间可以有**多条**通信链接；
2. 并非所有端口都只关联恰好两个进程。

一个进程可以保持一个开放端口，用来接收**任何**其他进程发来的消息。
这种端口叫**监听端口（listening port）**，它的用途是处理一类特殊消息：**连接请求（connection request）**，从而在进程之间建立新的**私有通信链接**。

```text
                        ┌──────────────────────────┐
   进程 X ──连接请求──►  │  监听端口（listening）    │
   进程 Y ──连接请求──►  │  只收 connection request │
   进程 Z ──连接请求──►  └────────────┬─────────────┘
                                     │ 接受后
                                     ▼
                        为每个客户建立私有链接
                   ┌──────────┬──────────┬──────────┐
                   │ 私有端口 │ 私有端口 │ 私有端口 │
                   │  ↔ X    │  ↔ Y     │  ↔ Z     │
                   └──────────┴──────────┴──────────┘
```

到这里有些概念应该开始耳熟了。

## 6. 消息传递的大优势：可以跨机器

消息传递有一个巨大优势：

> 因为它**不要求两个进程共享地址空间**，所以两个进程甚至**不需要在同一台机器上**。

当然，这需要更复杂的底层实现：

```text
跨机器消息传递需要的东西
├── 网络能力（networking capabilities）：在计算机之间建立连接
└── 驱动级编程：网卡（network interface card）等组件
```

但只要在操作系统层面实现正确，对开发者来说这个过程应该是**无感的（seamless）**：

> **不同机器上的进程之间的消息传递，用起来和同一台机器上的进程之间完全一样。**

## 7. 客户端-服务器与套接字

客户端-服务器（client-server）架构通常用**套接字接口（socket interface）**实现，
它是几乎所有主流操作系统今天都支持的一种消息传递机制。

它通常被画成这样，不过**作者说他并不完全同意这种画法**：

```text
经典画法（作者有异议）            作者的观点
──────────────────               ──────────────────
┌────────┐    ┌────────┐         客户端和服务器不是「机器」
│ Client │───►│ Server │         它们只是跑在机器上的「进程」
│ (机器) │    │ (机器) │         而且通信并不总是需要网络
└────────┘    └────────┘         用 localhost 测项目时，
                                 两者就跑在同一台机器上
```

客户端向服务器发请求时，两个地址项各管一件事：

```text
        192.168.1.10  :  8080
        └────┬─────┘     └─┬─┘
             │             │
   标识「托管服务器进程的   代表服务器进程接收
    是哪台机器」            请求用的那个「邮箱」
```

| 组成 | 对应概念 |
| --- | --- |
| IP 地址 | 机器（host） |
| 端口（port） | 服务器进程用来收请求的邮箱 |

提供具体服务的服务器，比如 HTTP、FTP、SSH，都依赖套接字接口。

## 8. 消息传递的代价：系统调用开销

消息传递也有缺点。

因为端口位于**内核的地址空间**，进程每次收发消息**都必须走系统调用**。
这在性能上可能相当昂贵。

```text
消息传递：每一条消息都要过内核
   send  ->  系统调用 -> 内核复制 -> 队列
   recv  ->  系统调用 -> 内核复制 -> 用户
   ↑ 每次收发都付一次开销

共享内存：只在建立阶段过内核
   创建共享区    ->  系统调用（一次）
   挂载到进程    ->  系统调用（一次）
   ─────────────────────────────────
   之后读/写     ->  0 次系统调用
   ↑ 像访问自己的地址空间一样直接读写
```

共享内存没有这个限制：系统调用只在**创建共享区**和**把进程挂载上去**时才需要。
这两步完成后，进程读写共享区就**像它是自己地址空间的一部分**一样，不再需要额外的系统调用。

结果是通信极快，**本质上和直接内存访问一样快**。

作者最后专门澄清了一句，避免被误读：

> 我不是说消息传递慢，只是共享内存更快。
> **99% 的情况下，消息传递完全够用。**

## 10. 核心总结

```text
进程间通信（IPC）
│
├── 为什么需要
│   ├── 进程 = 代码 + CPU 状态 + 内存区域 + 打开文件 + 其他资源
│   ├── 默认隔离 -> 无法协作
│   └── 需要协作的三个理由
│       ├── 共享数据
│       ├── 计算加速（拆任务并行跑）
│       └── 模块化（功能拆进不同进程）
│
├── 方案一：共享内存（shared memory）
│   ├── 建立：创建者用系统调用建区，其他进程 attach 到自己地址空间
│   ├── 操作系统只授权，不管内容
│   │   ├── 数据结构由进程约定
│   │   └── 写入位置由进程约定
│   ├── 三种典型误读（生产者-消费者）
│   │   ├── i8 被读成 u8：11111111 -> -1 还是 255
│   │   ├── 4 个 i8 被读成 1 个 u32：后续全部错位
│   │   └── 从错误地址开始读
│   ├── 后果：一方或双方失败，或未定义行为
│   ├── 竞态条件也要自己防（留给线程同步那一期）
│   ├── 优点：建立后 0 次系统调用，快到等于直接内存访问
│   └── 用例：Chromium（browser / renderer / plug-in）
│           仿真软件、游戏引擎、DBMS、深度学习框架
│
├── 方案二：消息传递（message passing）
│   ├── 机制：pipes / sockets / RPC
│   ├── 链接是「逻辑」路径，真身是内核地址空间里的队列
│   ├── 队列 = 邮箱，可异步、可带缓冲，全双工用两个队列
│   ├── 进程碰不到邮箱 -> 必须有 send / receive 两个系统调用
│   ├── Mach：进程叫 task，邮箱叫 port
│   │   ├── 消息发给端口，不是发给进程
│   │   ├── 两进程可有多条链接，端口不限于两个进程
│   │   └── 监听端口收 connection request，建立私有链接
│   ├── 最大优势：不共享地址空间 -> 进程可以不在同一台机器
│   │   ├── 代价：网络能力 + 网卡驱动级实现
│   │   └── 实现得好则对开发者无感，跨机与本机用法一致
│   ├── client-server 用 socket 接口实现
│   │   ├── IP = 机器，port = 服务器进程的邮箱
│   │   └── 客户端/服务器是进程不是机器，localhost 就在同机
│   └── 缺点：每次收发都要系统调用 -> 性能开销
│
└── 怎么选
    ├── 共享内存更快，但把正确性责任全交给程序员
    ├── 消息传递更安全省心，还能跨机器，但每条消息付一次内核开销
    └── 99% 的情况下消息传递够用
```

> 隔离是进程模型最大的优点，而 IPC 是主动在这层保护上开的口子。
> 开口子有两种开法：要么把墙拆掉一块共用（共享内存），从此约定全靠自己守，换来的是内存级的速度；要么让墙保持完整，托操作系统在中间送信（消息传递），换来的是安全、省心，以及一条能延伸到另一台机器的通路。
> 前者快，后者远。绝大多数时候，你需要的是后者。
