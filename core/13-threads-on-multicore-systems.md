# 多核系统上的线程：从并发到并行

> 视频来源：Core Dumped -《Threads On Multicore Systems》
> https://www.youtube.com/watch?v=5sw9XJokAqw

## 0. 这一期在讲什么

上一期讲了线程的基本原理，并且明确说过：**那些内容在单核处理器上就已经全部成立**。

这一期专门讨论线程在**多核处理器（multi-core processor）系统**上扮演的角色，也就是**并行（parallelism）**。

需要的前置背景仍然是**并发（concurrency）**：只有一个 CPU 却有多个进程时，操作系统靠极快地轮换 CPU 访问权，让人感觉所有进程在同时运行。

---

## 1. 回顾：线程解决的两个问题

上一期得出的结论是，线程在写程序时有两个关键用处：

| 场景 | 线程带来的好处 |
| --- | --- |
| 同一程序里一个任务耗时很长、另一个只要几毫秒 | 并发保证短任务不必等很久才能开始运行 |
| 某个任务在等 IO 资源（读文件、等网络响应） | 它用不了 CPU 的这段时间，操作系统可以分给别的就绪任务，而不是让 CPU 干等 |

所以**线程只是一种告诉操作系统「同一进程内的多个任务可以并发执行」的方式**。
它让应用程序能同时做多件事。

作者给的例子是一个邮件客户端：

```text
邮件客户端进程
├── 线程：在屏幕上显示用户界面
├── 线程：监听用户的键盘输入
├── 线程：从文件系统上传附件（比如一张照片）
├── 线程：做语法检查
└── 线程：监控是否有新邮件到达

要有好的用户体验 → 这些任务谁都不该等谁
```

## 2. 问题：并发任务多到一定程度，就不流畅了

实现并发是有代价的。

如果并发任务的数量增长得太多，到某个点系统就不再流畅了。
**哪怕 CPU 轮换得极快**，任务多到一定程度，每个任务**重新拿回 CPU 所要等的时间就太长了**。

```text
少量任务：每个任务很快能轮到
T1 ┤█   █   █   █   █   █
T2 ┤ █   █   █   █   █   █
T3 ┤  █   █   █   █   █   █
      ↑ 间隔短，感觉流畅

大量任务：轮一圈要很久
T1  ┤█                       █
T2  ┤ █                       █
... │
T50 ┤                █
      ↑ 同一个任务两次拿到 CPU 之间隔了很久 → 卡顿
```

---

## 3. 三种可能的解法

| 解法 | 思路 | 问题 |
| --- | --- | --- |
| ① 把 CPU 做得更快 | 同样时间内处理更多工作，任务就能更快重新拿到 CPU | 任务数继续涨，还是会回到原点；而且**过去十几年里让 CPU 变快已经越来越难** |
| ② 更聪明地调度 CPU 访问权 | 优化调度策略 | 复杂度高，值得单独一期，本期不展开 |
| ③ 加处理器 | 一个处理器再快也扛不住太多任务，那就多来几个 | 暴力，但有效 |

第 ③ 条和第 ① 条一样属于**暴力（brute force）路线**：**单个处理器无论多快都处理不完这么多任务，那就干脆多加处理器**。

## 4. 「多处理器」有几种实现形式

```text
① 多个 CPU 插槽（socket）              ② 多核处理器（multi-core）
┌──────────────────────────┐          ┌──────────────────────────┐
│ 主板                      │          │ 主板                      │
│  ┌────────┐  ┌────────┐  │          │  ┌────────────────────┐  │
│  │ CPU 1  │  │ CPU 2  │  │          │  │ 单个封装 / 芯片      │  │
│  └────────┘  └────────┘  │          │  │ ┌───┐┌───┐┌───┐┌───┐│  │
└──────────────────────────┘          │  │ │核1││核2││核3││核4││  │
                                      │  │ └───┘└───┘└───┘└───┘│  │
③ 两者结合（较少见）                    │  │      共享 cache      │  │
   同一块主板上插多颗多核芯片            │  └────────────────────┘  │
                                      └──────────────────────────┘
```

### 术语澄清

处理器相关的术语相当含混，作者特意澄清了一下：

| 术语 | 含义 |
| --- | --- |
| CPU | 常用来指**整个封装 / 芯片** |
| 核心（core） | 封装内部的每个处理单元，本质上就是一个 CPU，只是**和其他核心共享一些部件（比如 cache）** |

关键是最后一句：**每个核心在操作系统看来都是一个独立的处理器**。
所以本期大量出现的「核心」就是这个意思。

## 5. 并发（concurrency）与并行（parallelism）的区别

考虑一个有 **8 个线程**的应用：

```text
单核系统：并发但不并行
core0 ┤T1│T2│T3│T4│T5│T6│T7│T8│T1│T2│...
        └── 交错（interleaved），任一时刻只有一个线程在跑

四核系统：并发 + 并行
core0 ┤███ T1 ███│███ T5 ███
core1 ┤███ T2 ███│███ T6 ███
core2 ┤███ T3 ███│███ T7 ███
core3 ┤███ T4 ███│███ T8 ███
        └── 这四个是真正在同一时刻运行
```

在单核系统上，并发**仅仅意味着线程的执行在时间上交错**，因为处理核心一次只能执行一个线程。

在多核系统上，并发有了新的含义：**一部分线程可以真正同时运行**，因为系统能把每个线程分配到不同的核心上。
这时我们面对的就不只是并发了，而是**并行**。

| | 并发系统（concurrent） | 并行系统（parallel） |
| --- | --- | --- |
| 定义 | 支持多个任务，让**所有任务都能取得一些进展** | 能**真正同时**执行一个以上的任务 |
| 单核可否 | 可以 | 不可以 |

所以：**可以有并发而没有并行**。

并行系统的一大优势是：**多任务的流畅感不再那么依赖「快速交错」制造出来的错觉**，它是真的在同时跑。

到这里也就更清楚了：**为什么几乎所有现代操作系统都把线程而不是进程当作最基本的执行单元**。

## 6. 对程序员意味着什么：只管声明并发

多核处理器已成标准，同一进程内的线程可以充分利用并行。

对我们写程序的人来说，这意味着：

```text
想让任务并行执行
        │
        └─► 你要做的只有一件事：用线程把这些任务声明为「可并发」
                    │
                    └─► 剩下的交给操作系统：
                          ├─ 没有多余核心 → 在线程间交错分配 CPU
                          └─ 有多核处理器 → 每个线程分一个核心
```

这让我们的程序**更具可移植性（portable）**：**不需要针对特定的核心数量去编译**。

### 但要始终记住两件事

**① 核心数是固定的。**

创建一千个线程，**不代表**一千个任务会并行运行。
如果系统有 n 个核心，那么在任意时刻**最多有 n 个线程真正并行执行**。

```text
n = 4 核，程序创建 1000 个线程

任意时刻：
core0 ┤ 线程 a
core1 ┤ 线程 b     ← 真正并行的最多 4 个
core2 ┤ 线程 c
core3 ┤ 线程 d
其余 996 个线程 → 等待被调度（回到交错）
```

**② 注意是「最多 n 个」，因为线程要争抢资源。**

即使我们精确地按核心数创建线程，**其他进程的线程也需要 CPU 时间**。
操作系统的主要目标之一是**保证 CPU 资源在所有线程之间公平分配**，因此它会限制我们自己的线程有多少能真正并行。

## 7. 并行的另一个理由：性能

这一点很直白：**如果能真正同时运行多个任务，那么完成这些任务的总时间，就会比在单核系统上顺序执行少得多**。

并行一般分两类：

| 类型 | 分发的对象 | 每个核心做的事 |
| --- | --- | --- |
| 数据并行（data parallelism） | **数据的子集** | 所有核心做**同一种操作**，只是数据不同 |
| 任务并行（task parallelism） | **任务 / 线程** | 每个线程做**各自不同的操作** |

任务并行下还有多种情形：不同线程可能操作**同一份数据**，也可能操作**不同的数据**。

```text
数据并行                          任务并行
┌─────────────────────┐          ┌─────────────────────┐
│ 数据 → 切成 4 份      │          │ 同一份数据           │
│  ├─核0：同一操作(块1) │          │  ├─核0：操作 A       │
│  ├─核1：同一操作(块2) │          │  ├─核1：操作 B       │
│  ├─核2：同一操作(块3) │          │  ├─核2：操作 C       │
│  └─核3：同一操作(块4) │          │  └─核3：操作 D       │
└─────────────────────┘          └─────────────────────┘
```

## 8. 例子一：找出数组中的所有素数（数据并行）

> 作者原本计划在这一期演示实际的并行编程代码，但他把自己的电脑搞坏了，所以代码示例留到下一期，本期只看动画示例。

问题：有一个存着大量数字的数组，任务是找出其中所有的素数。

这需要遍历整个数组，逐个判断是否为素数。

**关键点在于：判断某个数是不是素数，其结果不依赖数组中其他数字的判断结果。**

```text
想知道最后一个数是不是素数？
不需要等前面的数被检查完 → 每个数都可以独立处理
```

于是在四核处理器上，可以把数据切成四等份，每份交给一个核心：

```text
原数组
┌───────────────────────────────────────────────────────┐
│ 2  9 15 23 41 ... │ ... │ ... │ ...              101  │
└─────────┬─────────┴──┬──┴──┬──┴──────┬────────────────┘
          ▼            ▼     ▼         ▼
       ┌─────┐     ┌─────┐┌─────┐  ┌─────┐
       │核心0│     │核心1││核心2│  │核心3│
       └─────┘     └─────┘└─────┘  └─────┘
       is_prime()  is_prime()      is_prime()   ← 同一个操作
```

这是**数据并行**的例子：**所有核心对分发下去的数据子集执行同一种操作**。

### 但四个核心不等于四倍性能

作者明确提醒：**把工作分到四个核心上，并不必然带来四倍的性能**。

他用同一个例子在自己的机器上测了**超过一千万次**，展示了每个子集计算耗时的平均值（视频里只在画面上给了表格，旁白没有读出具体数字）。

**并行到底能带来多少性能提升，超出本期范围**，作者把它留给了观众讨论。

## 9. 例子二：同一数据集上的四种不同操作（任务并行）

把问题改一下：还是那个数据集，但这次要做四件事：

```text
① 找出最小值
② 找出最大值
③ 计算所有元素的算术平均值
④ 检查数组中是否包含数字 101
```

这时候**再把数据切成子集就没意义了**，因为**每一个操作都需要访问整个数据集**才能算出结果。

但可以换个切法：**把每个操作分给一个不同的核心**。

```text
                同一份完整数据集
        ┌───────┬────────┬───────┬────────┐
        ▼       ▼        ▼       ▼
     ┌─────┐ ┌─────┐  ┌─────┐ ┌─────┐
     │核心0│ │核心1│  │核心2│ │核心3│
     │ min │ │ max │  │ avg │ │ ==101? │
     └─────┘ └─────┘  └─────┘ └─────┘
```

这就是**任务并行**：**不同的线程处理同一份数据集，但执行不同的操作**。

同样地，用四个核心不代表快四倍，但改善依然显著：

```text
单核系统                          四核系统
─────────────────────            ─────────────────────
min  ──►                          min ┐
max      ──►                      max ├─ 同时执行
avg          ──►                  avg │
find             ──►              find┘
└──── 四段时间相加 ────┘          └── 约等于最慢的那一个 ──┘
```

## 11. 核心总结

```text
多核系统上的线程
│
├── 起点：并发任务太多时，单核轮换会变慢，系统不再流畅
│   └── 三条出路：更快的 CPU / 更聪明的调度 / 更多处理器
│
├── 更多处理器的形态
│   ├── 多个 CPU 插槽
│   ├── 多核芯片（核心共享 cache）
│   └── 每个核心在操作系统眼里 = 一个独立处理器
│
├── 并发 ≠ 并行
│   ├── 并发：所有任务都能取得一些进展（单核靠交错即可）
│   ├── 并行：多个任务真正同时执行（必须有多核）
│   └── 可以有并发而无并行
│
├── 对程序员
│   ├── 只需用线程声明「这些任务可并发」，交错还是分核由 OS 决定
│   ├── 程序因此可移植，不必针对核心数编译
│   ├── n 个核心 → 任意时刻最多 n 个线程并行
│   └── 实际往往达不到 n，因为要和其他进程的线程公平分享 CPU
│
└── 并行的两种类型
    ├── 数据并行：切数据，各核做同一操作（找素数）
    └── 任务并行：切任务，各核做不同操作（min/max/avg/查找）
        └── 都不保证「核心数倍」的加速，但都是显著改善
```

> 单核上的线程解决的是「别让 CPU 闲着」，多核上的线程解决的是「让活儿真的同时干」。
> 而程序员要做的事没有变：**只管把可以并发的部分声明成线程，剩下的交给操作系统**。
