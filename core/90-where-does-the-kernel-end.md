## 1. 问题：进程树的根，是谁创建的？

### 1.1 进程是怎么被创建的

先回顾一下进程创建，两个系统的哲学不同，但结论一样。

| 系统 | 创建方式 |
| --- | --- |
| Windows | 一个进程发起系统调用，请操作系统**直接创建**一个新进程 |
| Linux / Unix-like | 进程先请操作系统**克隆自己**（`fork`），克隆出来的那个再请操作系统**替换掉自己的程序**（`exec`） |

两条路子不一样，但**根本的那件事是同一件**：

> 用户进程是由**别的用户进程**创建出来的。

本期后面统一用 Unix/Linux 的说法来讲。

### 1.2 顺着父进程往回追

既然所有用户进程都由别的用户进程创建，那么每个进程都有一个**创建它的父进程（parent process）**。

而父进程本身也是用户进程，它也有自己的父进程，如此往上。

```text
       ?
       │  创建
       ▼
    某个进程
       │
       ▼
    某个进程
       │
       ▼
     ...
       │
       ▼
   你刚打开的浏览器
```

一路回溯下去，最终一定会到达**一个**进程，它是系统里所有用户进程的共同祖先。

在 Linux 上可以直接把这棵树画出来：

```bash
pstree
```

树根确实只有一个进程。

### 1.3 关键的追问

树根这个进程，**是谁创建的？**

它不可能由另一个进程创建，否则它就不是树根了。

答案就藏在这里：

> **在这个进程之前发生的一切，都算内核。**

## 2. 先把内核定义清楚

### 2.1 分层：硬件在一端，用户在另一端

```text
          用户（想同时跑很多个应用）
                    │
        ┌───────────┴───────────┐
        │     用户应用程序       │
        └───────────┬───────────┘
                    │
        ╔═══════════╧═══════════╗
        ║   非常复杂的中间层     ║
        ║  它最贴近硬件的那部分  ║
        ║      就叫「内核」      ║
        ╚═══════════╤═══════════╝
                    │
        ┌───────────┴───────────┐
        │        硬件设备        │
        └───────────────────────┘
```

直接操作硬件既繁琐又危险。
为了防止应用因为 bug 或者烂代码把机器搞坏，中间必须垫一层。

这一层里**直接压在硬件上的那部分，就是内核**。

设计思路很简单：**用户程序每次需要用硬件，都由内核代它去操作硬件。**

### 2.2 光靠分层不够，还得靠 CPU 硬性拦住

用户进程仍然可能自己乱来，所以需要额外的强制手段。
CPU 因此被设计成有两种执行模式。

| 模式 | 能执行什么 | 谁在这里跑 | 对应空间 |
| --- | --- | --- | --- |
| 特权模式（privileged mode） | 指令集里几乎**全部**指令 | 内核 | 内核空间（kernel space） |
| 受限模式（restricted mode） | 一个**安全子集** | 所有用户应用 | 用户空间（user space） |

特权模式下能做的事：

* 配置硬件
* 通过页表（page tables）管理内存
* 控制中断（interrupts）
* 与 GPU、网卡、存储设备等 IO 外设通信

受限模式下能做的事：

* 计算、比较、循环、一般程序逻辑
* **不能**执行特权指令，**不能**直接碰硬件和关键系统资源

因为特权模式对处理器和系统资源有完全控制权，所以**跑在特权模式里的软件，决定了受限模式里的代码被允许做什么**。

### 2.3 系统调用是唯一的口子

用户应用想在屏幕上显示文字、想通过网络发消息，没有别的选择，只能**发起系统调用（system call）请内核代劳**。

```text
  用户空间                          内核空间
 ┌──────────────┐   system call   ┌──────────────┐
 │ 你的应用      │ ──────────────► │ 系统调用接口  │
 │（受限模式）   │ ◄────────────── │（特权模式）   │
 └──────────────┘     返回结果     └──────┬───────┘
                                          │
                                   ┌──────▼───────┐
                                   │ 一整叠子系统  │
                                   │ 内存 / 文件 / │
                                   │ 网络 / 调度…  │
                                   └──────┬───────┘
                                          ▼
                                        硬件
```

内核作为整体跑在特权模式，但它内部不是一个单体。
里面是一整叠子系统（subsystems），每个管一种资源或者提供一种服务。

**系统调用接口是内核离用户程序最近的那一部分。**

没有内核，用户应用根本活不下去，因为它们处在受限模式，做不了自己需要做的事。

## 3. 引导过程与 init：内核唯一亲手创建的用户进程

### 3.1 bootstrapping

开机之后，在能干任何对用户有意义的事情之前，**内核的可执行代码必须先被加载进内存**。

这个过程叫**引导（bootstrapping）**。

等所有关键组件都加载完、可以运行了，内核会亲手创建**一个且仅有一个**用户进程。

这个进程叫 **init**，它的进程 ID 是 **1**。

> init 是 Unix/Linux 系统里**唯一**一个不是由别的用户进程创建出来的用户进程。

### 3.2 内核源码里那段硬编码

内核代码深处有一段**硬编码（hard-coded）的例程**，它会去文件系统里按优先级顺序找一个叫 `init` 的可执行文件：

| 优先级 | 路径 |
| --- | --- |
| 1 | `/sbin/init` |
| 2 | `/etc/init` |
| 3 | `/bin/init` |
| 4 | `/bin/sh` |

对应的源码在 `init/main.c`：

```text
init/main.c
│
├── kernel_init()                 ← 初始化一大堆资源
│      │
│      └── 引导末期尝试执行上面那几个路径
│             │
│             └── run_init_process(path)
│                      │
│                      └── kernel_execve(path, argv, envp)
```

这里有两个细节值得注意。

**细节一：`kernel_execve` 不是那个 `execve` 系统调用。**

这段代码本身已经运行在内核态了，没有必要再发起一次系统调用。
所以用的是 `kernel_execve` 这个变体，直接调用加载新进程的那段例程。

```text
  用户进程调用 execve                内核内部调用 kernel_execve
 ┌────────────────┐                 ┌────────────────┐
 │ 受限模式        │                 │ 已经在特权模式  │
 │   │            │                 │   │            │
 │   │ 陷入内核    │                 │   │ 不需要陷入  │
 │   ▼            │                 │   ▼            │
 │ 系统调用接口    │                 │ 直接调加载例程  │
 └────────────────┘                 └────────────────┘
```

**细节二：四个路径全都找不到，内核会 panic。**

引导过程直接失败，机器起不来。

### 3.3 为什么这段代码是本期的关键

因为**内核开发者对用户空间软件的关心，到这里就为止了**。

他们硬编码了「启动第一个用户进程」这段例程，但**完全不关心这个进程之后干什么**。

更直接的证据：

> 这个 `init` 程序，在 Linux 内核源码里**根本找不到**。
> 它不属于内核。

## 4. 那么，缺了什么？

把上面那张分层图停下来想一想：**用户应用依赖的那些操作系统服务，图里有吗？**

随手就能数出一堆：

| 组件 | Linux 上的例子 | Windows 上的对应物 |
| --- | --- | --- |
| 显示服务器（display server） | Wayland、X11 | 桌面窗口管理器（DWM） |
| Shell | bash、zsh、fish | cmd.exe、PowerShell |
| 会话管理器（session manager） | systemd-logind | Winlogon / smss.exe |
| 网络管理器（network manager） | NetworkManager | 网络连接服务 |
| 包管理器（package manager） | apt、dnf、snap | winget、Microsoft Store |
| SSH 服务器（远程访问） | sshd | OpenSSH Server / 远程桌面 |
| 桌面环境（desktop environment） | GNOME、KDE、Cosmic | Windows Shell（explorer.exe） |
| 终端模拟器 | GNOME Terminal、Konsole | Windows Terminal |
| 文件管理器 | Nautilus、Dolphin | 文件资源管理器 |
| 设置面板 | GNOME Settings | 设置 / 控制面板 |
| 任务管理器 | 系统监视器 | 任务管理器 |

这些东西我们平时**全都会叫它「操作系统的一部分」**。

而它们**没有一个属于内核**。

### 4.1 所以

> 我们平时随口说的「操作系统」，有一大部分其实就是**一堆用户空间进程**。

不是所有操作系统都跑在内核空间里。

### 4.2 最好的例子：桌面环境

KDE、GNOME、Cosmic，那些 dock、任务栏、窗口平铺系统，我们跟「桌面」联系在一起的一切抽象，**全部跑在用户态**。

桌面环境不属于内核，所以它**不直接操作硬件**。
它去跟另一个用户空间进程，也就是显示服务器通信；显示服务器再用图形相关的系统调用去请内核把渲染好的缓冲区送上屏幕。

```text
 用户空间                                        内核空间
┌──────────────┐   ┌──────────────────┐        ┌──────────┐
│ 桌面环境      │──►│ 显示服务器        │──────► │ 内核      │──► GPU ──► 屏幕
│ GNOME / KDE  │   │ Wayland / X11     │ syscall│          │
│              │   │（把像素渲进缓冲区）│        │          │
└──────────────┘   └──────────────────┘        └──────────┘
   全是用户态，全是受限模式                       这里才是特权模式
```

内核那边看到的是什么？

> 内核**不知道什么是窗口**。
> 它不知道什么是按钮、什么是控件、什么是暗色模式。
> 你在屏幕上看到的一切，是因为用户空间软件把像素渲染进了缓冲区，然后请内核让 GPU 把它显示出来。
> **对内核来说，那就只是内存和硬件访问。**

### 4.3 更精确的定义

所以这一期给出的定义是：

> **操作系统是一堆软件的集合。**
> **其中一部分跑在特权模式，那部分我们叫内核；其余的跑在受限模式。**

**这就是那条线。**

```text
                    ▲  用户应用
                    │
   ─────────────────┼─────────────────  ← 这条线
                    │
   受限模式（用户空间）│ 特权模式（内核空间）
   桌面环境 / 显示服务器 / shell /      内存管理 / 文件系统 /
   网络管理器 / 包管理器 / init …       调度器 / 驱动 / 中断 …
```

## 5. 这些用户进程是谁生出来的？init

有个细微但重要的点：**这些用户进程不会凭空出现，它们必须由另一个进程创建。**

init 就是在这里派上用场的。

引导过程中，内核初始化完关键子系统、准备切换到用户空间时，就执行前面那段硬编码例程，找到并启动 init。

为什么只启动一个就够？

> 因为**那一个用户空间进程，足以孵化出前面看到的整棵进程树**。

从那一刻起，操作系统的其余部分就开始涌现出来。
它们不是直接从内核里长出来的，而是**从用户空间代码里长出来的**，由这些代码搭建起应用所依赖的整套服务基础设施。

```text
内核（特权模式）
   │ 硬编码：找 /sbin/init 并执行
   ▼
init  PID 1 ─────────────────── 用户空间从这里开始
   ├── 网络管理器
   ├── 任务调度器
   ├── 日志相关服务
   ├── 显示服务器（Wayland）
   ├── 桌面环境的一大堆进程（Ubuntu 上就是 GNOME）
   ├── snap（那个人人喊打的包管理器）
   └── …
```

## 6. 于是「没有默认版本的 Linux」

### 6.1 两台机器的进程树

| 机器 | 树根之下能看到什么 |
| --- | --- |
| Ubuntu | GNOME 的一大堆进程、Wayland、snap、网络管理器、日志服务…… |
| Fedora（KDE 版） | **完全看不到 GNOME**，因为装的是 KDE 桌面环境 |

同一份内核，长出来的东西完全不同。

> 这个根进程负责孵化的那些服务和应用，**定义了你那个发行版的行为和个性**。

### 6.2 发行版是怎么来的

这也解释了为什么**不存在「默认版本的 Linux」**：

* Linux 开发者只提供**一个内核**。
* 讽刺的是，**这个内核自己完全没用**，没有跑在它上面的用户空间程序，它提供不了任何功能。

所有发行版共享同一个内核，区别在于**建在这个内核之上的服务基础设施**，而这取决于发行版作者的设计哲学。

### 6.3 连根进程的名字都可能不一样

因为 init 有多种实现：

| 类型 | 实现 |
| --- | --- |
| 传统 | SysV init、OpenRC、runit |
| 现代、更复杂 | systemd |

内核并不关心这个进程怎么工作，所以不同项目对「init 该有什么职责、不该有什么职责」发展出了完全不同的哲学。

### 6.4 那个符号链接的小把戏

传统做法很直白：把你喜欢的 init 实现编译成名字叫 `init` 的可执行文件，放进系统二进制目录（或者内核会找的其他目录）。

但出于历史和现实原因，现代系统往往用**别的名字**编译、放在**别的地方**，然后在内核期待的那个目录里放一个叫 `init` 的**符号链接（symbolic link）**，类似快捷方式。

自己验证一下：

```bash
ls -l /sbin/init
# lrwxrwxrwx 1 root root 20 ... /sbin/init -> /lib/systemd/systemd
```

```text
内核以为它在启动：           实际上启动的是：
┌──────────────┐            ┌──────────────────────┐
│ /sbin/init   │ ── 符号链接 ─►│ /lib/systemd/systemd │
└──────────────┘            └──────────────────────┘
```

这个不起眼的间接层，恰好把整件事说透了：

> **内核只关心「启动第一个用户空间进程」这件事。**
> **那个进程究竟是什么、接下来要干什么，完全不在内核的关心范围之内。**

## 7. 内核确实给了 init 两项特殊待遇

虽然不关心它干什么，内核还是给了这个进程两个特殊性质。

### 7.1 特权：永远拿到 PID 1

正常情况下，一个程序会拿到什么进程 ID 是没有保证的。

但 init 一定是 1，理由很朴素：**它是第一个被创建的进程。**

好处是在任务管理器之类的工具里非常好认。

### 7.2 责任：绝不能退出

这一条与其说是特权，不如说是义务。

> **init 永远不能终止。**

原因是：**内核不喜欢孤儿进程（orphaned processes）。**

设想一个程序启动了一个 Firefox 进程，父子关系很清楚。
但如果父进程终止了，而子进程还在跑呢？

> **一个进程不能有一个已经不存在的父进程。**

所以当某个进程或者一组进程变成孤儿时，Linux 内核会把它们的父进程**重新指派（reassign）给 init**。

```text
   崩溃前                          崩溃后
 ┌────────┐                     ┌────────┐
 │ 父进程  │ ✗ 终止              │ init   │  PID 1
 └───┬────┘                     └───┬────┘
     │                              │  ← 内核把孤儿收养过来
 ┌───▼────┐                     ┌───▼────┐
 │Firefox │ 还在跑              │Firefox │
 └────────┘                     └────────┘
```

换句话说：**init 必须一直活着，因为内核需要它来收养孤儿进程。**

### 7.3 内核有多认真？

给它发信号 9（`SIGKILL`）试试：

```bash
sudo kill -9 1     # 什么也不会发生
```

进程不会终止。

> 内核太在意这个进程不能死，以至于它**干脆拒绝投递这个信号**。

### 7.4 顺带的两个结果

**一：init 常被写成恢复机制。**
因为它永不退出，很多 init 实现顺便承担了看门狗的职责。
某个关键服务崩了（比如桌面环境），init 可能会自动把它重启起来。

**二：init 一旦没了，内核就 panic。**
无论是 init 自己因为 bug 崩溃，还是它**正常无错误地退出**，内核都会 panic。

```text
init 退出（哪怕 exit code 是 0）
        │
        ▼
   内核 panic
        │
        └── 尽管内核**自己内部什么都没坏**
```

但无论如何都要记住一件事：

> **init 有一些特殊待遇，但它不跑在内核空间里。**

## 8. 第二条线：操作系统和用户应用之间

这一段是作者剪片时临时加的。

第一条线很好画：

> **凡是跑在特权模式的操作系统部分，就是内核。**

那剩下那些呢？
既然操作系统的这些组件都只是普通的用户空间进程，那**操作系统**和**用户应用**之间的线又该画在哪儿？

### 8.1 问题从预装软件开始

几乎每个现代操作系统都预装一个浏览器，Linux 世界里通常是 Firefox。

浏览器算操作系统的一部分吗？

大多数人会说不算，因为它对系统运转不是必需的。

**可同样的论证也能套在别的东西上：**

* 文件管理器
* 文本编辑器
* 系统监视器
* 桌面环境自带的任务管理器
* 甚至桌面环境本身

毕竟这些程序做的事，**技术上你都可以通过终端和 shell 完成**。

那它们是不是就只是用户应用、不算操作系统了？

### 8.2 作者的立场与那个反例

作者本人不这么认为：

> 桌面环境和它自带的那些应用，**恰恰是让一个操作系统「有自己的样子」的东西**。

这当然是主观的。但看一个反例：**90 年代的 Mac OS 9**。

它的设计理念是**用户永远不需要打字输命令**。

| Mac OS 9 | 有没有 |
| --- | --- |
| shell | 没有 |
| 终端模拟器 | 没有 |

在那种环境里，文件管理器、任务管理器、设置面板是**绝对必需**的，因为那是**与系统交互的唯一途径**，哪怕它们只是用户空间进程。

### 8.3 候选定义，以及它的漏洞

作者能想到的最接近定义的说法是：

> **凡是由 init 自动启动的程序**，因为理论上它们才是必需的服务。

但这个定义也有问题：

有些必需的工具**不是由 init 启动的**，因为在用户主动调用之前根本不需要它们。

* 终端（terminal）
* **coreutils**：几乎每个 Linux 发行版都带的那一套核心工具集，提供了你在 shell 里用的那些又小又必不可少的命令

这些大多不由 init 启动。
我们都同意它们是用户进程，可又很难不把它们当成操作系统的一部分。

> 想象一下一个没有这些命令的终端。
> Linux 就不像 Linux 了。

### 8.4 结论

作者明说了：**第二条线，他没有确定的答案。**

```text
硬件
 │
 ├─ 内核（特权模式）
 │
═══════════════════  ← 第一条线：清晰、由 CPU 硬件强制
 │
 ├─ init / 显示服务器 / 网络管理器 / shell / 桌面环境 / coreutils …
 │
 ┅┅┅┅┅┅┅┅┅┅┅┅┅┅┅┅┅  ← 第二条线：模糊、主观、没有标准答案
 │
 └─ Firefox / 你自己写的程序 …
```

## 9. 核心总结

```text
内核到哪里为止
│
├── 定义（第一条线，清晰）
│   └── 操作系统 = 一堆软件
│       ├── 跑在特权模式的那部分 = 内核
│       └── 其余跑在受限模式 = 用户空间
│           └── 这条线由 CPU 的两种执行模式硬性保证
│
├── 边界在哪儿被交接
│   ├── 引导：内核代码被载入内存
│   ├── init/main.c 的 kernel_init 硬编码去找 init
│   │   ├── /sbin/init → /etc/init → /bin/init → /bin/sh
│   │   ├── 用 kernel_execve（不是系统调用，本来就在内核态）
│   │   └── 一个都找不到 → panic
│   └── 交接完成，内核不再关心
│       └── init 程序根本不在内核源码里
│
├── 用户空间才是「操作系统的观感」
│   ├── 显示服务器 / 桌面环境 / shell / 网络管理器 / 包管理器 / SSH
│   ├── 内核不知道什么是窗口、按钮、暗色模式
│   │   └── 对它来说只是内存和硬件访问
│   └── 所以没有「默认版本的 Linux」
│       ├── 所有发行版共享同一个内核
│       ├── 差别全在建在它之上的服务基础设施
│       └── 连 init 都有多种实现：SysV init / OpenRC / runit / systemd
│           └── /sbin/init 往往只是指向 systemd 的符号链接
│
└── 内核给 init 的两条特殊规则
    ├── 永远是 PID 1
    └── 永远不能退出
        ├── 因为内核需要它收养孤儿进程
        ├── SIGKILL 干脆不投递给它
        └── 它一旦退出（哪怕 exit 0）→ 内核 panic
```

> 「Linux 不是操作系统，它是内核」这句话的真正含义是：
> Linux 开发者只交付了那一层跑在特权模式、并且硬编码了一件事的代码 - 开机末尾去找一个叫 `init` 的文件并运行它。
> 那一刻之后的一切，桌面、终端、网络、包管理、你按下的每一个按钮，都是用户态进程一层层自己长出来的。
> 内核画得出自己的边界，是因为 CPU 帮它画；而「操作系统」和「应用」之间那条线，至今没人画得干净。
