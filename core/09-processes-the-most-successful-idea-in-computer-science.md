## 0. 这一期在讲什么

上一期把「程序不是进程」这件事讲清楚了，但只停在概念层面。
这一期开始进入**技术细节**。

作者在开头说明了频道的方向：接下来会往操作系统更底层的话题走，包括 CPU 调度（CPU scheduling）、线程（threads）、分页（paging）、虚拟内存（virtual memory）。
问题是这些话题全都深度依赖同一个还没讲透的概念，也就是**进程（process）**。
所以这一期是后面所有内容的地基。

本期的主线是一条推理链：

```text
进程要轮流用 CPU
        │
        ▼
天真地切换会出两个致命问题（安全 + 正确性）
        │
        ▼
解法是上下文切换（context switch）
        │
        ▼
既然要切「上下文」，那进程本质上就是一个上下文
        │
        ▼
上下文没法直接塞进队列，所以需要 PCB
```

## 1. 从程序到进程：地址空间

非正式定义还是那句：**进程就是执行中的程序（a program in execution）**。
这句话说明这两个概念不是一回事。

程序是**被动实体（passive entity）**，比如硬盘上一个可执行文件，你双击它才会开始运行。
运行时内部发生的事情是：可执行文件被加载进内存。
到这一刻，程序就变成了进程。

但光有可执行文件的副本不够。
进程执行过程中还需要额外的内存来存放**用户输入**和**临时结果**。
这部分内存由操作系统负责分配。

分配给一个进程的这整块内存有一个专门的名字：**地址空间（address space）**。

```text
硬盘                          内存
┌──────────────┐             ┌───────────────────────┐
│ program.exe  │ ─── 加载 ──►│ 可执行文件的副本       │
│ （被动实体）  │             │ （指令 + 静态数据）    │
└──────────────┘             ├───────────────────────┤
                             │ 用户输入               │
                             │ 临时结果               │ ← 操作系统额外分配
                             └───────────────────────┘
                             └──── 地址空间 ─────────┘
```

这个词后面还会回来，先记住。

但地址空间**不等于**进程。
进程比它的地址空间要多得多，这一期剩下的篇幅基本都在补齐「多出来的那部分」。

## 2. 轮流用 CPU：先看 CPU 里有什么

现代操作系统使用并发（concurrency），让多个进程**交替**访问计算机资源。

内部实现方式是把进程放进一个**队列（queue）**。

```text
        正在用 CPU        等待队列
        ┌──────┐      ┌──────┐  ┌──────┐  ┌──────┐
CPU ◄───┤  P1  │      │  P2  │  │  P3  │  │  P4  │  ...
        └──────┘      └──────┘  └──────┘  └──────┘
```

关键点：**任意时刻只有一个进程能用 CPU，其余全在等。**

那「用 CPU」具体是在用什么？
回忆前几期讲过的 CPU 内部组件：

| 组件 | 英文 | 作用 |
| --- | --- | --- |
| 通用寄存器 | general-purpose registers | 存放正在运算的数据 |
| 指令寄存器 | instruction register (IR) | 存放当前正在执行的指令 |
| 地址寄存器 / 程序计数器 | address register / program counter (PC) | 指向下一条要取的指令 |
| 栈指针 | stack pointer (SP) | 指向栈顶 |
| 标志位 | flags | 上一次运算的结果状态 |

```text
┌───────────────────── CPU ─────────────────────┐
│  通用寄存器   R0  R1  R2  ...                  │
│  指令寄存器   IR                               │
│  程序计数器   PC   ← 决定下一条指令从哪取        │
│  栈指针       SP                               │
│  标志位       ZF  CF  ...                      │
└───────────────────────────────────────────────┘
```

一个进程拿到 CPU 后，就是靠这些组件搬运和操作数据。
这就是「运行一个程序」的本质。

## 3. 天真的切换：两个致命问题

问题来了：在多个进程之间交替使用 CPU，**没有听起来那么简单**。

如果只是简单地切换，新拿到 CPU 的进程会发现自己身处**上一个进程留下的 CPU 状态**里。

```text
P1 跑了两条指令           直接改 PC 跳走            P2 拿到 CPU
┌──────────────┐                             ┌──────────────┐
│  R0 = 12     │  ─────────────────────────► │  R0 = 12     │  ← P1 的数据还在
│  R1 = 20     │                             │  R1 = 20     │
└──────────────┘                             └──────────────┘
                                                    │
                        ┌───────────────────────────┴──────────────────────┐
                        ▼                                                  ▼
              问题一：安全性                                    问题二：执行正确性
              P2 能读到 P1 的残留数据                   P2 一写寄存器就毁掉 P1 的现场
```

### 问题一：安全性（security）

当前进程可以直接读到上一个进程的敏感信息。

作者举的例子：假设上一个进程正在**哈希一个密码**，密码的一部分可能还留在寄存器里。
没有任何机制能阻止当前进程把这段信息读走用于恶意目的。

### 问题二：执行正确性（correctness of execution）

现在假设所有进程都是诚实的，绝不会去偷看上一个进程的数据。
问题解决了吗？
**没有。**

因为即使当前进程完全无意使用那些信息，它**仍然需要操作寄存器来完成自己的任务**。
它一写寄存器，就改掉了上一个进程的 CPU 状态。

于是等上一个进程重新拿到 CPU 时，它被中断那一刻的 CPU 状态**已经丢了**。

诚实与否根本不重要，这是个结构性问题。

## 4. 完整推演：两个进程如何互相毁掉对方的结果

作者用了一个具体例子。
两个程序编译成机器码后运行，为了教学方便用汇编展示。

用视频里的数字重建这两段代码：

```text
进程 A                              进程 B
────────────────────────           ────────────────────────
LOAD  R0, 12                       1013:  LOAD  R0, 100
LOAD  R1, 20                              LOAD  R1, 35
ADD   R0, R1     ; R0 = R0+R1             ADD   R0, R1
────────────────────────           ────────────────────────
应得结果：12 + 20 = 32              应得结果：100 + 35 = 135
```

前提设定：

* 两个程序**同时启动**，都被加载进内存。
* 操作系统的并发模型允许每个进程**执行两条指令**后就切换 CPU。
* 进程 B 的第一条指令在内存地址 **1013**。

### 逐步推演（没有保存状态的版本）

| 步骤 | 执行者 | 指令 | R0 | R1 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 0 | - | - | ? | ? | 操作系统把 PC 指向 A 的代码 |
| 1 | A | `LOAD R0, 12` | **12** | ? | 第一条 |
| 2 | A | `LOAD R1, 20` | 12 | **20** | 第二条，用满配额 |
| 3 | - | 切换到 B | 12 | 20 | PC 指向 1013，**寄存器原封不动** |
| 4 | B | `LOAD R0, 100` | **100** | 20 | B 不作恶，但它必须写寄存器 |
| 5 | B | `LOAD R1, 35` | 100 | **35** | 第二条，用满配额 |
| 6 | - | 切回 A | 100 | 35 | **第一个错误在这里** |
| 7 | A | `ADD R0, R1` | **135** | 35 | 本该算 12+20，实际算了 100+35 |
| 8 | - | 切回 B | 135 | 35 | A 的加法又覆盖了 R0 |
| 9 | B | `ADD R0, R1` | **170** | 35 | 本该算 100+35，实际算了 135+35 |

### 第一个错误：PC 根本没存

第 6 步操作系统想让 A「从中断处继续」，就必须把 PC 设回正确的地址。
但这个地址**在切走之前压根没被保存到任何地方**。
所以严格来说，A 已经无法恢复了。

先假装操作系统把 PC 存下来了并能正确恢复，继续往下看数据错在哪。

### 结果对照

```text
              应得        实得
进程 A        32    ──►   135      （算成了 100 + 35）
进程 B        135   ──►   170      （算成了 135 + 35）
```

两个进程的结果**双双被毁**。

CPU 只是老老实实照指令执行，它没有任何办法知道发生了什么，只会拿着错误的数据一路错下去。

## 5. 真正的噩梦是不确定性

最糟糕的一点不是「算错了」，而是**这些错误值不是确定性的（not deterministic）**。

```text
同样两段代码
      │
      ├── 加进第三个进程         ──► 完全不同的错误结果
      ├── 第二个程序晚启动几毫秒  ──► 完全不同的错误结果
      └── 调度顺序稍有变化        ──► 完全不同的错误结果
```

再考虑现实规模：

* 现代计算机同时处理**几百个**进程。
* 实践中**极难预测**进程的确切执行顺序（这属于 CPU 调度那一期的内容）。

一个每次跑都错得不一样、还没法复现的 bug，基本等于无法调试。

## 6. 解法：上下文切换（context switch）

操作系统怎么同时保证安全性和正确性？
**解法需要额外的步骤。**

还是同样的例子：两个进程同时启动，A 先跑，`R0 = 12`，`R1 = 20`。
接下来 CPU 要交给 B。

但这次操作系统**不是**直接覆盖地址寄存器往 B 的代码跳。
它先运行一段**特殊的内核例程**，把当前 CPU 状态**拍一张快照**。

```text
                A 运行中
                    │
                    ▼
      ┌──────────────────────────┐
      │ 1. 捕获 A 的 CPU 状态     │
      │    寄存器 / 标志位 / PC   │ ──── 复制进内存 ────► A 的存档
      └──────────────────────────┘
                    │
                    ▼
      ┌──────────────────────────┐
      │ 2. 恢复 B 的 CPU 状态     │ ◄─── 从内存读出 ───── B 的存档
      │    写回 CPU 的对应寄存器  │
      └──────────────────────────┘
                    │
                    ▼
                B 运行中
```

要点：

* 拷贝的内容是**寄存器、标志位、程序计数器**。
* 操作系统为**计算机上运行的每一个进程**都保留一份 CPU 状态的副本。
* 顺序是**先存旧的，再取新的**，两步不能颠倒也不能省。

B 是第一次运行，所以它的存档里所有寄存器都是 0，只有 PC 例外，PC 指向它下一条该执行的指令，此刻就是地址 **1013**。

### 加上保存/恢复之后的推演

| 步骤 | 执行者 | 指令 | R0 | R1 | 存档动作 |
| --- | --- | --- | --- | --- | --- |
| 1 | A | `LOAD R0, 12` | 12 | 0 | |
| 2 | A | `LOAD R1, 20` | 12 | 20 | |
| 3 | - | 切换 | - | - | **存 A**(12, 20, PC) → **取 B**(0, 0, PC=1013) |
| 4 | B | `LOAD R0, 100` | 100 | 0 | |
| 5 | B | `LOAD R1, 35` | 100 | 35 | |
| 6 | - | 切换 | - | - | **存 B**(100, 35, PC) → **取 A**(12, 20, PC) |
| 7 | A | `ADD R0, R1` | **32** | 20 | 正确 |
| 8 | - | 切换 | - | - | **存 A** → **取 B**(100, 35, PC) |
| 9 | B | `ADD R0, R1` | **135** | 35 | 正确 |

两个问题同时被解决：

```text
安全性    ──► 进程再也读不到上一个进程正在用的信息
                （切进来时寄存器已经被换成自己的存档）

正确性    ──► 自己的状态不会被别的进程改动
                （每次重获 CPU，寄存器和被中断那一刻一模一样）
```

**这个「捕获一个进程的 CPU 状态、恢复另一个进程的状态以让它继续执行」的动作，就叫上下文切换（context switch）。**

操作系统就是靠它，在多个进程共享 CPU 的同时保证安全性和正确性。

## 7. 为什么叫「上下文」：进程就是一个上下文

到这里我们知道进程有：地址空间、程序计数器、寄存器。
后三者可以非正式地统称为进程的 **CPU 状态**。

那进程还有什么？

它还可能有**打开的文件列表**，以及**分配给它的 IO 设备**。

```text
┌──────────────── 一个进程 ─────────────────┐
│                                          │
│  地址空间                                 │
│    text / data / heap / stack            │
│                                          │
│  CPU 状态                                 │
│    PC + 通用寄存器 + 标志位 + ...          │
│                                          │
│  打开的文件列表                            │
│                                          │
│  分配到的 IO 设备                          │
│                                          │
└──────────────────────────────────────────┘
        与其他进程彼此隔离（isolated）
```

作者的结论：进程**不是一个单一实体**，而是这一整套彼此隔离的环境。

> 用一个词描述进程，最好的词是：**上下文（a context）**。

这也正是那段内核例程叫 **context switch** 的原因。
切换进程时，我们替换的是**整个系统运行所处的上下文**。

### 这解释了一个高层现象

为什么多个进程可以有**完全相同的可执行指令**，运行结果却不同？

```text
       相同的指令序列
              │
       ┌──────┴──────┐
       ▼             ▼
   上下文 A       上下文 B
   （不同的内存、  （不同的内存、
     寄存器、文件）  寄存器、文件）
       │             │
       ▼             ▼
    结果 A         结果 B
```

**重要的不只是指令本身，还有这些指令被执行时所处的上下文。**

作者打了个日常的比方：你问别人一个问题，对方反问「在什么语境下（in what context）？」
因为同一个问题在不同情境下会有不同答案。

## 8. 怎么把上下文放进队列：PCB

新问题来了。

进程是这么一整套东西，从寄存器这种底层组件到打开文件列表这种高层信息。
**它不是一个能直接当作数据结构元素的对象**，那怎么把它放进队列？

答案是 **PCB**。
不是印刷电路板（printed circuit board），这里是 **Process Control Block（进程控制块）**。

PCB 是操作系统用来追踪每一个进程的一个专门结构。

```text
┌────────── Process Control Block ──────────┐
│  process ID          进程唯一标识          │
│  state               进程状态              │
├───────────────────────────────────────────┤
│  program counter                          │
│  general-purpose registers                │  ← 所谓「CPU 状态」
│  instruction register                     │    上下文切换存/取的就是这块
│  flags                                    │
│  (stack pointer / index registers /       │
│   accumulators / 依硬件而定的其他组件)      │
├───────────────────────────────────────────┤
│  memory management information            │  ← 地址空间边界
├───────────────────────────────────────────┤
│  open files / IO devices                  │  ← 分配到的其他资源
└───────────────────────────────────────────┘
```

逐项说明：

| 字段 | 为什么需要 |
| --- | --- |
| process ID | 每个进程都是唯一的，需要一个标识符 |
| state | 进程有若干种可能的状态 |
| CPU 状态 | 上下文切换要保存的数据，**存的就是这里** |
| 内存管理信息 | 见下一节 |
| 打开文件 / IO 设备 | 进程持有的其他资源 |

关于 `state` 的几种具体取值，作者说「稍后详细讨论」，但本期实际上没有展开，属于后续内容。

## 9. 内存管理信息为什么必须在 PCB 里

还记得每个进程都有自己的地址空间吗？

并发运行多个程序引入了一个**新的安全问题**：如果不加额外防护，任何进程都可能**读写另一个进程的地址空间**。

```text
             内存
   ┌────────────────────────┐
   │  进程 A 的地址空间       │ ◄──┐
   ├────────────────────────┤    │  没有边界检查的话
   │  进程 B 的地址空间       │ ───┘  B 可以随便读写 A
   ├────────────────────────┤
   │  空闲区域               │
   └────────────────────────┘
```

操作系统必须知道这些**边界**，才能拦截恶意的内存访问。

另外还有一个纯功能性的理由：新进程被创建时，操作系统需要知道**所有现有进程的地址空间**，才能为新进程正确划出一块可用的内存区域。

```text
创建新进程
     │
     ▼
 查看所有已有进程的地址空间边界
     │
     ▼
 找到一块没被占用的区域 ──► 分配给新进程
```

所以 PCB 必须包含内存管理信息，**至少要有每个进程地址空间的内存上下界**。

## 10. 真实实现：Linux 的 task_struct

上面画的结构只是一个示例。
想看真实实现，可以去读 Linux 内核源码里的对应结构体。

作者注意到两件有意思的事：

### 1. 它不叫 process，叫 task

Linux 里这个结构体的名字是 **task**，不是 process。

作者先给了一个猜测（Linux 源自 Unix，那个年代说计算机运行的是 task），并明确表示自己不是内核专家、可能说错，欢迎评论区指正。

随后给出了真正的原因：

> Linux 用 "task" 表示**执行的基本单位**，用**同一个数据结构**同时涵盖线程（threads）和进程（processes），在调度层面把两者视为同一种东西。

```text
        Linux 的 task
              │
      ┌───────┴───────┐
      ▼               ▼
   process          thread
      └───── 调度器眼中是同一类东西 ─────┘
```

### 2. PCB 里有家族关系

真实的 PCB 包含：

* 一个指向**父进程 PCB 的指针**
* 一份该进程**创建的所有子进程的列表**

```text
        ┌───────────┐
        │ 父进程 PCB │
        └─────┬─────┘
              │ parent 指针
        ┌─────▼─────┐
        │  本进程 PCB│
        └─────┬─────┘
              │ children 列表
      ┌───────┼───────┐
      ▼       ▼       ▼
   ┌─────┐ ┌─────┐ ┌─────┐
   │子 1 │ │子 2 │ │子 3 │
   └─────┘ └─────┘ └─────┘
```

所以可以把这两项也加进前面的示例结构里。

### 最重要的一点

作者反复强调：

> **PCB 不是进程本身，而是进程的一个「表示（representation）」。**

它是一个仓库，存放启动或恢复一个进程所需要的全部数据，外加一些记账信息（accounting information）。

而**真正被放进队列的，就是这个表示**。

```text
进程（一整个上下文）      无法直接当队列元素
        │
        ▼
   用 PCB 来表示它
        │
        ▼
   ┌──────┐   ┌──────┐   ┌──────┐
   │ PCB1 │──►│ PCB2 │──►│ PCB3 │──► ...
   └──────┘   └──────┘   └──────┘
              就绪队列
```

第 2 节里那个「把进程放进队列」的说法，到这里才算落实。

## 11. 单核与多核

最后一点说明：本期讲的所有内容对**单处理器系统**和**多核系统**都成立。

唯一的区别是：

```text
单核系统                          多核系统
──────────────────               ──────────────────────
core0: [ 上下文 A ]               core0: [ 上下文 A ]
                                 core1: [ 上下文 B ]
                                 core2: [ 上下文 C ]

同一时刻只有一个上下文             同一时刻可以有多个上下文
                                 因为每个核心有自己的执行流水线
```

多核系统能**同时**操作多个上下文，原因是每个核心都有自己的执行流水线（execution pipeline）。
但每个核心上发生的事情，和单核完全一样。

## 13. 核心总结

```text
进程 = 一个上下文（a context）
│
├── 为什么需要这个概念
│   ├── 多个进程要交替使用 CPU
│   ├── 任意时刻只有一个进程在 CPU 上，其余排队
│   └── 天真地切换会同时毁掉安全性和正确性
│
├── 天真切换的两个问题
│   ├── 安全性：新进程能读到旧进程留在寄存器里的数据
│   │   └── 例：上一个进程正在哈希密码
│   └── 正确性：新进程即使诚实，也必须写寄存器，从而毁掉旧现场
│       ├── A 应得 32，实得 135（算成了 100 + 35）
│       ├── B 应得 135，实得 170（算成了 135 + 35）
│       └── 更糟：错误值不确定，多一个进程或晚几毫秒就全变
│
├── 解法：上下文切换（context switch）
│   ├── 切走前：把寄存器 / 标志位 / PC 快照进内存
│   ├── 切入前：把目标进程的存档写回 CPU
│   ├── 顺序不可颠倒：先存旧的，再取新的
│   └── 操作系统为每一个进程都保留一份 CPU 状态副本
│
├── 进程包含什么
│   ├── 地址空间（text / data / heap / stack）
│   ├── CPU 状态（PC + 寄存器 + 标志位 + ...）
│   ├── 打开的文件列表
│   ├── 分配到的 IO 设备
│   └── 与其他进程隔离
│       └── 所以相同指令 + 不同上下文 = 不同结果
│
└── PCB（Process Control Block）
    ├── 定位：进程的「表示」，不是进程本身
    ├── 内容
    │   ├── process ID
    │   ├── state
    │   ├── CPU 状态（上下文切换存取的就是这块）
    │   ├── 内存管理信息（地址空间边界）
    │   │   ├── 用途一：拦截跨进程的非法内存访问
    │   │   └── 用途二：为新进程找空闲内存区域
    │   ├── 打开文件 / IO 设备
    │   └── 父进程指针 + 子进程列表
    ├── 真实实现：Linux 的 task_struct
    │   └── 叫 task 因为它统一表示进程和线程，调度层面一视同仁
    └── 真正被放进队列的，是 PCB
```

> 一段指令自己什么都决定不了。
> 决定结果的是它运行时身处的那个上下文：寄存器里是什么、地址空间在哪、打开了哪些文件。
> 操作系统能让几百个进程共用一颗 CPU 而互不干扰，靠的不是让它们变得诚实，而是在每次交接时把整个上下文原样封存、原样取回。
> 进程这个概念之所以成功，是因为它把「隔离」变成了默认值。
