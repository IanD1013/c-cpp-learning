# 为什么单核处理器也需要线程

> 视频来源：Core Dumped -《Why Are Threads Needed On Single Core Processors》
> https://www.youtube.com/watch?v=M9HHWFp84f0

## 0. 这一期在讲什么

线程（thread）听上去很吓人，但作者的说法是：只要掌握四个概念，线程其实简单得出奇。

这一期的主线是：**在只有一个核心的机器上，线程解决的到底是什么问题**。
注意这个前提，本期讲的所有内容**在单核处理器上同样成立**，跟「多核并行」没有关系，并行是下一期的话题。

需要的前置背景：

| 前置概念 | 在本期里的作用 |
| --- | --- |
| 并发（concurrency） | 单 CPU 通过快速轮换制造「同时运行」的错觉 |
| CPU 调度（CPU scheduling） | 决定 CPU 下一刻分配给谁 |
| 进程（process） | 目前为止我们认为的「最小执行单元」 |
| 程序计数器（program counter） | 记录进程被打断时执行到哪条指令 |

---

## 1. 前置：并发有两个目的，不止一个

大家熟悉的那个目的是**多任务**。

一个 CPU、多个进程时，操作系统让它们轮流占用 CPU，轮换得极快，用户就产生了「所有进程同时在跑」的错觉。

```text
物理时间轴（单个 CPU）
├─ P1 ─┤├─ P2 ─┤├─ P3 ─┤├─ P1 ─┤├─ P2 ─┤├─ P3 ─┤ ...
      切换      切换     切换     切换     切换

用户感知到的：P1、P2、P3 同时在跑
```

但还有一个不那么显眼的目的：**把计算资源用满**。

关键在于，进程虽然被定义为「执行中的程序」，但**它并不总是在用 CPU**，哪怕 CPU 已经分配给它了。
最典型的情况是进程在等一个 IO 资源。
这时把 CPU 给它是浪费，因为在 IO 资源就绪之前，它一条指令都执行不了。

```text
只按「公平轮换」分配 CPU：
P1 ┤███ 计算 ███│░░░░░ 等磁盘 IO ░░░░░│███ 计算 ███
                └── CPU 被占着，却什么都没干（浪费）

按「谁能跑就给谁」分配：
P1 ┤███ 计算 ███│░░░░░ 等磁盘 IO ░░░░░│███ 计算 ███
P2 ┤            │███████ 填进空隙 ███│
```

所以并发的第二个理由是：**把某个进程用不了 CPU 的那些小空隙，交给另一个能用的进程**。

## 2. 问题：传统进程模型下，进程内部无法并发

到目前为止这个系列一直把进程当作**最基本的执行单元**，也就是说，在调度的意义上没有比进程更小的东西了。

这句话的直接后果是：**同一个程序里的两个函数，没法异步执行**。

原因回到进程那一期：每个进程只有**一个程序计数器**，它记录进程被打断时停在哪条指令。

```text
进程 P（只有一个 PC）
┌──────────────────────────────┐
│ PC ──► 0x4051  函数 A 的某行  │
├──────────────────────────────┤
│ 函数 A ... 函数 B ...         │
└──────────────────────────────┘

想在 A 和 B 之间来回切？
切走 A 时 PC 存 A 的位置，切到 B 后 PC 变成 B 的位置，
那 A 停在哪儿就没人记得了。
→ 一个 PC 只能记住一个「断点」
→ B 必须等 A 执行完
```

这就是限制的根源：**单个程序计数器让进程控制块（process control block，PCB）没法同时追踪一个以上的任务**。

---

## 3. 那为什么不用「多进程 + IPC」

一个很自然的反问：如果想让两段代码并发执行并互相配合，把它们放进不同进程，再用进程间通信（IPC）协调，不就行了？

可以，但 IPC 并不总是直观的。
有些代码彼此关联太紧密、共同服务于同一个目标，把它们拆到不同进程里**就是感觉不对**。

作者给的例子是一个服务器：

```text
监听端口 3000，职责是返回每个客户端对应的头像图片

客户端请求 ──► ① accept（接受请求）
                    │
                    ▼
              ② process（在磁盘上查找并读入图片）  ← 昂贵的 IO
                    │
                    ▼
              ③ respond（把内存中的图片发回去）
```

因为图片以文件形式存在磁盘上，第 ② 步需要一次代价高昂的 IO 操作。
结果就是：**处理一个请求的时间，远长于接受或响应它的时间**。

这三步是顺序执行的，总共也就几毫秒，单个客户端完全没问题。
但客户端一多，问题就来了。

```text
5 个请求几乎同时到达（顺序处理）

C1 │A│███████ process ███████│R│
C2 │                          │A│███████ process ███████│R│
C3 │                                                     │A│████ ...
C4 │                                                            等
C5 │                                                            等
   └── 后面的请求要等很久才被受理 ──►
```

5 个请求还好，**想象一千个请求**，真正的问题才暴露出来：时间轴上那些灰色的空隙。

```text
CPU 时间轴
│███ accept ███│░░░░░ 等磁盘把图片读上来 ░░░░░│███ respond ███│
                └──────── CPU 完全闲着 ────────┘
                这段时间本可以用来接受并开始处理别的客户端请求
```

当两个任务本来互相独立，其中一个却因为另一个在跑而无法执行时，这种现象叫**阻塞效应（blocking effect）**。

---

## 4. 旧方案：Listener 进程 + 为每个客户端 fork 一个进程

长期以来的解法是这样的：

```text
        ┌──────────────────┐
        │ Listener 进程     │  只负责监听和 accept
        └────────┬─────────┘
   每来一个客户端 │ 创建一个全新进程
        ┌────────┼─────────┬─────────┐
        ▼        ▼         ▼         ▼
     ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
     │ 子P1 │ │ 子P2 │ │ 子P3 │ │ 子P4 │  各自伺候一个客户端
     └──────┘ └──────┘ └──────┘ └──────┘
```

这样 Listener 就和「正在服务上一个客户端」的进程并发运行，新请求不必等上一个请求彻底处理完。
换句话说，它利用并发把 CPU 尽可能用满了。

聪明，但不完美，有三个代价：

| 代价 | 说明 |
| --- | --- |
| 内存 | 每个进程都是一个自带地址空间的自包含上下文。几百个客户端还行，上千个就非常浪费 |
| 创建开销 | 创建进程不是廉价操作，本身要吃处理时间。目标是填满 CPU 空隙，结果一部分空隙被「创建进程」本身吃掉了 |
| 全局状态 | 服务器若要维护某种全局状态，所有子进程都得同步，这又得靠 IPC，实现复杂度上升 |

进程是计算机科学里最重要的概念之一，但它不完美。

---

## 5. 解法：把程序计数器从进程身上摘下来

进程这个概念太有用，不能丢掉，但可以**稍微改一改**，让单个进程内部的可执行代码也能并发。

回忆一下进程大致由什么组成：

```text
进程 = ID + 程序计数器 + 寄存器组 + 地址空间 + 其他资源（打开的文件、IO 设备……）
              ▲
              └── 瓶颈就在这里：只有一个
```

解法是：**不再把程序计数器直接关联到进程上，而是给每个想并发执行的「内部可执行实体」各配一个程序计数器**。

这些内部实体就是**线程（thread）**。

```text
改造前                        改造后
┌─────────────────┐          ┌───────────────────────────────┐
│ 进程            │          │ 进程                           │
│  PC   ──► 一个   │          │  地址空间（共享）               │
│  寄存器组         │          │  打开的文件（共享）             │
│  地址空间         │          │  ┌────────┐┌────────┐┌───────┐│
│  打开的文件       │          │  │ 线程1  ││ 线程2  ││ 线程3 ││
└─────────────────┘          │  │ PC     ││ PC     ││ PC    ││
                             │  │ 寄存器  ││ 寄存器  ││ 寄存器 ││
                             │  │ 栈指针  ││ 栈指针  ││ 栈指针 ││
                             │  │ 栈     ││ 栈     ││ 栈    ││
                             │  └────────┘└────────┘└───────┘│
                             └───────────────────────────────┘
```

这就解决了阻塞问题，而且**不需要创建新进程**：某个线程去等 IO 资源（比如把文件内容读进数组），其他线程照常执行，不被阻塞。

### 为什么线程必须有自己的 CPU 状态

线程共享所属进程的**整个地址空间**，但**不能共享 CPU 状态**。

理由和进程一模一样：线程也会被打断，好把 CPU 让给别的线程。
既然要被打断，就必须能把它的状态捕捉下来，等 CPU 再分配回来时恢复。

所以线程有了自己的 PC，就必然还要有自己的**寄存器组、标志位（flags）、累加器（accumulator）等**，本质上就是**自己的一整套 CPU 状态**。

其中特别要注意**独立的栈指针（stack pointer）**。
栈是组织和访问局部变量的高效方式，如果同一进程内两个并发运行的函数共用一个栈，它们会轻易覆盖掉彼此的数据。

```text
共用一个栈（错误）              每个线程一个栈（正确）
┌──────────────┐              ┌──────────┐ ┌──────────┐
│ 线程2 的局部变量 │ ← 覆盖！     │ 线程1 栈  │ │ 线程2 栈  │
│ 线程1 的局部变量 │              │ sp1 ──►  │ │ sp2 ──►  │
└──────────────┘              └──────────┘ └──────────┘
```

**所以每个线程必须有自己的栈。**

## 6. 「有自己的栈」不等于「别人访问不到」

作者特意强调了一点，很容易被误解：

**每个线程有自己的栈，并不意味着线程之间不能读写对方的栈。**

道理很直接：**地址空间是进程的属性，不是线程的属性**。
既然所有线程的栈都位于这块共享的地址空间之内，就没有任何东西能阻止一个线程去访问另一个线程的栈。

```text
进程的地址空间（共享）
┌─────────────────────────────────────────────┐
│  text（代码）  data（常量）  heap（堆）        │
│                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ 线程1 栈  │  │ 线程2 栈  │  │ 线程3 栈  │  │
│  └──────────┘  └────▲─────┘  └────┬─────┘  │
│                     └─── 可以访问 ──┘        │
└─────────────────────────────────────────────┘
```

「能不能」和「该不该」是两回事。
一般来说，除非你非常清楚自己在干什么，**最好别直接访问其他线程的栈**。

### 线程之间想共享内存，用堆

如果同一进程内的线程需要通过共享内存来通信，**堆（heap）更合适**，因为堆里的数据本来就不是按可预测的方式组织的。

但即使用堆也仍需谨慎：一个线程在读某块内存，另一个线程同时在写，结果可能是灾难性的。
同步并发任务重要到什么程度？**相应的机制被直接实现在硬件里**。
这是后续一期的内容，本期不展开。

### 跨进程仍然需要 IPC

因为我们并没有完全丢弃进程这个概念，**不同进程的地址空间依然是隔离的**。

```text
同一进程内的线程  ──► 默认共享内存，直接读写即可
不同进程的线程    ──► 仍然需要 IPC
```

## 7. 内核怎么表示线程：Linux 的 task

用多线程模型替换传统多进程模型，需要重新实现进程控制块（PCB）。

最直白的路子是**再搞一个结构体来表示线程**。
实现细节因平台而异，但最常见的做法是 **Linux 内核的方案：进程和线程用同一个结构体表示，叫 `task`**。

作者认为这是编程中命名的完美范例，因为它**抽象掉了进程和线程的区别**：

```text
不用再说：「在进程之间、线程之间、或者两者之间轮换 CPU」
只需要说：「在 task 之间轮换」
```

如果想用**同一个调度器**同时管线程和进程，这种实现要直观得多。

### 主线程

不管用哪种方案，这么做都要求**每个进程至少有一个线程，叫主线程（main thread）**。

进程被创建时，操作系统会自动创建这个线程。
所以即使一个进程完全不用多线程，操作系统也能通过调度它的主线程来给它分配 CPU。

### 静态还是动态创建线程

进程是「启动时就带固定数量的额外线程」，还是「运行时动态创建」，取决于操作系统的实现。

**主流操作系统都偏好动态方案**：每个进程都以单线程启动，需要时在运行时创建额外线程。

这当然增加了操作系统内部实现的复杂度，因为它必须提供动态创建线程的系统调用。
但它仍是首选，原因很实际：**很多情况下根本无法在编译期知道运行时需要多少线程**。

### 主线程一死，全体陪葬

在许多实现里，因为主线程标识着它所属的进程：

```text
主线程 ──► 派生出 线程A、线程B、线程C
   │
   └─ 主线程执行结束
          ▼
   线程A、线程B、线程C 立即全部终止
```

处理这个问题有多种办法，但那是另一期的话题。

## 8. 回到服务器例子

用多线程方案，可以**为每个到来的客户端派生一个新线程**。

```text
        ┌────────────────────────────────┐
        │ 服务器进程（一个地址空间）        │
        │  主线程：accept                 │
        │  ├── 线程1 → 处理客户端 C1       │
        │  ├── 线程2 → 处理客户端 C2       │
        │  ├── 线程3 → 处理客户端 C3       │
        │  └── ...                       │
        └────────────────────────────────┘
```

效果和多进程方案类似，但有两个明显好处：

| 对比项 | 多进程 | 多线程 |
| --- | --- | --- |
| 内存消耗 | 每个客户端一整套地址空间 | 共享一个地址空间，消耗少得多 |
| 创建速度 | 创建进程的系统调用慢 | 创建线程的系统调用**通常快得多** |
| 共享全局状态 | 需要 IPC | 直接共享内存（但要同步） |

到这里，为什么线程更快的原因应该已经不言自明了。

## 9. 线程到底是什么：先说它不是什么

**线程不是函数。**

线程执行的任何代码，都位于进程内存布局的 **text 段**。
**线程本身不包含代码，它通过自己的程序计数器指向代码。**

这意味着：**多个线程可以指向完全相同的可执行代码**。

服务器例子里正是如此：所有请求的处理方式都一样，所以所有 handler 线程**并不各自持有一份函数，而是指向内存中同一个函数**。

```text
进程地址空间
┌──────────────────────────────────────────────┐
│ text 段                                       │
│   0x4010: handle_client:                     │
│              ...                             │
└──────▲────────────▲────────────▲─────────────┘
       │            │            │
   ┌───┴───┐   ┌────┴──┐   ┌─────┴─┐
   │ 线程1 │   │ 线程2 │   │ 线程3 │   三个 PC 都指向 0x4010
   │ PC    │   │ PC    │   │ PC    │   但各自有独立的栈和寄存器
   └───────┘   └───────┘   └───────┘
```

多个线程同时访问这块内存危险吗？**不危险。**

因为可执行代码和常量分别位于 **text 段和 data 段**，这**两个区域永远不会被写入**。
所有运行时产生的、属于特定线程的信息，都在**栈或堆**上。

所以，**多个线程并发访问同一段可执行代码是完全安全的**。

### 为什么 C 里创建线程要传函数指针

理解上面这点，就能明白为什么在 C 这样的低级语言里，创建线程需要**传一个函数指针作参数**。

看起来困惑，实际上做的事情很朴素：**把线程将要执行的那段代码的起始内存地址传过去**。

```text
pthread_create(&tid, NULL, handle_client, arg);
                             │
                             └──► 0x4010，新线程 PC 的初值
```

所以请不要误解动画：**线程不是异步函数（asynchronous function）。**

### 线程的三种定义

| 视角 | 定义 |
| --- | --- |
| 操作系统视角 | 线程就是上一期的进程所扮演的角色：**最基本的执行单元** |
| 开发者视角 | 一种告诉操作系统「我程序里的这几段代码可以并发执行」的机制 |
| 另一种常见说法 | 线程是**轻量级进程（lightweight process）**，更容易、更快创建 |

## 11. 核心总结

```text
为什么需要线程
│
├── 起点：并发的两个目的
│   ├── 多任务的错觉
│   └── 填满 CPU 因等待 IO 而闲置的空隙
│
├── 障碍：进程只有一个程序计数器
│   └── 同进程内的两个函数无法交替执行 → 阻塞效应
│
├── 旧解法：多进程 + IPC
│   ├── 内存开销大（每个进程一套地址空间）
│   ├── 创建进程本身消耗 CPU 时间
│   └── 全局状态要靠 IPC 同步
│
├── 新解法：把 PC 从进程移到线程
│   ├── 每线程私有：PC、寄存器组、标志位、栈指针、栈
│   ├── 进程共享：地址空间、text/data、打开的文件
│   └── Linux 用同一个 task 结构表示进程和线程
│
└── 结论
    ├── 每个进程至少有一个主线程，主线程死则全体死
    ├── 线程不是函数，只是指向 text 段的一个 PC
    ├── 并发访问 text/data 安全，并发访问堆需要同步
    └── 以上全部在单核 CPU 上就已经成立
```

> 线程不是「同时跑得更快的函数」，而是**把「程序计数器」这一份资源从进程手里拆出来分给多个执行流**，从而让一个进程内部也能享受并发，把等 IO 的那些空隙填满。
