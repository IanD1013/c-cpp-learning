# 为什么有些项目会用多种编程语言

> 视频来源：Core Dumped -《Why Some Projects Use Multiple Programming Languages》
> https://www.youtube.com/watch?v=XJC5WB2Bwrc

## 0. 这一期在讲什么

「为什么有的项目里同时出现好几种编程语言」是这个频道收到最多的提问之一。

这个问题可能极其简单，也可能极其困难，取决于项目属于哪一类。

**第一类：多语言 = 多进程。**

以全栈框架 Django 为例，Python 写后端跑在服务器上，HTML / CSS / JavaScript 写界面跑在客户端。

这确实是多语言项目，但不难理解：本质上是**两个独立的进程**，在运行期通过某种进程间通信（inter-process communication）远程对话。

**第二类：多语言 = 同一个进程。**

用不同语言写的组件，最终被打包进**同一个可执行文件**，作为**同一个进程**跑起来。

```text
第一类（Django 那种）                     第二类（本期主题）
─────────────────────                    ─────────────────────
┌────────────┐   IPC   ┌────────────┐    ┌──────────────────────────┐
│ 进程 A      │◄───────►│ 进程 B      │    │        单个进程           │
│ Python 后端 │  网络/  │ JS 前端     │    │ ┌────────┐  ┌──────────┐ │
└────────────┘  管道/  └────────────┘    │ │ C 部分  │  │ Rust 部分 │ │
                 socket                  │ └────────┘  └──────────┘ │
                                         └──────────────────────────┘
两套工具链，两个二进制，              一套链接结果，一个二进制，
互不相干                              必须在机器码层面互相兼容
```

本期只回答第二类，而且**先只考虑编译成机器码的语言**。

编译型语言和解释型语言怎么混，作者说留到下一期讲。

前置知识主要是编译与可执行文件，见 [为什么应用程序是操作系统专属的](14-why-applications-are-os-specific.md) 和 [一个程序不是一个进程](08-a-program-is-not-a-process.md)。

## 1. 问题：每种语言都有自己的编译器，怎么可能住进同一个二进制

一般来说，每种编程语言都有自己专属的编译器。

我们不能拿一个 Rust 文件丢给 Go 编译器去编译。

那么问题就来了：

> 如果大多数语言都有**各自独立的编译器、运行时和内存模型**，它们怎么可能共存于同一个二进制文件里？

让人困惑的根源是一个流传很广的**过度简化**：

> 编译器就是把源代码直接变成可执行文件的工具。

编译器确实会产出可执行文件，但那只是一个**多步骤流程**的最终结果，中间那些步骤我们平时看不见。

把这个黑盒拆开，答案就出来了。

---

## 2. 拆开黑盒：GCC 的四个阶段

### 2.1 示例程序

视频里用了一个很简单的 C 程序：打印一句话，但**打印的内容取决于运行它的操作系统**。

（下面是根据旁白重建的代码。）

```c
#include <stdio.h>

int main(void) {
#ifdef __linux__
    printf("Hello from GNU/Linux\n");
#elif defined(_WIN32)
    printf("Hello from Windows\n");
#else
    printf("Hello from somewhere else\n");
#endif
    return 0;
}
```

在大多数 GNU/Linux 系统上，C 的首选编译器是 **GCC**。

GCC 过去代表 GNU C Compiler（GNU C 编译器），但这个说法**已经不成立了**，原因在第 6 节。

从我们的视角看只有两步：

```bash
gcc hello.c -o hello    # 编译
./hello                 # 运行
```

### 2.2 底下真正发生的四步

```text
  hello.c
    │
    │  ① 预处理（preprocessing）
    │     去掉注释 / 展开宏 / 处理条件编译 / 展开 #include
    │     #include <stdio.h> 这一行会被**头文件的全部内容**替换掉，
    │     并且它自己 include 的头文件也一并展开
    ▼
  hello.i        ← 输出仍然是 C 代码，只是「预处理过的 C 代码」
    │
    │  ② 编译（compilation）
    │     C  ->  汇编语言
    ▼
  hello.s        ← 人类可读的汇编，不是机器码
    │
    │  ③ 汇编（assembling），由汇编器（assembler）完成
    │     汇编  ->  机器码（CPU 认识的 0 和 1）
    ▼
  hello.o        ← 目标文件（object file），还**不能运行**
    │            函数在二进制中的位置还没确定
    │
    │  ④ 链接（linking）
    │     + C 标准库的目标文件（printf 的真正实现在那里）
    ▼
  hello          ← 可执行文件
```

### 2.3 第一个被打破的迷思

> **编译器并不总是把源代码变成机器码。**

事实上很多编译器把源代码变成**中间表示（intermediate representation）**，比如汇编，甚至变成**另一种编程语言**。

GCC 的第 ② 步就是典型：它的产物是 `.s` 汇编文件，不是机器码。

真正生成机器码的是第 ③ 步的**汇编器**，而汇编器技术上也是一种编译器。

### 2.4 为什么目标文件还不能跑

我们的例子只是往控制台打印一行字。

但 `printf` 的**真正实现**在 C 标准库里，那个库也得走一遍完全一样的编译流程。

所以到了第 ④ 步，手上往往有**多个目标文件**：一些来自我们自己的代码，一些来自引入的外部库。

链接器（linker）的工作，就是把这些目标文件合并成**一个自包含的可执行文件**。

## 3. 链接的两种方式：静态与动态

### 3.1 静态链接（static linking）

最简单的做法：把库里每个用到的函数的机器码**直接拷贝进**最终的可执行文件。

程序需要的库函数全部内嵌在输出文件里，完全自包含，随时可以运行。

### 3.2 动态链接（dynamic linking）

想一想你系统上有多少程序在用标准库的 `printf`。

如果每个程序都静态内嵌一份自己的拷贝，磁盘上就会散落着**成千上万份一模一样的机器码**。

动态链接的做法是把库预编译成一种特殊文件：**动态共享库（dynamic shared library）**。

| 平台 | 扩展名 |
| --- | --- |
| Unix-like（Linux / macOS） | `.so` |
| Windows | `.dll` |

这种文件和可执行文件很像，里面同样是库函数的可执行机器码。

**关键区别是它没有入口点（entry point）**。

这很合理，因为库通常没有 `main` 函数 - `main` 是用来启动一个程序的。

采用动态链接编译时，链接器**不会**把库函数拷进可执行文件，而是只插入一条**对库的引用**。

运行期如果程序需要那个函数，操作系统会把它加载进程序的**地址空间（address space）**，程序用起来就像它本来就是可执行文件的一部分。

```text
静态链接
┌────────────┐  ┌────────────┐  ┌────────────┐
│ prog_a     │  │ prog_b     │  │ prog_c     │
│ ┌────────┐ │  │ ┌────────┐ │  │ ┌────────┐ │
│ │ printf │ │  │ │ printf │ │  │ │ printf │ │  ← 三份一模一样的机器码
│ └────────┘ │  │ └────────┘ │  │ └────────┘ │
└────────────┘  └────────────┘  └────────────┘

动态链接
┌────────────┐  ┌────────────┐  ┌────────────┐
│ prog_a     │  │ prog_b     │  │ prog_c     │
│ ref → libc │  │ ref → libc │  │ ref → libc │  ← 只存一条引用
└──────┬─────┘  └──────┬─────┘  └──────┬─────┘
       └───────────────┼───────────────┘
                       ▼  运行期由操作系统加载进地址空间
         ┌───────────────────────────┐
         │ libc.so                   │
         │  printf 的机器码（仅 1 份） │
         │  没有 main，没有入口点      │
         └───────────────────────────┘
```

### 3.3 两者对比

| | 静态链接 | 动态链接 |
| --- | --- | --- |
| 库代码在哪 | 拷进可执行文件 | 单独的 `.so` / `.dll` |
| 可执行文件体积 | 大 | 小 |
| 磁盘占用（N 个程序共用一个库） | N 份 | 1 份 |
| 内存占用 | 每个进程各自一份 | 共享，按需加载 |
| 运行依赖 | 无，完全自包含 | 必须能找到那个库 |
| 打补丁 | 每个程序都得重新编译 | 换掉库文件即可 |

动态链接省磁盘也省内存，在装了大量程序、共用公共库的系统上优势巨大。

而且更灵活：可以更新或修补一个库，而不必重新编译所有用到它的程序。

> 作者说链接（静态和动态）本身就值得单独一期，本期只讲到这里。

## 4. 流水线是可以拆开的

既然拆成了这么多阶段，很自然会问：**为什么要这么模块化？直接从源码到可执行文件不好吗？**

我们平时看不到中间步骤，只是因为 GCC 这类编译器**默认把它们隐藏了**，只把最终的可执行文件摆出来。

加上合适的编译参数，这些阶段就会全部暴露。

| 参数 | 效果 |
| --- | --- |
| `--save-temps` | 除最终可执行文件外，保留全部中间文件（`.i` / `.s` / `.o`） |
| `-E` | 只做预处理，停在 `.i` |
| `-S` | 停在生成汇编之后，产出 `.s` |
| `-c` | 停在汇编之后，产出 `.o`（不链接） |

```bash
gcc --save-temps hello.c -o hello
# hello.i  hello.s  hello.o  hello

gcc -S hello.c        # 只要汇编
# hello.s
```

这在教学场景里非常有用：可以直接看到高级 C 代码是怎么翻译成汇编或机器码的。

在工程场景里也常用来**审查性能关键代码**，看看编译器生成的指令到底够不够高效。

### 4.1 更关键的一点：可以从流水线的任意阶段进入

不仅能提前停，还能**从中间插进去**。

我们可以直接把一个汇编文件丢给 GCC，告诉它「只需要汇编 + 链接」。

```text
      源文件                    可以从任意一层切入
        │
   .c ──┼──► 预处理 ──► .i ──► 编译 ──► .s ──► 汇编 ──► .o ──► 链接 ──► 可执行
        │                              ▲               ▲          ▲
   .i ──┘                              │               │          │
   .s ─────────────────────────────────┘               │          │
   .o ─────────────────────────────────────────────────┘          │
   .a / .so ──────────────────────────────────────────────────────┘
```

这一点非常重要，因为它意味着：

> 我们可以用汇编写一部分代码，在不同阶段喂给编译器，最后由**链接器**把它们混合成一个可执行文件。

原始问题的答案，到这里已经露头了。

## 5. 第一个多语言例子：C + 汇编

假设要写一个程序，计算 0 到某个数之间有多少个质数，而且要**尽可能快**。

整个程序当然可以用 C 写完。

但假设我们不信任编译器的优化，决定把那个**重计算的函数直接用汇编写**，然后从 C 里调用它。

```c
/* main.c */
#include <stdio.h>

/* 实现在汇编文件里 */
extern int count_primes(int n);

int main(void) {
    printf("%d\n", count_primes(1000000));
    return 0;
}
```

```asm
; primes.s
    .globl count_primes
count_primes:
    ; ... 手写优化过的质数计数
    ret
```

然后把两个文件一起交给 GCC：

```bash
gcc main.c primes.s -o primes
```

```text
 main.c ──► 预处理 ──► 编译 ──► 汇编 ──► main.o ──┐
                                                 ├──► 链接器 ──► primes
 primes.s ─────────────────────► 汇编 ──► primes.o ┘
```

GCC 会：编译并汇编 C 代码，汇编那个汇编文件，然后把两个目标文件链接成单个可执行文件。

**我们就这样编译出了一个多语言项目。**

### 5.1 这不是玩具

这个技巧被大量真实系统使用：

| 项目 | 用法 |
| --- | --- |
| Linux 内核 | 大部分逻辑 C，性能与底层部分汇编 |
| FFmpeg | 编解码热点用汇编 |
| OpenSSL | 密码学原语用汇编 |
| 各类嵌入式项目 | 启动代码、中断处理用汇编 |

共同模式是：**逻辑用 C，性能真正要命的地方退回汇编。**

---

## 6. 迷思二：GCC 不是「一个编译器」

我们随口叫的「C 编译器」，比如 GCC，其实不是单个编译器。

它是一条**工具链（tool chain）**：一串按顺序执行的工具，每一级消费上一级的输出。

而且每个工具都是**可插拔的**。

我们可以替换工具链的某些部分，也可以在不同环节喂进自己的文件（第 4 节已经演示过）。

这正是为什么 GCC 不只支持 C：

```text
                     GCC = 一堆前端 + 共用的后端
  C ──────────┐
  C++ ────────┤
  Objective-C ┤
  Fortran ────┼──► 各自的前端 ──► 汇编 ──► 汇编器 ──► 目标文件 ──► 链接器 ──► 可执行
  Ada ────────┤                            （共用）    （共用）    （共用）
  D ──────────┤
  Go ─────────┘   （取决于编译时的配置）
```

GCC 最初确实代表 **GNU C Compiler**。

但随着它演化成支持众多语言的编译器套件，这个名字变得有误导性。

于是这个缩写被**重新定义**为：

> **GCC = GNU Compiler Collection（GNU 编译器集合）**

作者特意强调这件事的重要性：

每次有人随口叫它「GNU C 编译器」，都在无意中强化一个错误印象 - 好像这整套系统是个**把 C 代码变成可执行文件的单一黑盒**。

而事实上，它已经很多年不是那个东西了。

## 7. 混两种高级语言：C + Fortran

汇编不是人人都会写。

而且平心而论，汇编**本来就是 C 编译流水线的一环**，拿它举例多少有点「作弊」。

那换成高级语言呢？比如把项目的一部分用 **Fortran** 实现。

完全可行，而且比想象中常见。

但这时通常需要**多个步骤**：

```bash
gfortran -c fast.f90 -o fast.o     # ① 编译 + 汇编 Fortran 文件
gcc      -c main.c  -o main.o      # ② 编译 + 汇编 C 文件
gcc  main.o fast.o -lgfortran -o app   # ③ 把两个目标文件链接成一个可执行文件
```

```text
 fast.f90 ──► Fortran 自己的流水线 ──► fast.o ──┐
                                               ├──► 链接器 ──► app
 main.c   ──► C 的流水线            ──► main.o ─┘
```

和汇编不同的是：汇编已经内嵌在 C 的编译流水线里，而 **Fortran 有自己独立的流水线、自己的编译器，有时还有自己的运行时依赖**。

到这里，原始问题的答案已经非常清楚了：

> **不同语言能住进同一个可执行文件，归根结底靠的是链接器（linker）。**

## 8. 跨工具链：C + Rust

参与的语言甚至**不需要来自同一个编译器套件**。

拿 Rust 举例。

它的工具链和 C 完全不同：不同的编译器、不同的构建系统、甚至不同的设计哲学。

但当它要产出最终二进制时，猜猜靠什么？

**Rust 同样依赖链接器。**

### 8.1 从 C 调用 Rust 函数

四步：

1. 用 Rust 实现那个函数；
2. 把 Rust 代码编译成**静态库或动态库**；
3. 在 C 代码里**声明并使用**这个函数；
4. 编译 C 代码，并与 Rust 编译出的库**链接**。

```rust
// src/lib.rs
#[no_mangle]
pub extern "C" fn add(a: i32, b: i32) -> i32 {
    a + b
}
```

```c
/* main.c */
extern int add(int a, int b);   /* 实现在 Rust 库里 */

int main(void) {
    return add(2, 3);
}
```

```text
 lib.rs ──► rustc（Rust 工具链）──► libmylib.a ──┐
                                                ├──► 链接器 ──► app
 main.c ──► gcc（C 工具链）    ──► main.o     ──┘
```

### 8.2 反过来也行，而且更常见

从 Rust 调用 C 函数同样可行，取决于你想干什么。

事实上，**Rust 调 C 比 C 调 Rust 更常见**。

原因是 C 更老，大量成熟的库和系统 API 都是 C 写的。

Rust 开发者经常需要接入这个既有生态，尤其是在**图形、密码学、操作系统 API** 这些领域。

### 8.3 另一个动机：性能

很多项目里，**整个系统并不需要都飞快，只有某些部分需要**。

于是常见做法是：

```text
┌──────────────────────────────────────────┐
│ 项目主体：高级语言                          │
│   为了开发便利和开发速度                     │
│   （Python / JavaScript / Go ...）         │
│                                          │
│   ┌────────────────────────────────┐     │
│   │ 性能关键组件：低级语言            │     │
│   │   （C / C++ / Rust / 汇编）      │     │
│   └────────────────────────────────┘     │
└──────────────────────────────────────────┘
```

## 9. 最重要的一点：能链接 ≠ 能正确调用

收尾前有个非常重要的点。

假设有两种高级语言：语言 A 和语言 B。

**它们都有最终的链接阶段，并不自动意味着它们能被正确地链接进同一个可执行文件。**

### 9.1 例子一：参数放的寄存器对不上

在语言 B 里实现一个函数，从语言 A 调用它。

即使两个编译器为**同一种架构**生成汇编，它们对「函数之间如何传递数据」的假设也可能不同。

比如语言 A 的编译器把两个参数放在寄存器 0 和 1，而语言 B 的编译器期望参数在寄存器 1 和 2。

```text
语言 A（调用方）                       语言 B（被调用方）
────────────────                      ────────────────
r0 = 5    ← 第 1 个参数                期望第 1 个参数在 r1  ✗ 读到的是 7
r1 = 7    ← 第 2 个参数                期望第 2 个参数在 r2  ✗ 读到的是垃圾
r2 = （没动）
          call ──────────────────►
                                      算完把结果写进 r1
          ◄────────────────── ret
读 r0 拿返回值  ✗ r0 从头到尾没被写过
```

两边产生的机器码都是**合法的**，但由于**调用约定（calling convention）**不同，运行期的结果是**未定义行为（undefined behavior）**。

语言 A 把参数放错了地方，语言 B 拿错误的数据做运算。

而且问题不止于此：语言 B 把结果写进 r1 就返回了，语言 A 却去 r0 取结果。

所以不仅算错了，**语言 A 压根看不到也用不上那个结果**。

### 9.2 例子二：传引用 vs 传值

换成语言 X 和语言 Y。

这次两边都用 r0 和 r1 传参和收参，寄存器编号没问题。

但假设语言 X 对所有函数参数**一律传引用（pass by reference）**：它往寄存器里放的是变量的**地址**，而不是变量的**值**。

而语言 Y **传值（pass by value）**：它期望寄存器里就是实际的值，被调用时立刻把两个寄存器的内容相加。

```text
语言 X（一律传引用）                    语言 Y（一律传值）
──────────────────                     ──────────────────
a = 5  存放在 0x7ffd1000
b = 7  存放在 0x7ffd1008

r0 = 0x7ffd1000   ← 地址，不是 5
r1 = 0x7ffd1008   ← 地址，不是 7
       call ───────────────────►
                                       直接 add r0, r1
                                       = 0x7ffd1000 + 0x7ffd1008
                                       = 0xFFFA2008
                                       期望的却是 5 + 7 = 12
```

这种不匹配让语言 Y 把**内存地址当成了实际的值**，把两个地址加了起来，而不是把地址里存的值加起来。

结果要么完全错误，要么直接崩溃。

> 所以即使两个编译器都产出了合法可执行的汇编，**除非双方就「怎么互相说话」达成一致，最终链接出来的二进制就是不一致的。**

### 9.3 这套规则叫 ABI

这类底层规则由 **ABI（application binary interface，应用二进制接口）** 定义。

| | API | ABI |
| --- | --- | --- |
| 层级 | 应用层（源代码） | 二进制层（机器码） |
| 规定什么 | 有哪些函数、参数是什么 | 参数放哪个寄存器、返回值放哪、栈怎么用、符号怎么命名 |
| 谁来遵守 | 写代码的人 | 编译器生成的机器码 |

> 正如 API 在应用层定义函数，**ABI 定义二进制代码的不同组件如何通过硬件互相交互**。

所以混用两种语言时，**光是两边都能产出目标文件是不够的**。

至少有一方 - 更准确地说，是它当中**与另一种语言交互的那部分** - 必须符合对方的 ABI 预期。

### 9.4 怎么让它们对齐

回到语言 X / 语言 Y 的例子，有两个方向：

```text
方案一：让 Y 迁就 X                     方案二：让 X 迁就 Y
─────────────────                      ─────────────────
X: r0/r1 放地址（不变）                  X: r0/r1 改成直接放值
Y: 先解引用（dereference），             Y: 直接相加（不变）
   从地址取出真实的值装进寄存器，
   再做加法

Y 符合了 X 的 ABI 预期                   X 符合了 Y 的 ABI 预期
```

### 9.5 好消息：语言设计者早就想到了

这些底层细节，我们平时**不需要操心**，除非在系统层面工作。

现代语言都提供了关键字、属性和编译参数来简化这件事：

| 语言 | 写法 |
| --- | --- |
| C | 用 `extern` 声明外部函数 |
| Rust | `extern` 关键字 + `#[no_mangle]` 属性 |
| Fortran | `bind` 属性（如 `bind(C, name="...")`） |
| Go | 在 `import "C"` 上方紧贴一个特殊注释块（cgo），甚至可以**在 Go 源文件里直接内联写 C 代码** |

每种语言有自己的写法，但在编译期它们的作用完全一样：

> 告诉编译器：「嘿，这个函数要和另一种语言写的代码交互，请确保生成的汇编遵循预期的 ABI。」

## 11. 核心总结

```text
不同语言如何住进同一个可执行文件
│
├── 前提：编译不是一步，是一条流水线
│   ├── ① 预处理  .c → .i     （仍是 C 代码）
│   ├── ② 编译    .i → .s     （汇编，不是机器码 ← 迷思一被打破）
│   ├── ③ 汇编    .s → .o     （机器码，但还不能跑）
│   └── ④ 链接    .o + 库 → 可执行文件
│
├── 关键结论：答案是链接器
│   ├── 流水线可以提前停（-E / -S / -c / --save-temps）
│   ├── 也可以从任意阶段切入（直接喂 .s / .o / .a / .so）
│   └── 只要都能产出目标文件，就能被链接到一起
│
├── 链接的两种方式
│   ├── 静态：把机器码拷进可执行文件，自包含但重复
│   └── 动态：只存引用，运行期由 OS 载入地址空间
│       └── 省磁盘、省内存、可单独打补丁；.so / .dll；无入口点
│
├── 三层递进的例子
│   ├── C + 汇编     → 汇编本来就在 C 流水线里（Linux 内核 / FFmpeg / OpenSSL）
│   ├── C + Fortran  → 各自独立的流水线，汇合于链接器
│   └── C + Rust     → 完全不同的工具链，依然汇合于链接器
│
├── 迷思二：GCC 不是一个编译器
│   └── 是可插拔的工具链 = GNU Compiler Collection
│       （C / C++ / Objective-C / Fortran / Ada / D / Go）
│
└── 真正的门槛不是链接，是 ABI
    ├── 调用约定：参数放哪个寄存器、返回值放哪个寄存器
    ├── 传参语义：传引用 vs 传值
    ├── 不一致 → 未定义行为或崩溃（两边机器码都合法！）
    └── 解法：让一方遵守另一方的 ABI
        └── C `extern` / Rust `extern` + `#[no_mangle]` /
            Fortran `bind` / Go cgo
```

> 多语言项目之所以可能，不是因为某个编译器懂好几种语言，而是因为**所有编译流水线最后都在同一个地方汇合 - 目标文件与链接器**。
> 编译器把各自的源码翻译成同一种「通用货币」（目标文件里的机器码），链接器再把它们拼成一个二进制。
> 但拼得起来不等于说得通：**链接器只负责把代码放在一起，ABI 才负责让它们听懂对方在说什么。**
