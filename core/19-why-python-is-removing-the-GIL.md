# 为什么 Python 正在移除 GIL（global interpreter lock）

> 视频来源：Core Dumped -《Why Python Is Removing the GIL》
> https://www.youtube.com/watch?v=UXwoAKB-SvE

## 0. 这一期在讲什么

前面几期讲过并发（concurrency）与并行（parallelism）的区别，也讲过多核系统上的线程。

本期回答一个被反复问到的具体问题：**为什么 Python 开了一堆线程，CPU 却只有一个核在干活？**

答案不在 Python 这门语言里，而在它的官方解释器 CPython 的一个 1990 年代的设计决定上。

前置知识见 [并发不是你想的那样](05-concurrency-is-not-what-you-think.md)、[多核系统上的线程](13-threads-on-multicore-systems.md) 和 [为什么有些项目要用多种编程语言](16-why-some-projects-use-multiple-programming-languages.md)。

---

## 1. 问题：同一份逻辑，两种语言，两种结果

作者写了两个程序，逻辑完全一致：

1. 查出系统有几个 CPU 核心，就开几个线程；
2. 每个线程在无限循环里做数学运算。

一个用 Python 写，一个用 C 写。

单看终端输出，两个都只是安静地跑着，看不出区别。

打开资源监视器（resource monitor）才看出问题：

```text
                 C 版本                        Python 版本
core 0  ████████████████ 100%        core 0  ████████████████ 100%
core 1  ████████████████ 100%        core 1  ██               ~5%
core 2  ████████████████ 100%        core 2  █                ~3%
core 3  ████████████████ 100%        core 3  ██               ~4%
core 4  ████████████████ 100%        core 4  █                ~2%
core 5  ████████████████ 100%        core 5  ██               ~4%
core 6  ████████████████ 100%        core 6  █                ~3%
core 7  ████████████████ 100%        core 7  ██               ~5%
        ────────────────                     ────────────────
        总计 ≈ 800% CPU                      总计 ≈ 100% CPU
```

C 版本吃满了所有核。

Python 版本的总吞吐，等于**一个核**的量，剩下的核心哪怕空着也用不上。

（8 核只是为了举例，作者没报具体核数；关键在于 C 的总量随核数线性增长，Python 的总量卡在 100% 不动。）

线程确实都创建出来了，为什么不并行？

## 2. 前置纠正：线程 ≠ 并行

学底层概念时最常见的错误之一，就是**默认线程自动等于并行**。

作者认为这个误解来自教程的措辞：很多文章把线程解释成「不阻塞主函数的情况下跑一段代码」，于是读者自然联想到「同时运行」。

而「同时」这个词很容易骗人。

**并发（concurrency）** 的目的是让系统同时处理多个任务，也就是多任务（multitasking）。

因为系统的处理器数量通常少于任务数量，实现方式是**轮流占用 CPU**：

```text
单核上的并发（交替，是幻觉）

core 0 │ A │ B │ C │ A │ B │ C │ A │ B │ C │
       └───┴───┴───┴───┴───┴───┴───┴───┴───┘
       ──────────────► 时间

切换得足够快 → 看起来三个任务在同时跑
```

如果系统有多个核心，并发可以再进一步：把不同任务分配到不同核心上。

到这一步，多任务就不再是幻觉，而是真正的同时执行：

```text
多核上的并行（真的同时）

core 0 │ A A A A A A A A A │
core 1 │ B B B B B B B B B │
core 2 │ C C C C C C C C C │
       ──────────────► 时间
```

| | 并发 concurrency | 并行 parallelism |
| --- | --- | --- |
| 含义 | 同时**处理**多个任务 | 同时**执行**多个任务 |
| 需要多核吗 | 不需要 | 需要 |
| 实现 | 交替占用 CPU | 分配到不同核心 |
| 关系 | 大类 | 并发的一个子集 |

两者都属于并发，但只有后者是并行。

我们写程序开多个线程时，真正在做的事情是：**告诉操作系统，同一个程序内的多段代码可以并发运行，如果条件允许，还可以并行运行。**

这是绝大多数主流语言的行为。

Python 的问题在于：不管你的系统有多少核，你开多少线程，它们就是不会并行。

## 3. 为什么需要锁：竞态条件与 mutex

问题的根源要从并发本身的风险讲起。

两个并发运行的线程如果共享**可变数据**，就有可能同时读写同一份数据。

设想两个线程共享一个字符串，一个线程正在更新它：

```text
线程 A：正在把 "hello" 改成 "hello world"

时刻 t0   "hello"
时刻 t1   "hello wo"        ← 改到一半
                └──────────► 线程 B 此刻读走了 "hello wo"
时刻 t2   "hello world"

线程 B 拿到的是一份不一致的数据
```

时机刚好错开的话，另一个线程会在第一个线程还没改完时读到半成品，拿到不一致的数据。

这就是**竞态条件（race condition）**。

解决办法在细节上很复杂，但高层次上归结为一种特殊的变量：**互斥锁（mutex lock）**。

用储物柜和钥匙来类比：共享变量被放进一个上了锁的盒子里。

```text
        ┌─────────── 受保护的盒子 ───────────┐
        │                                    │
钥匙 🔑 │        shared_string                │
  ▲     │                                    │
  │     └────────────────────────────────────┘
  │
  ├── 线程 A：拿到钥匙 → 进盒子 → 修改 → 归还钥匙
  │
  └── 线程 B：想进去，没钥匙 → 阻塞等待
              （读也不行，读同样要拿钥匙）
```

线程想访问变量，必须先拿到钥匙、进入受保护区域，才能开始操作。

钥匙只有一把，所以同一时刻只有一个线程能持有锁。

其他线程想改这个变量是改不了的，因为它没有钥匙，必须等到当前线程改完、释放锁。

**读也一样**：没有钥匙就不能读，必须等对方结束并释放锁。

这就是避免竞态条件的极简版解释。

## 4. 关键转折：你从来没有「直接运行」过 Python

CPU 看不懂 Python 代码。

我们没法把 Python 代码加载进内存，然后指望 CPU 开始执行它。

要跑一个 Python 脚本，需要另一个程序：**解释器（interpreter）**，一个读取 Python 脚本并执行它的程序。

这个程序是用高性能语言写的，官方 Python 解释器用的语言是 **C**。

所以严格来说，我们**从来没有直接运行过 Python 程序**。

我们真正运行的，是一个「解释 Python 代码的 C 程序」。

每一行 Python 代码，都对应着一连串最终跑在硬件上的 C 例程（routine）。

以一个最简单的表达式为例：

```python
c = a + b
```

解释器要做的事情是：

```text
c = a + b
│
├─ 1. 解析左手边（left-hand side）    → 找到 c 这个名字
├─ 2. 解析右手边（right-hand side）   → 查出 a 的值、b 的值
├─ 3. 判定 + 这个符号代表哪种运算     → 整数加？字符串拼接？
└─ 4. 执行对应的逻辑                  → 真正的一次加法

以上每一步都是 C 代码
```

于是核心问题变成：

> 如果 Python 这门语言支持并发，那么**解释这个脚本的那段 C 代码**是不是也必须能并发运行？

答案取决于解释器采取的方案。

官方 Python 解释器选择了最直白的那一种：**每创建一个 Python 线程，解释器就在它的 C 代码里创建一个对应的操作系统线程。**

```text
Python 脚本层                   解释器（C）层
┌──────────────┐               ┌────────────────────┐
│ threading.   │               │  OS thread #1      │
│   Thread() ──┼──────────────►│  跑解释器例程       │
├──────────────┤               ├────────────────────┤
│ threading.   │               │  OS thread #2      │
│   Thread() ──┼──────────────►│  跑解释器例程       │
└──────────────┘               └────────────────────┘
                                        │
                                        └─► 共享解释器的全部内部状态
```

听起来简单，但代价严重：**如果解释器自己并发运行，它的内部机制就要在多个线程之间共享。**

注意这里的要害：竞态条件影响的不是 Python 脚本，而是**解释这个脚本的那段 C 代码**。

而解释器一旦行为失常，它正在运行的脚本几乎必然跟着失常。

## 5. 具体例子：解释器内部的哈希表被写坏

假设解释器用一个哈希表（hash map）来存放已声明变量的值。

运行脚本时，每创建一个变量，它在解释器内部会被表示成一个自定义结构体，然后插入这个哈希表。

之后需要用到这个变量时，解释器再去哈希表里查出它的值。

现在想象两个 Python 线程并发运行，而这个哈希表**没有任何保护**：

```text
无锁时：两个解释器线程同时找「下一个空槽」

           哈希表
        ┌──────────┐
slot 0  │  x = 1   │
slot 1  │  y = 2   │
slot 2  │  (空)    │◄──┬── C thread #1 认为：下一个空槽是 slot 2
slot 3  │  (空)    │   └── C thread #2 认为：下一个空槽是 slot 2
        └──────────┘

两个线程都往 slot 2 写：

slot 2  │  b = 20  │   ← 后写的 b 覆盖了先写的 a

Python 那边创建了两个变量，解释器只记下了一个
```

从每个解释器线程各自的视角看，哈希表里「下一个可用的槽位」是同一个。

结果是执行这两段脚本的 C 代码把两个变量插到了同一个位置。

Python 脚本创建了两个变量，但解释器实际只记录下了其中一个。

后面如果访问那个被覆盖掉的变量，解释器会去哈希表里找、找不到，然后报错，类似 `变量未声明`，**哪怕脚本前面明明正确声明过它**。

如果这个数据结构被 mutex 保护起来，情况就完全不同：

```text
有锁时：串行化访问

C thread #1  ── 取锁 ──► 看到下一个空槽 = slot 2 ──► 写入 a ──► 放锁
                                                                 │
C thread #2  ────────── 等待 ──────────────────────────► 取锁 ───┘
                        ──► 看到**更新后**的状态，下一个空槽 = slot 3
                        ──► 写入 b ──► 放锁

           哈希表
slot 2  │  a = 10  │
slot 3  │  b = 20  │   两个都在
```

每次解释一行 Python 代码、需要访问哈希表时，这个机制都保证解释器内部同一时刻只有一个线程能碰这张表。

这个例子要说明的是：**如果解释器想用「并发」来提供并发，那么所有数据结构、集合、以及任何可能出现竞态条件的组件，都必须被保护起来。**

## 6. GIL：一把大锁替代成千上万把小锁

于是就到了主问题的答案。

官方 Python 解释器没有为每一个敏感组件配一把专用 mutex，而是**用一把全局互斥锁保护整个解释器核心**，也就是执行 Python 代码的那部分。

这就是 **全局解释器锁（global interpreter lock，GIL）**。

```text
方案 A：细粒度锁（没被采用）      方案 B：一把全局大锁（GIL，被采用）
────────────────────────         ──────────────────────────────
哈希表      → mutex_1            ┌──────────────────────────┐
引用计数    → mutex_2            │                          │
对象池      → mutex_3            │    整 个 解 释 器 核 心   │  🔑 GIL
内置类型    → mutex_4            │                          │
垃圾回收    → mutex_5            └──────────────────────────┘
导入系统    → mutex_6                      一把锁
... 还有几百处                             改动极小
────────────────────────         ──────────────────────────────
可并行，但要重写整个解释器        不可并行，但几乎不用改代码
还要处理死锁、锁顺序等一堆问题
```

所以真实的执行图景是这样的：

```text
每个 Python 线程 → 一个真正的 OS 线程（这部分是真的）

OS thread #1 ──┐
OS thread #2 ──┤
OS thread #3 ──┼──► 想执行 Python 代码？先拿 GIL
OS thread #4 ──┘
                    ┌──── 只有一把 ────┐
                    │      🔑 GIL      │
                    └──────────────────┘
                             │
                 同一时刻只有一个线程能解释 Python 代码

core 0 │ T1 │ T2 │ T3 │ T4 │ T1 │ T2 │   ← 线程在核心之间被调度
core 1 │    等待 GIL，空转/阻塞          │
core 2 │    等待 GIL                     │
core 3 │    等待 GIL                     │
```

每次 spawn 一个 Python 线程，解释器确实创建了一个真正的操作系统线程。

但因为整个解释器被这**唯一一把锁**保护着，任何线程想执行 Python 代码都得先拿到它。

锁只有一把，所以同一时刻只有一个线程在解释 Python 代码。

结果：**Python 线程无法并行**。

这就是开头那张资源监视器截图的全部原因。

### 这是 CPython 的限制，不是 Python 的限制

关键区分：这个限制并非 Python 这门语言固有的，而是属于它的官方解释器 **CPython**。

要证明这一点，可以换一个 Python 解释器来跑同一份代码。

作者演示了一个**用 Rust 写的 Python 实现**，跑开头那个同样的程序，它**确实能吃满多个核心**。

```text
同一份 .py 文件

├─ CPython（C 实现，有 GIL）      → 卡在一个核的量
└─ Rust 实现的 Python（无 GIL）   → 随核心数扩展
```

语言没变，变的只是执行它的那个程序。

## 7. 当初为什么要这么设计

短答案是：**简单**。

视频里直接引用了 Python 之父 Guido van Rossum 的说法。

> 全局解释器锁解决的问题是：Python 最初完全不是按照异步或并行来设计的。
> 语言里没有并发，没有并行，也没有线程。

时间线是这样的：

```text
1991  Python 发布
      │  当时线程还不流行，语言里压根没有线程的概念
      │
1990s 中  所有主流操作系统突然开始提供线程 API
      │  Guido 觉得 Python 支持这个新特性会很棒
      │  动机：让开发者写并发程序，而不必去面对 C 的复杂度
      │
      ├─ 遇到岔路口：
      │    A. 给解释器里每一个内部数据结构配一把 mutex
      │       → 解释器里全是共享状态，全部改成线程安全
      │       → 代码库复杂度会暴涨，等于重写整个解释器和运行时
      │    B. 一把 GIL 罩住整个解释器核心
      │       → 几乎不用改现有逻辑，解释器立刻是安全的
      │       → 代价：没有并行
      │
      │  当时的判断依据：1990 年代中期多核 CPU 极其罕见，
      │  光是并发本身，Python 开发者就已经很受用了
      │  （交替够快，响应时间就变好）
      │
      └─► 选 B
      │
2000s 中  芯片厂商开始量产多核 CPU
      │  原因：没法再把 CPU 做得更快，但可以做得更小，
      │        于是把多个 CPU 塞进一块芯片
      │  「并行」的压力一夜之间出现
      │  十年前的那个决定，变成了一个大限制
      │
      └─► GIL 从此声名狼藉
      │
2020s  30 多年后，移除 GIL 的工作终于启动
       Python 将终于能够真正并行地运行线程
```

Guido 本人的几段原话，构成了这个决定的完整辩护与反思：

> 当时我们并不想为了线程安全去重写解释器，因为那会是对全部解释器代码和运行时代码的一次极其复杂的重构。

> 随着 C 的多线程库出现，我们想 - 也许我们想错了 - 但在当时，我们想尽快支持这些多线程，因为在 90 年代初它们是新东西，至少对我来说，它们看起来是一种很酷、很有意思的编程范式。

> 我们当时以为自己已经把线程这个抽象搞定了，毕竟多核 CPU 那时并不在大多数 Python 程序员手上。

> 芯片设计者们发现他们没法让 CPU 更快了，但可以让它更小，于是就能把多个 CPU 放在一块芯片上。突然之间，到处都是「并行地做事」的压力，而这正是 Python 当时那套方案失效的地方。那差不多就是 GIL 开始变得声名狼藉的时刻。

一个重要的事实：即使线程不并行，**这种快速交替的并发模式在很多场景下依然有用**。

因为只要切换得足够快，响应时间就会改善。

所以 GIL 方案在最初的近 10 年里，是够用的。

## 8. 核心总结

```text
为什么 Python 线程不并行
│
├── 表层现象
│   └── 开满核心数的线程，总 CPU 仍只有 ≈ 100%，而 C 是 ≈ 核数 × 100%
│
├── 概念前提
│   ├── 线程 ≠ 并行；开线程只是「告诉 OS 这几段代码可以并发，有条件的话再并行」
│   ├── 并发 = 交替，单核即可，是幻觉
│   └── 并行 = 分核，真同时，是并发的子集
│
├── 真正的原因链
│   ├── 1. CPU 看不懂 Python，跑的其实是「解释 Python 的 C 程序」
│   ├── 2. 一个 Python 线程 = 一个真正的 OS 线程
│   ├── 3. 于是解释器自身的 C 代码在并发运行，共享全部内部状态
│   ├── 4. 竞态条件伤的是解释器，不是脚本
│   │      （哈希表槽位冲突 → 变量被覆盖 → 「变量未声明」报错）
│   ├── 5. 修法只有两条：给每个敏感组件配一把小锁，或一把大锁罩住全部
│   └── 6. CPython 选了大锁 = GIL → 同一时刻只有一个线程能解释 Python
│
├── 责任归属
│   ├── 限制属于 CPython，不属于 Python 语言
│   └── 换成 Rust 写的 Python 实现，同一份代码就能吃满多核
│
└── 历史账
    ├── 1991 发布时语言里没有线程
    ├── 1990s 中 OS 普遍提供线程 API，Guido 想低成本支持它
    ├── 重写解释器做到线程安全太贵 → 选 GIL
    ├── 当时多核 CPU 罕见，光有并发已经够用，所以这个选择近 10 年都没问题
    ├── 2000s 中多核普及，旧决定变成硬伤，GIL 开始声名狼藉
    └── 30 多年后的今天，移除 GIL 的进程终于开始
```

> GIL 从来不是 Python 为了限制你而加的东西，而是 1990 年代中期一次「用一把锁换掉一次全解释器重构」的成本权衡。
> 在多核 CPU 还罕见的年代，这笔交易是划算的：Python 白拿到了线程 API 和并发，代价是一个当时几乎没人用得上的并行能力。
> 真正的教训不是「GIL 是个错误」，而是**为当下硬件做出的正确决定，会被十年后的硬件变成债**，而这笔债，Python 还了三十年才开始还。
