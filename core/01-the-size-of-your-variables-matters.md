# 变量的大小为什么重要（Fixed-Size Types）

> 视频来源：Core Dumped -《The size of your variables matters.》

## 0. 这一系列在讲什么

从 JavaScript、Python 这类脚本语言转向系统级编程时，会突然撞上一大堆陌生概念：

```text
栈（stack）        堆（heap）
指针（pointer）     系统调用（syscall）
局部性（locality）  并发（concurrency）
并行（parallelism）
```

很多人学 Rust 失败，并不是因为 Rust 的语法难，而是因为「借用检查器到底在替我挡什么坑」这件事没搞明白。
官方的 The Book 讲的是 Rust 本身，不会展开这些属于系统编程通识的底层概念。

所以这一系列笔记不是 Rust 教程，而是补齐底层概念，让你理解并认同这些语言的设计决策。

本篇的主题是系统级语言最基础的一个特征：**固定大小类型（fixed-size types）**。

---

## 1. 问题：为什么数字类型有这么多种

从 Python / JavaScript 转到 C 或 Rust，最先注意到的就是：

* 不写类型（或者不能推导出类型）就不让你声明变量；
* 数字不是只有一个 `number`，而是分成一大堆。

对比一下：

```javascript
// JavaScript：所有数字都是 number
let age = 25;
let price = 19.99;
```

```rust
// Rust：整数和浮点各自还要再分
let age: u8 = 25;
let price: f64 = 19.99;
```

Rust 里数字类型大致是这样一张表：

| 类别 | 类型 | 占用 |
| --- | --- | --- |
| 无符号整数 | `u8` `u16` `u32` `u64` `u128` | 1 / 2 / 4 / 8 / 16 字节 |
| 有符号整数 | `i8` `i16` `i32` `i64` `i128` | 1 / 2 / 4 / 8 / 16 字节 |
| 浮点数 | `f32` `f64` | 4 / 8 字节 |

一句话回答「为什么」：

> 系统级语言允许你精确指定：用多少内存空间来表示你的数据。

---

## 2. 前置知识：位、组合与表示范围

计算机里所有信息都是一串二进制位（bit），每一位只能是 `0` 或 `1`。

二进制表示数据的思路是：**枚举这串位的所有可能组合，再把每种组合和一个具体的值对应起来。**

### 2 位序列

```text
2 位 → 2^2 = 4 种组合

  00  →  0
  01  →  1
  10  →  2
  11  →  3

  4   →  ✗ 组合用完了，表示不出来
```

### 加一位：3 位序列

```text
3 位 → 2^3 = 8 种组合

  000 → 0        100 → 4
  001 → 1        101 → 5
  010 → 2        110 → 6
  011 → 3        111 → 7
```

如果还不够，就继续加位，直到组合数足够覆盖你想表示的值域。

### 关键规律

因为每一位只有两种取值，所以**每增加一位，可表示的范围就翻一倍**。

```text
位数：  1     2     3     4    ...    8      16       32          64
组合：  2     4     8    16    ...   256   65536   ~42.9 亿   ~1.84 × 10^19
       └──┘  └──┘  └──┘  └──┘        └──┘   └───┘    └────┘      └───────┘
        ×2    ×2    ×2    ×2          每加一位翻一倍
```

| 位数 | 组合数 | 无符号范围 |
| --- | --- | --- |
| 8 | 256 | `0 ..= 255` |
| 16 | 65,536 | `0 ..= 65,535` |
| 32 | 4,294,967,296 | `0 ..= 4,294,967,295` |
| 64 | 18,446,744,073,709,551,616 | `0 ..= 18,446,744,073,709,551,615` |

## 3. 为什么是 8、16、32、64

程序运行时，所有变量都要占用内存，而**内存是有限的**。

这些类型存在的意义，就是给你一种「超能力」：明确、精确地告诉编译器，你需要多少内存来表示程序要用的信息。

不过出于效率和实现上的方便，计算机并不直接以单个位为单位操作，而是以 **8 位为一组，称为一个字节（byte）**。

```text
1 byte = 8 bits

┌───┬───┬───┬───┬───┬───┬───┬───┐
│ 0 │ 0 │ 0 │ 1 │ 1 │ 0 │ 0 │ 1 │  = 25
└───┴───┴───┴───┴───┴───┴───┴───┘
 128  64  32  16   8   4   2   1
```

这带来两个结论：

1. 能用来表示数据的最小位数是 **8**，而不是 1；
2. 所以你常见到的是 8 / 16 / 32 / 64 位的数字，而**不会**看到 3 位或 47 位这种奇怪宽度的类型。

## 4. 实例：存一个人的年龄

### 用 `u64`（8 字节）

```rust
let age: u64 = 25;
```

内存里长这样：

```text
                       age: u64  =  25
 byte7    byte6    byte5    byte4    byte3    byte2    byte1    byte0
┌────────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┐
│00000000│00000000│00000000│00000000│00000000│00000000│00000000│00011001│
└────────┴────────┴────────┴────────┴────────┴────────┴────────┴────────┘
└──────────────── 7 个字节永远都是 0 ────────────────┘ └─ 真正用到的 1 字节 ─┘
                        （纯浪费）
```

64 位远远超出需求，因为年龄极少超过 100。

### 用 `u8`（1 字节）

一个字节能表示 256 种值（`0 ..= 255`），年龄永远碰不到 255 这个上限。

```rust
let age: u8 = 25;
```

```text
     age: u8 = 25
   ┌────────┐
   │00011001│      1 字节，范围 0 ..= 255，刚好够用
   └────────┘
```

### 规模一放大，差距就出来了

单个变量浪费 7 个字节，听起来无所谓，毕竟现在的机器动辄几十 GB 内存。
但如果你要处理成千上万个年龄呢？

```text
10,000 条年龄记录

  u64:  10,000 × 8 字节 = 80,000 字节  ≈ 78 KB
  u8 :  10,000 × 1 字节 = 10,000 字节  ≈ 9.8 KB
        ─────────────────────────────────────────
        白白浪费          70,000 字节  ≈ 68 KB（87.5%）
```

在脚本语言里，这件事完全不由你决定：

```text
脚本语言：
   你声明变量
        ↓
   解释器决定「放在哪里」「占多大」
        ↓
   结果：几乎总是比实际需要多用很多内存
```

## 5. 附带的好处：有符号 / 无符号的语义

Rust 的类型系统还让你表达「这个数能不能是负数」。

年龄不可能是负数，所以用无符号类型，相当于让编译器帮你拒绝一切可能赋负值的代码：

```rust
let age: u8 = 25;

let delta: i32 = -5;
// age = delta;        // ✗ 编译错误：类型不匹配，负值进不来
```

```text
u8  →  0 ..= 255          （无符号，天然排除负数）
i8  →  -128 ..= 127       （有符号，最高位表示符号）
```

这不是运行时检查，而是**编译期就把非法状态挡在门外**。

---

## 6. 另一个好处：强制显式，避免踩坑

看这段 JavaScript，光看代码你能回答吗：

```javascript
let a = 10;      // 整数
let b = 3.5;     // 浮点数
let c = a + b;   // c 是整数还是浮点数？
                 // 解释器会先把 3.5 取整再算，还是把 10 转成浮点再算？
```

如果你 JS 写得多，可能确实知道答案，这很好。
**不好的地方在于**：你的答案来自经验，或者藏在互联网某个角落的文档里，而**不是来自这段代码本身提供的任何信息**。

Rust 里这段代码根本写不出来：

```rust
let a: i32 = 10;
let b: f64 = 3.5;

// let c = a + b;          // ✗ 编译错误：i32 和 f64 不能直接相加

let c = a as f64 + b;      // ✓ 你必须显式说清楚你想干什么
```

代价是多写几个字，收益是**意图写在代码里，而不是留在读者的记忆里**。

## 7. 性能：动态类型的隐藏成本

### 解释器怎么知道一段位是什么

内存里一切都是位。
解释器把内存分配给变量之后，等到后面要用这些变量时，它怎么知道这堆位代表什么？

```text
   01001000 01101001
   
   这是数字？是字符串？还是别的什么？
   光看位，无从判断。
```

解决办法有多种，最简单的一种是：**给每个值额外附加一份类型信息（type tag）**。

```text
动态语言中一个值的概念示意

┌──────────────┬────────────────────────┐
│   类型标签    │          数据          │
│   "number"   │        00101010        │
└──────────────┴────────────────────────┘
   额外开销              真正的数据
```

于是运算时，解释器先读标签，再决定该做什么：

```text
        a + b
          │
          ├─ 标签是 number  →  执行数值加法
          │
          └─ 标签是 string  →  执行字符串拼接
```

### 好处：运行时能报错

一个像样的动态类型系统还能利用这份信息在运行时抓错：

```python
>>> 1 + "2"
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

而某些「非常糟糕的语言」不会告诉你任何事，只会悄悄把其中一个值隐式转换，然后硬算出一个结果：

```javascript
1 + "2"        // "12"      数字被转成了字符串
1 - "2"        // -1        字符串被转成了数字
[] + {}        // "[object Object]"
```

这种「只能用未定义行为来描述」的东西，甚至被当成特性。

### 成本一：额外的内存

这些标签不是凭空存在的，它们要占内存。
示意图里为了省地方把标签画成 1 个字节，**现实中往往要好几个字节**。

```text
        u8 in Rust                动态语言中的一个小整数
      ┌────────┐              ┌──────────────┬────────┐
      │00011001│              │  tag（数字节）│00011001│
      └────────┘              └──────────────┴────────┘
        1 字节                     远大于 1 字节
```

结论：你不但**失去了对变量大小的控制**，解释器还要**额外**为每个变量再花一份内存。

### 成本二：运算开销（更要命）

这种做法给最简单的算术运算也套上了一层不小的开销：

```text
      c = a + b   （动态类型）
        │
        ├─ 标签必须被初始化   →  花时间
        ├─ 标签必须被读取     →  花时间
        ├─ 标签必须被比较     →  花时间
        ├─ 分派到具体实现（加法 / 拼接 / 抛错）
        ├─ 执行真正的运算     ←  这一步才是你的代码
        └─ 结果的标签必须被写入（运行时）→  花时间
```

所有这些活儿都要吃 CPU 时间。
也就是说，**大部分时间解释器在跑那些额外步骤，而不是在跑你的代码。**

### 静态类型 + 固定大小：编译器能生成高效机器码

当你被要求写清类型和大小时，编译器就能把这份信息直接用于代码生成：

```rust
let a: i32 = 10;
let b: i32 = 20;
let c = a + b;
```

编译器知道这两个变量在运行时是内存里的 32 位数字，于是直接发出：

```text
   mov  eax, [a]     ; 取出 a
   add  eax, [b]     ; 加上 b
   mov  [c], eax     ; 结果存进 c
   
   就这样。没有额外内存，没有额外校验。
```

因为你在**编译期**就把信息给足了。

```text
动态类型                          静态类型
─────────────────────            ─────────────────────
tag 初始化                        （无）
tag 读取 × 2                      （无）
tag 比较                          （无）
类型分派                          （无）
实际运算                          实际运算
tag 写入                          （无）
额外内存                          （无）
```

这就是静态类型语言通常比动态类型语言快上一个甚至几个数量级的主要原因之一。
注意：这一点**不只适用于系统级语言**，任何静态类型语言都能吃到这份收益。

## 8. 推广到复合类型

既然基本类型的大小在编译期已知，那么由它们组成的复杂类型，大小自然也在编译期已知。

```rust
struct Person {
    age: u8,      // 1 字节
    height: u16,  // 2 字节
    id: u32,      // 4 字节
}
```

```text
Person 的内存布局（不考虑对齐填充时）

┌────┬─────────┬───────────────────┐
│age │ height  │        id         │
└────┴─────────┴───────────────────┘
  1B      2B            4B          →  合计已知
```

所以前面讲的一切，同样适用于你自定义的数据类型。

### 但不是所有东西都能固定大小

考虑这种情况：

```rust
struct Data {
    values: [u8],     // ✗ 编译错误：数组长度未知，Data 的大小无法确定
}
```

解决办法之一是把长度写死：

```rust
struct Data {
    values: [u8; 2],  // ✓ 固定 2 个元素
}
```

代价是：每次初始化这种变量，都必须**不多不少提供恰好那么多个元素**。

```rust
let d = Data { values: [1, 2] };       // ✓
// let d = Data { values: [1, 2, 3] }; // ✗ 编译器报错
// let d = Data { values: [1] };       // ✗ 编译器报错
```

### 长度在编译期未知怎么办

有些场景下你根本不知道数组会有多长，或者你**就是想让它在运行时增减**。

解决办法：把数据放进一块**可以动态增长和收缩的特殊内存区域**，而你的类型本身不直接持有数组，只持有：

* 指向那块内存的**引用（指针）**；
* 加上一些附加信息，比如**长度**，这样才知道那块区域到底有多大。

```text
固定大小的部分                  大小可变的部分
（你的类型持有的东西）            （真正的数据）

┌───────────────────┐          ┌────┬────┬────┬────┬────┐
│ ptr   ────────────┼─────────►│  1 │  2 │  3 │  4 │  5 │
├───────────────────┤          └────┴────┴────┴────┴────┘
│ len   = 5         │           可以在运行时变长 / 变短
├───────────────────┤
│ cap   = 8         │
└───────────────────┘
     大小固定：
   指针 + 两个整数
```

对应到 Rust 里就是 `Vec<T>`、`String` 这类类型：

```rust
let mut v: Vec<u8> = Vec::new();
v.push(1);
v.push(2);   // 运行时增长，Vec 本身在栈上的大小始终不变
```

> 至于「为什么会有这个限制」，超出本视频范围。

## 10. 核心总结

```text
为什么变量大小重要
│
├── 空间
│   ├── N 位 → 2^N 种组合，每加一位范围翻倍
│   ├── 最小单位是字节（8 位），所以只有 8/16/32/64
│   ├── u64 存年龄 → 7/8 的空间永远为 0，纯浪费
│   └── 规模一大，浪费按倍数放大
│
├── 正确性 / 表达力
│   ├── 无符号类型 → 编译期排除负值
│   └── 禁止隐式混算 → 意图写在代码里，不靠经验和文档
│
├── 性能
│   ├── 动态类型：值要带类型标签
│   │   ├── 标签占额外内存（现实中好几个字节）
│   │   └── 标签的初始化/读取/比较/写入都吃 CPU 时间
│   └── 静态类型：编译器直接发出 取值 → 相加 → 存回
│       └── 无额外内存，无额外校验
│
└── 推广
    ├── 基本类型大小已知 → 复合类型大小也已知
    ├── [u8] 大小未知 → 编译错误；[u8; 2] 固定长度 → 可以
    └── 长度运行时才定 → 存「指针 + 长度 + 容量」，数据放可增长的内存区
```

一句话：

> 类型不只是给编译器看的标注，它是你对「这份数据在内存里占多少、能取哪些值」的显式声明。
> 说清楚了，编译器才能既替你省内存，又替你生成快代码，还顺手挡掉一批错误。
