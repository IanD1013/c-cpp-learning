# 处理器是怎么执行条件判断和循环的

> 视频来源：Core Dumped -《How computer processors run conditions and loops》
> https://www.youtube.com/watch?v=Ui6QyzcD3_E

## 0. 这一期在讲什么

计算机跑程序的方式是「一条条按顺序执行指令」，但这不等于它**永远**严格按顺序执行。

要真正有用，计算机必须能做到两件事：

1. **做决定**：根据情况执行这个分支或那个分支；
2. **重复步骤**：把同一段逻辑跑很多遍。

这一期就是把 `if` 和 `while` 拆到硬件层面，看它们最终变成了什么。

作者说这是这个底层系列的**最后一期**。
所以前半段是对前面内容的回顾（CPU 怎么取指令、怎么执行），后半段才是新东西：**jump、标志位（flags）、条件跳转**。

一个提前给出的结论：所谓「条件」和「循环」，在硬件上根本不是两种机制。
它们是同一件事的两种排列方式，而这件事就是**改写程序计数器**。

## 1. 前置回顾：CPU 是怎么一条条跑指令的

### 1.1 可执行文件里不只有指令

我们写程序用的是编程语言，而计算机看不懂编程语言。
所以才需要**编译器（compiler）**：它把某种语言写的代码翻译成别的东西，通常是一个**可执行文件（executable file）**。

这里有一个常见的误解：**可执行文件就是一串 CPU 指令**。

不对。
它里面还包含程序运行时需要的**数据**。

看视频里那个例子：

```c
a = 20 + 100;
```

`20` 和 `100` 是程序在运行时（runtime）需要的值。
它们不是指令，但程序离了它们跑不起来，所以编译器必须把这两个值也塞进可执行文件里的某个位置。

```text
   可执行文件
 ┌────────────────────────┐
 │  指令区                │  <- 「做什么」
 │    load / add / store  │
 ├────────────────────────┤
 │  数据区                │  <- 「用什么做」
 │    20    100           │
 └────────────────────────┘
```

要运行程序，就把这个可执行文件**装载进内存**，然后 CPU 就可以开始从内存里取指令了。

记住这个前提：处理器连着 RAM，可以从 RAM 读、也可以往 RAM 写，读写的内容**既可能是指令、也可能是数据**。

### 1.2 一条指令要走三个阶段

执行一条指令，要经过三个阶段。

**阶段一：fetch（取指）**

把**地址寄存器（address register）**里的内容送到内存的地址输入端，同时激活**读使能信号（read enable）**。
内存于是把那个位置的内容输出出来，写进 CPU 的**指令寄存器（instruction register）**。

地址寄存器还有个更常见的名字：**程序计数器（program counter，PC）**。

```text
                    ┌───────────────────────────┐
                    │            RAM            │
      address ─────►│  ┌────┬────┬────┬─────┐   │
  read enable ─────►│  │ 0  │ 1  │ 2  │ ... │   │
                    │  └────┴────┴────┴─────┘   │
                    └─────────────┬─────────────┘
                                  │ 输出该地址的内容
   ┌──────────────────────────────▼──────────────┐
   │ CPU                                         │
   │  ┌───────────────┐      ┌────────────────┐  │
   │  │ address reg   │      │ instruction    │  │
   │  │ (程序计数器)  │      │   register     │  │
   │  └───────┬───────┘      └────────┬───────┘  │
   │          │                       │          │
   │          │  +1            读取   ▼          │
   │          │              ┌─────────────────┐ │
   │          └──────────────│  control unit   │ │
   │                         └─────────────────┘ │
   └─────────────────────────────────────────────┘
```

**阶段二：decode（解码）**

**控制单元（control unit）**读取指令寄存器里的内容，解释这条指令，也就是搞清楚「CPU 下一步该做什么动作」。

**阶段三：execute（执行）**

指令解码完，控制单元把一切线路都配置好，让这条指令真正被执行。
在这个例子里，它把内存位置 5 的内容（也就是数字 20）加载进寄存器 0。

**收尾：PC 递增**

指令执行完之后，控制单元把地址寄存器的值**加一**。
这样当 CPU 回到 fetch 阶段时，取到的就是刚才那条指令**紧接着的下一条**。

```text
 ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
 │  fetch   │──►│  decode  │──►│ execute  │──►│  PC + 1  │
 │  取指令  │   │   解码   │   │   执行   │   │  地址+1  │
 └──────────┘   └──────────┘   └──────────┘   └────┬─────┘
      ▲                                            │
      └────────────────────────────────────────────┘
```

**这个「PC + 1」就是整期视频的关键。**
顺序执行不是什么天然规律，它只是控制单元每次都老老实实给 PC 加了个 1。
后面要讲的 jump，做的事情就是把这个「加一」换成「覆盖」。

## 2. 手工编译一个最小程序

源码就一行：

```c
a = 20 + 100;
```

这个程序需要四条指令。

**第一条**：从内存位置 5 取出 20，放进寄存器 0。
**第二条**：从内存位置 6 取出 100，放进寄存器 1。

**第三条**：算术运算。
解码之后 CPU 知道要做的是：把寄存器 0 和寄存器 1 里当前的值相加，然后**把结果写回存放第一个操作数的那个寄存器**。

这里有个重要的点：**如果没有前面两条 load，`add` 指令是没有意义的。**
ALU 只能对寄存器里的东西动手，所以想加什么，得先把它搬进来。

**第四条**：光算出来不够。
我们不只是想把两个数加起来，我们还想把结果**存进一个变量**。

给变量赋值的意义在于「以后还能用变量名把这个值取回来」，也就是**记住**它。
翻译到底层就是：**结果必须落到内存里**，这样以后需要时才能再读出来。

`store` 指令干的就是这件事：让寄存器把值送到内存，指定一个地址，然后激活**写使能信号（write enable）**，告诉内存「这次是要往这个位置写，不是读」。

**外加一条**：程序到这里逻辑上就结束了，但 CPU **分不清指令和数据**。
如果不管它，PC 会继续加一，把后面的数据当成指令去执行。

所以末尾要加一条 `halt`，让 CPU 停下来。

```text
 地址   指令                      作用
 ─────  ────────────────────────  ──────────────────────────
   0    LOAD   reg0, [5]          reg0 = 20
   1    LOAD   reg1, [6]          reg1 = 100
   2    ADD    reg0, reg1         reg0 = reg0 + reg1 = 120
   3    STORE  [7], reg0          a = 120（写回内存）
   4    HALT                      停机，别把数据当指令

 数据   位置 5 = 20   位置 6 = 100   位置 7 = a
```

一句话概括这一整套机制：

```text
   内存 ──► CPU ──► 加工 ──► 内存
     取数据    在寄存器里     存回结果
               操作它
              （一条接一条）
```

## 3. 加一行代码，两个新麻烦

现在改一下程序，加一行：

```c
a = 20 + 100;
b = a + 1;
```

第一行的指令几乎不变，只有**地址**要改，这个稍后说。

第二行也是个加法，所以照套路走：两个操作数都得进寄存器。
第一个操作数是变量 `a` 的值，第二个操作数是数字 `1`，然后做加法，然后存结果。

朴素版本：

```text
   LOAD   reg0, [addr_20]
   LOAD   reg1, [addr_100]
   ADD    reg0, reg1
   STORE  [addr_a], reg0
   LOAD   reg0, [addr_a]     <- 把 a 读回来
   LOAD   reg1, [addr_1]     <- 把常量 1 读进来
   ADD    reg0, reg1
   STORE  [addr_b], reg0
   HALT
```

这样写是**对的**，但可以优化。

### 3.1 优化一：用 increment 指令

这个架构里有一条特殊指令，可以**直接把寄存器里的值加一**，不需要先把数字 1 加载到另一个寄存器。

于是 `LOAD reg1, [addr_1]` 整条没了，连内存里那个常量 `1` 都不用存了。

### 3.2 优化二：寄存器里的值还在

做前一次加法时，变量 `a` 的值被写回了寄存器 0。
从那之后我们**没有往这个寄存器里装过别的东西**，所以 `a` 的值还在里面。

那条 `LOAD reg0, [addr_a]` 就是多余的。

优化后：

```text
 地址   指令                   作用
 ─────  ─────────────────────  ─────────────────────────────
   0    LOAD   reg0, [15]      reg0 = 20
   1    LOAD   reg1, [14]      reg1 = 100
   2    ADD    reg0, reg1      reg0 = 120
   3    STORE  [13], reg0      a = 120
   4    INC    reg0            reg0 = 121   <- 省掉一次 LOAD
   5    STORE  [12], reg0      b = 121      <- 省掉一次 LOAD
   6    HALT
```

指令数从 9 条降到 7 条。

作者说，这类**减少指令条数的小聪明多得是，编译器一直在干这种事**。
他还提到考虑单独做一期讲基本的编译器优化，属于后续话题，超出本期范围。

### 3.3 麻烦：地址会漂

前面说「第一行的指令几乎不变，只有地址要改」，就是这个问题。

前两条 `LOAD` 要读的是数据，可是我们在中间**插入了更多指令**，`20` 和 `100` 已经不在原来的内存位置上了。
所以必须把地址改对。

`store` 指令也一样，变量的位置也漂了。

```text
   加代码之前                    加代码之后
 ┌────┬──────────┐             ┌────┬──────────┐
 │ 0  │ 指令     │             │ 0  │ 指令     │
 │ .. │ ...      │             │ .. │ ...      │
 │ 4  │ HALT     │             │ 6  │ HALT     │  <- 指令区变长了
 │ 5  │ 20       │             │ .. │          │
 │ 6  │ 100      │             │ 13 │ a        │  <- 数据全被挤走
 │ 7  │ a        │             │ 14 │ 100      │
 └────┴──────────┘             │ 15 │ 20       │
                               └────┴──────────┘
```

**一个老但好用的技巧：指令放在内存开头，数据放在内存末尾。**

这样指令区往后长、数据区往前长，两边各自增长时不会一上来就互相踩到。

本期这个架构非常受限，**只有 16 个 RAM 位置**（0 到 15），所以程序最终长这样：

```text
  位置   内容
 ──────  ────────────────────────────
   0     LOAD   reg0, [15]
   1     LOAD   reg1, [14]
   2     ADD    reg0, reg1
   3     STORE  [13], reg0
   4     INC    reg0
   5     STORE  [12], reg0
   6     HALT
   ...   （空闲）
   12    b            ┐
   13    a            │ 数据从末尾往前排
   14    100          │
   15    20           ┘
```

现代架构处理这个问题的方式各有不同，超出本期范围。

但要记住：**真实硬件里这一切仍然只是 1 和 0。**

## 4. 顺序执行的天花板

到这里，计算机跑程序的**基本原理**已经完整了：
把数据从内存搬到 CPU，用某种方式加工它，再把结果存回内存，一条指令接一条指令。

这个模型看起来很合理，因为我们写程序的时候，即使用的是高级语言，也确实是**一行一行**写的。

但我们还没考虑**条件**和**循环**。

「根据情况做这个或做那个」、「把步骤重复若干遍」这两种能力，比很多人以为的要关键得多。
事实上，**没有这两个特性，计算机能干的事会极其有限。**

作者说图灵完备性（Turing completeness）会另开一期讲，超出本期范围。

## 5. jump：无条件跳转

先从最简单的开始，手工编译一个**无限循环**：

```c
a = 0;
while (true) {
    a = a + 1;
}
```

**第一行**：把 0 加载到寄存器，再复制到变量 `a` 所在的内存位置。

**循环体里那行**：需要做加法。
但变量 `a` 的最新值已经在寄存器 0 里了，不用再 load 一次，所以直接用 increment 加一。

而且我们不只是在做加法，我们还要**用加法结果更新变量 `a`**，所以后面必须跟一条 `store`。

**关键的一步**：我们需要这个过程**无限重复**下去。

这就是 `jump` 指令登场的地方。

这条指令带一个内存地址作为参数。
如它的名字所示，它唯一的作用就是**让程序跳到那个位置**。

```text
  位置   指令                    说明
 ──────  ──────────────────────  ────────────────────────────
   0     LOAD   reg0, [15]       reg0 = 0
   1     STORE  [14], reg0       a = 0
   ┌──►
   2  │  INC    reg0             a + 1
   3  │  STORE  [14], reg0       写回 a
   4  └─ JUMP   2                跳回位置 2
   5     HALT                    永远到不了

  数据：位置 14 = a    位置 15 = 常量 0
```

因为它跳到的是**前面**的一条指令，程序跑一会儿又会撞上这条 `jump`，于是就一直转下去。

`halt` 当然还在那儿，但它**永远不会被执行到**，因为 `jump` 每次都把程序拽回前一步。

### 5.1 jump 的内部实现：它根本不是「跳」

如果好奇它内部怎么工作的，答案其实特别简单。

「跳转」只是我们给这条指令**执行效果**起的名字。
它真正做的事是：**告诉控制单元用给定的值去覆盖地址寄存器的内容。**

所以它跟 `load` 指令很像，只不过写的目标是**地址寄存器**，而不是通用寄存器。

```text
   普通指令执行完                jump 指令执行时
 ────────────────────────      ────────────────────────────
   PC = PC + 1                   PC = 指令里带的那个地址
   （控制单元做递增）             （控制单元做覆盖写）

   下次 fetch 拿到              下次 fetch 拿到的
   紧邻的下一条                  就不是下一条了
                                 ==> 在我们看来就像「跳」了
```

这么一来，CPU 取到的指令不再是序列里的下一条，在我们看起来就好像它「跳」了一下。

**这就是无限循环在硬件层面的实现方式。** 全部。

## 6. 标志位（flags）：ALU 的额外情报

`jump` 很酷，但它有个硬伤：**它总是跳。**

那如果我们只想在**满足某个条件时**才跳呢？

回答这个问题之前，得先讲**标志位（flags）**。

跑一个简单程序：把一个数减去它自己。

```c
a = 12 - 12;
```

```text
   LOAD   reg0, [x]      reg0 = 12
   SUB    reg0, reg0     reg0 = 12 - 12
   STORE  [y], reg0      存结果
   HALT
```

结果显然是 0，没什么新鲜的。
但运行时会注意到界面上多了几个**小方块**。

那些小方块是**只有 1 个 bit 的寄存器**，叫做标志位。

**每次 ALU 做一次运算，它输出的不只是结果，还附带一些关于这个结果的额外信息。**

```text
              ALU
        ┌──────────────┐
   a ──►│              │
        │   a - b      │───► 结果 ──► 寄存器 / 内存
   b ──►│              │
        └──┬────┬───┬──┘
           │    │   │
           ▼    ▼   ▼
          [O]  [Z] [N]      <- 三个 1 bit 寄存器（flags）
           │    │   │
           │    │   └── negative：结果是负数
           │    └────── zero：结果是 0
           └─────────── overflow：结果放不下了
```

| 标志位 | 置 1 的含义 | 视频里的触发例子 |
| --- | --- | --- |
| overflow | 结果溢出，放不进目标宽度 | 无限循环里 `a` 到 255 再加一 |
| zero | 结果是 0 | `12 - 12` |
| negative | 结果是负数 | 小数减大数 |

### 6.1 三个例子

**zero 标志**：上面 `12 - 12` 的结果是 0，ALU 就是在通知我们这件事。

**overflow 标志**：如果去跑第 5 节那个无限循环程序，会发现当变量 `a` 涨到 **255** 时，再加一就会点亮 overflow 标志。

对不熟悉的人补充一句原因：256 对应的二进制序列已经**放不进一个字节（byte）**了。

```text
    a = 255                      a = 255 + 1 = 256
  ┌──────────┐                 ┌───┬──────────┐
  │ 11111111 │  <- 8 bit 满了  │ 1 │ 00000000 │
  └──────────┘                 └───┴──────────┘
                                 └─ 第 9 位，一个字节装不下
                                    ==> overflow 置 1
```

**negative 标志**：用小的数减大的数，结果是负数，negative 标志就来通知我们。

### 6.2 ALU 为什么要多管这个闲事

原因很简单：**这样我们的程序才能拿这些信息去做决定。**

标志位就是「条件判断」这件事在硬件上的物理载体。

## 7. 条件跳转（conditional jumps）

有了标志位，就可以介绍**条件跳转**了。

这类指令的工作方式是：**跳到指定地址，但只在跟标志位状态相关的某些条件被满足时才跳。**

作者说这是他能给出的最一般的解释，并建议花点时间把那一页指令表看清楚，因为后面的例子都要用。

```text
   JUMP        addr     总是跳
   JUMP_NEG    addr     只在 negative 标志为 1 时跳
   JUMP_ZERO   addr     只在 zero 标志为 1 时跳
   JUMP_ABOVE  addr     只在 zero 和 negative 都为 0 时跳
   ...
```

条件跳转失败时会发生什么？
**什么特别的都不发生**：PC 照常加一，CPU 执行紧跟在它后面的那条指令。

这个「失败就往下走」的行为，正是后面构造分支的全部手段。

## 8. while 循环：把比较变成减法

现在做一个**带条件的 while 循环**，这样它就不会无限跑了：

```c
a = 0;
while (a < 5) {
    a = a + 1;
}
```

第一行照旧：加载一个常量，存到变量所在的地址。

但这次**不能**上来就执行循环体里的代码然后跳回去了，因为现在有个条件要检查。

### 8.1 关键洞察：比较就是减法

想一下：**每当我们想比较两个数，我们真正在做的事其实是减法。**

`a` 和 `5` 的差是第三个数，叫它 `b`。
`b` 只有三种可能：

```text
        b = a - 5

   b < 0   ──►  a 小于 5
   b = 0   ──►  a 等于 5
   b > 0   ──►  a 大于 5
```

所以想检查 `a < 5`，就把这两个数减一下。
**只要这个条件成立，negative 标志就会亮**，我们就能用 `jump negative` 指令捕捉到它。

这就是高级语言里的比较运算符和硬件之间的全部距离：
**一次减法 + 看一眼标志位。**

### 8.2 组装出来的程序

具体做法：把数字 5 加载到另一个寄存器，然后从已经在寄存器 0 里的 `a` 的值里减掉它。

减法之后**紧接着**用一条 `jump negative`，检查结果是否为负；
如果是，就跳到那段「执行循环体」的指令。

而循环体那行代码执行完之后，需要一条 `jump` **跳回减法指令**。

为什么跳回减法而不是跳回循环开头？
因为**每一轮迭代之前都要重新检查条件是否还成立**。

如果减法没有触发 negative 标志，条件跳转就不会发生，CPU 会去执行紧跟在它后面的那条指令。
标志位不亮，正说明循环条件已经不成立了，所以**这个位置正好放一条无条件 jump 来跳出循环**。

循环后面没有别的代码了，所以程序在这里应该停机。

```text
  位置   指令                    对应的高级语言
 ──────  ──────────────────────  ────────────────────────────
   0     LOAD   reg0, [15]       ┐ a = 0
   1     STORE  [13], reg0       ┘
   2     LOAD   reg1, [14]         reg1 = 5（循环外只需一次）
   ┌──►
   3  │  SUB    reg0, reg1       ┐ while (a < 5)
   4  │  JUMP_NEG  6             │   条件成立 -> 进循环体
   5  │  JUMP   10               ┘   条件不成立 -> 跳出
      │
   6  │  LOAD   reg0, [13]       ┐
   7  │  INC    reg0             │ a = a + 1
   8  │  STORE  [13], reg0       ┘
   9  └─ JUMP   3                  跳回去重新判断条件
  10     HALT

  数据：位置 13 = a    位置 14 = 常量 5    位置 15 = 常量 0
```

> 补充一个细节，视频里没有明说但顺着规则能推出来：
> `SUB reg0, reg1` 会**把结果写回第一个操作数所在的寄存器**（第 2 节讲 `add` 时定的规则）。
> 所以减完之后 reg0 里装的是 `a - 5`，**`a` 本身被冲掉了**。
> 因此循环体开头需要重新 `LOAD reg0, [13]` 把 `a` 取回来，这就是为什么这里没法像无限循环那样省掉 load。
> 而 reg1（常量 5）从头到尾没被动过，所以它的 load 可以留在循环外面。

### 8.3 两条 jump 的分工

只要条件成立，**位置 4 的条件跳转**和**位置 9 的无条件跳转**这一对，就会让 CPU 反复执行循环体的内容。

一旦条件不再成立，条件跳转**失败**，CPU 就顺势执行下一条指令，也就是**位置 5 那条无条件跳转，把程序计数器设到循环之外**。

```text
   条件成立时的路径                条件不成立时的路径
 ────────────────────────        ────────────────────────
   3  SUB                          3  SUB
   4  JUMP_NEG 6  ──┐              4  JUMP_NEG 6   ✗ 不跳
   5  JUMP 10       │              5  JUMP 10   ───┐
   6  LOAD       ◄──┘              6  LOAD         │
   7  INC                          7  INC          │
   8  STORE                        8  STORE        │
   9  JUMP 3  ──► 回到 3           9  JUMP 3       │
  10  HALT                        10  HALT      ◄──┘
```

运行起来能看到：只要变量 `a` 的值小于 5，这几条指令就被反复执行；
但因为每次迭代 `a` 都在变大，总有一刻它等于 5，减法就不再触发 negative 标志，循环于此断开。

```text
   轮次   a    a - 5    negative    JUMP_NEG
   ────  ───  ───────  ──────────  ──────────
    1     0     -5         1          跳，进循环
    2     1     -4         1          跳，进循环
    3     2     -3         1          跳，进循环
    4     3     -2         1          跳，进循环
    5     4     -1         1          跳，进循环
    6     5      0         0          不跳 -> 跳出循环
```

## 9. if 语句：把那条回跳删掉就行

如果好奇 CPU 是怎么处理 `if` 语句的，好消息是：**你已经知道了。**

在 while 循环的例子里我们就已经在求值一个条件了。

仔细想想，这两个程序非常相似。
**唯一的区别是：`if` 在执行完块里的代码之后不需要跳回去，所以那条无条件回跳是多余的。**

```c
a = 0;
if (a < 5) {
    a = a + 1;
}
```

```text
  位置   指令                    对应的高级语言
 ──────  ──────────────────────  ────────────────────────────
   0     LOAD   reg0, [15]       ┐ a = 0
   1     STORE  [13], reg0       ┘
   2     LOAD   reg1, [14]         reg1 = 5
   3     SUB    reg0, reg1       ┐ if (a < 5)
   4     JUMP_NEG  6             │   成立 -> 进块
   5     JUMP   9                ┘   不成立 -> 跳过整块
   6     LOAD   reg0, [13]       ┐
   7     INC    reg0             │ a = a + 1
   8     STORE  [13], reg0       ┘
   9     HALT
                                  ^ 这里没有 JUMP 3 了
```

* 条件**成立**：内层块被执行。
* 条件**不成立**：条件跳转失败，CPU 执行下一条指令，**等效于跳过了 if 里面的代码**。

```text
   while                        if
 ─────────────────────        ─────────────────────
   SUB  （比较）                SUB  （比较）
   条件 JUMP -> 块体            条件 JUMP -> 块体
   JUMP -> 循环外               JUMP -> 块后
   块体                         块体
   JUMP -> 回到 SUB   ◄──唯一   （无）
                        区别
```

作者说：这样讲下来，汇编也没那么难，对吧。

## 10. 换比较运算符，就是换标志位和跳转指令

比较也不总是同一种。
换一个比较运算符，改的只有两处：**看哪个标志位、用哪条条件跳转指令。**

| 高级语言写法 | `a - 5` 的结果 | 标志位状态 | 用的指令 |
| --- | --- | --- | --- |
| `a < 5` | 负数 | negative = 1 | `JUMP_NEG` |
| `a == 5` | 0 | zero = 1 | `JUMP_ZERO` |
| `a > 5` | 正数 | zero = 0 且 negative = 0 | `JUMP_ABOVE` |

注意最后一行的判定方式：想检查 `a` 是否大于 5，减法**既不该触发 zero，也不该触发 negative**。
这个「两个都不亮」的状态，就是 `jump above` 指令负责检测的。

程序的**骨架完全不变**，就是把第 8 节那份汇编里的 `JUMP_NEG` 换成对应指令而已。

## 12. 核心总结

```text
处理器怎么执行条件和循环
│
├── 前提：顺序执行只是「控制单元每次给 PC 加一」
│   ├── 可执行文件里不只有指令，还有程序需要的数据
│   ├── fetch -> decode -> execute -> PC + 1，循环往复
│   ├── CPU 分不清指令和数据，所以结尾必须有 HALT
│   └── 数据必须先 load 进寄存器才能被 ALU 加工，结果要 store 回内存才算「记住」
│
├── jump：把「PC + 1」改成「PC = 给定地址」
│   ├── 「跳转」只是这个行为的名字
│   ├── 实现上就是 load，只不过写的是地址寄存器
│   └── 跳回前面一条指令 ==> 无限循环，HALT 永远到不了
│
├── flags：ALU 每次运算附带的三个 1 bit 情报
│   ├── overflow：结果放不下（255 + 1 装不进一个字节）
│   ├── zero：结果为 0
│   ├── negative：结果为负
│   └── 存在的意义就是让程序能据此做决定
│
├── 条件跳转 = jump + 标志位检查
│   ├── 条件满足 -> 覆盖 PC
│   └── 条件不满足 -> 什么也不做，顺序执行下一条（分支就靠这个）
│
├── 比较运算符 = 一次减法 + 看一眼标志位
│   ├── a - 5 < 0  -> negative -> JUMP_NEG      对应 a < 5
│   ├── a - 5 = 0  -> zero     -> JUMP_ZERO     对应 a == 5
│   └── 两个都不亮 -> JUMP_ABOVE                对应 a > 5
│
└── while 和 if 在硬件上是同一个东西
    ├── while：比较 + 条件跳转进体 + 无条件跳转出循环 + 体末回跳到比较
    ├── if：  把「体末回跳」删掉，其余一模一样
    └── 每轮迭代前都要重新比较，所以回跳的目标是减法指令，不是循环开头
```

> 计算机看起来会「做决定」，其实它从来没有做过决定。
> 它只有一个程序计数器，默认每执行完一条指令就加一。
> 所谓条件和循环，全部是在**改写这个计数器**：
> `jump` 无条件改写它，条件跳转在标志位允许时才改写它，而标志位只是 ALU 做完一次减法后顺手记下的三个 bit。
> `if` 和 `while` 的区别，仅仅是那条回跳指令在不在。
