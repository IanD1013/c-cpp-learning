## 0. 这一期在讲什么

之前讲进程间通信（inter-process communication，IPC）时给出了两条路：共享内存区域，或者互相发消息。

两种方式都需要操作系统提供支持，也都假设「进程之间要传数据」。

本期讲第三条路：**信号**。

它几乎从来不被写进 IPC 的教材章节里，因为它传的不是数据，而是「有事发生了」这个事实本身。

前置知识见 [进程间通信](11-inter-process-communication.md) 和 [一个程序不是一个进程](08-a-program-is-not-a-process.md)。

## 1. 问题：Ctrl+C 到底做了什么

在终端里跑一个程序，按下 Ctrl+C，你预期它立刻终止。

但作者现场演示了一个程序：按 Ctrl+C，它不但不退出，反而播放了一段猫叫。

于是问题变成三个：

1. Ctrl+C 凭什么能终止一个正在跑死循环的程序？
2. 为什么有的程序按了没反应？
3. 既然能被改写，有没有什么是**改不掉**的？

## 2. 信号是什么：车喇叭类比

你在红绿灯前停在另一辆车后面，灯变绿了，前车不动。

这种情况下你不会给对方司机**发邮件**，也不会**下车走过去**当面说，你会按喇叭。

```text
共享内存 / 消息传递              信号
──────────────────              ──────────────────
写一封信，内容是                 按一下喇叭
「绿灯了，请前进」               （声音里没有任何词句）
        │                              │
        ▼                              ▼
接收方读取内容                   接收方被打断，
按内容行事                       自己去看灯，自己决定怎么做
```

喇叭声不包含任何词句，但它是一个**信号**，通知对方「发生了某件事」。

对方的反应是被打断、检查状况、然后行动。

> 信号是一条很小的消息，用来通知某个进程：系统里发生了某个事件。

有时候进程之间根本不需要传大块数据，只需要发一个提示，让对方在检测到的瞬间触发某个动作。

## 3. Linux 的信号表

系统里会发生的事件种类很多，所以操作系统定义了一整套信号，进程和内核自己都可以往别的进程发。

所有信号的用途都是「通知事件」，但每一个的**含义**不同。

本期出现过的主要信号（编号为 Linux x86 上的取值）：

| 编号 | 名字 | 含义 | 默认行为 |
| --- | --- | --- | --- |
| 2 | `SIGINT` | 来自键盘的中断（interrupt from keyboard） | 终止 |
| 4 | `SIGILL` | 非法指令（illegal instruction） | 终止并 dump core |
| 8 | `SIGFPE` | 浮点异常（floating point exception），含整数除零 | 终止并 dump core |
| 9 | `SIGKILL` | 强制杀死 | 终止，**不可捕获** |
| 10 | `SIGUSR1` | 用户自定义信号 1 | 终止 |
| 11 | `SIGSEGV` | 段错误（segmentation violation） | 终止并 dump core |
| 12 | `SIGUSR2` | 用户自定义信号 2 | 终止 |
| 15 | `SIGTERM` | 请求终止（`kill` 的默认信号） | 终止 |
| 18 | `SIGCONT` | 继续运行（continue） | 恢复执行 |
| 19 | `SIGSTOP` | 停止运行 | 暂停，**不可捕获** |
| 20 | `SIGTSTP` | 终端停止（terminal stop，即 Ctrl+Z） | 暂停 |

其中 `SIGUSR1` 和 `SIGUSR2` 是仅有的两个**通用信号**，含义由程序员自己规定，系统不赋予它们任何预设语义。

## 4. 发一个信号：`kill` 函数

在 Linux 上用 C 发信号，用的是 `kill` 函数：

```c
#include <signal.h>

int kill(pid_t pid, int sig);
```

两个参数：

* `sig`：想发送的那个信号的编号；
* `pid`：接收信号的进程 ID。

作者写了两个程序来演示。

**program A**：打印自己的进程 ID，然后进入死循环不停打印一条消息。

```c
// program_a.c
#include <stdio.h>
#include <unistd.h>

int main(void) {
    printf("My PID is: %d\n", getpid());
    while (1) {
        printf("Program A is running...\n");
        sleep(1);
    }
    return 0;
}
```

**program B**：把命令行参数当成 PID，向它发一个 `SIGUSR1`，打印一条消息后结束。

```c
// program_b.c
#include <stdio.h>
#include <stdlib.h>
#include <signal.h>

int main(int argc, char *argv[]) {
    pid_t pid = atoi(argv[1]);
    kill(pid, SIGUSR1);
    printf("Signal sent to process %d\n", pid);
    return 0;
}
```

实验过程：

```text
终端 1                              终端 2
──────────────────────            ──────────────────────
$ ./program_a
My PID is: 4217
Program A is running...
Program A is running...            $ ./program_b 4217
Program A is running...            Signal sent to process 4217
[1]    terminated  ./program_a  ◄──────────┘
```

**program A 死掉了。**

## 5. 中断不等于终止

它明明在跑死循环，为什么会停？

这里有信号最关键的一条性质：

> 信号让进程和内核可以**打断**其他进程。

所以 program A 在不在死循环里根本不重要，它照样会被打断。

但是，**打断一个进程不等于终止它**。

那它为什么真的死了？

因为每个信号在接收进程里都有一个**默认处理函数（default handler）**。

`SIGUSR1` 的默认处理函数就是「终止本进程」。

program A 从来没告诉系统自己想怎么处理这个信号，于是就退回到默认行为，把自己终止了。

```text
program B                内核                     program A
   │                      │                          │
   │  kill(4217,SIGUSR1)  │                          │
   ├─────────────────────►│                          │
   │                      │   打断当前执行流          │
   │                      ├─────────────────────────►│ ← 死循环也拦不住
   │                      │                          │
   │                      │   查 program A 为该信号   │
   │                      │   安装过处理函数吗？       │
   │                      │        │                 │
   │                      │   没有 → 默认处理函数     │
   │                      │        └──► 终止进程      │
```

## 6. 自己写处理函数：`signal`

`kill` 负责**发**信号，`signal` 负责规定**收到之后怎么办**：

```c
#include <signal.h>

typedef void (*sighandler_t)(int);

sighandler_t signal(int signum, sighandler_t handler);
```

两个参数：

* `signum`：要处理的那个信号；
* `handler`：一个特殊类型 signal handler 的值，本质上就是**指向另一个函数的指针**。

如果你不熟悉 C，可以类比 TypeScript 这类高级语言里「把一个函数当参数传给另一个函数」的写法。

handler 就是另一个函数，里面写收到信号时程序该做什么。

给 program A 加上处理函数，让它不再被 `SIGUSR1` 杀死：

```c
// program_a.c（改进版）
#include <stdio.h>
#include <unistd.h>
#include <signal.h>

void handle_sigusr1(int signum) {
    printf("Received SIGUSR1! But I'm not going to die.\n");
}

int main(void) {
    printf("My PID is: %d\n", getpid());
    signal(SIGUSR1, handle_sigusr1);   // ← 安装处理函数
    while (1) {
        printf("Program A is running...\n");
        sleep(1);
    }
    return 0;
}
```

`signal` 在底层会发起一个系统调用，告诉操作系统：

> 只要这个特定信号到达，立刻暂停我正在做的一切，改去执行这个 handler 函数。

这个动作的正式说法叫**安装处理函数（installing a handler）**。

再跑一次，program A 不再终止，而是打印我们定义的消息。

program B 可以反复运行，每一次 program A 都执行 handler 而不是去死。

注意最后一点：**handler 执行完之后，程序会回到它刚才正在做的事情上**。

```text
       正常执行流                信号到达
  ┌──────────────────┐             │
  │ while (1) {      │◄────────────┼─────┐
  │   printf(...)    │             ▼     │ 执行完返回原处
  │   sleep(1)       │      ┌────────────┴───┐
  │ }                │      │ handle_sigusr1 │
  └──────────────────┘      └────────────────┘
```

## 7. 终端、shell 和控制字符

要把上面这些和 Ctrl+C 连起来，先要澄清一个常见混淆。

你看到的那个黑框叫**终端（terminal）**，但真正解释你命令的程序叫 **shell**。

终端只是显示 shell 输出的那个窗口。

```text
┌──────────────────────────────────┐
│           终端（窗口）            │  ← 只负责显示和收键
│  ┌────────────────────────────┐  │
│  │          shell             │  │  ← 解释命令的程序
│  │   ┌──────────────────┐     │  │
│  │   │      kernel      │     │  │  ← shell 把它「包住」
│  │   └──────────────────┘     │  │     所以叫 shell（壳）
│  └────────────────────────────┘  │
└──────────────────────────────────┘
```

shell 之所以叫「壳」，是因为它是你与内核交互的唯一通道，像是完全包住了内核。

只通过文本和用户交互的 shell 就是命令行界面（CLI）。

你每按一个键，shell 登记这次击键、把字符加进缓冲区、更新屏幕显示。

**但不是所有击键都产生可见字符。**

查 ASCII 表，**前 32 项（0 到 31）都是不可打印的控制码**。

早年计算机没有显示器，这些码用来控制电传打字机（teletype）和打印机：回车（carriage return）、换行（line feed）、制表（tab）都是靠这些特殊字符实现的。

今天它们依然存在，只是不再用来控制打印机，而是用于屏幕上的文本格式化，以及其他用途。

问题是这些码大多没法用单独一个键打出来，所以我们用 Ctrl 加另一个键的组合。

事实上，键盘上那个键叫 **Control**，正是因为它当初就是用来向终端发送控制字符、执行移动光标或清屏之类动作的。

```text
Ctrl + 字母  =  该字母的 ASCII 码 - 64

  'C' = 65+2 = 67   →  67 - 64 = 3   →  0x03  (ETX)
  'Z' = 90          →  90 - 64 = 26  →  0x1A  (SUB)
  'D' = 68          →  68 - 64 = 4   →  0x04  (EOT)
```

关键在这里：**既然这些控制字符没法显示，shell 就把它们重新利用，让用户借此触发特定动作。**

## 8. Ctrl+C = SIGINT

回到信号表，里面有一个 `SIGINT`，signal interrupt 的缩写，描述写着「interrupt from keyboard」。

有时候用户希望给某个进程发信号，又不想为此专门写一个、跑一个程序。

于是：**某些控制字符会告诉内核，你想发出一个信号。**

在终端里跑程序时，其实同时存在两个进程：shell 和你的程序。

```text
你按下 Ctrl+C
      │
      ▼
┌──────────────────────┐
│ 内核里的终端驱动      │  把 0x03 解释为
│ (terminal driver)    │  「请发 SIGINT」
└──────────┬───────────┘
           │  SIGINT
           ▼
   前台进程组（foreground process group）
   ┌───────────────┐
   │  你的程序      │ ← 被打断
   └───────────────┘
           │
           ├─ 装了 handler？ → 执行 handler，然后继续跑
           └─ 没装？        → 默认行为：终止
```

所以程序在终端里被 Ctrl+C 终止，是因为**内核的终端驱动把 Ctrl+C 解释成「向前台进程组发送 SIGINT」**。

`SIGINT` 本身只是**打断**它们。

大多数程序会死，只是因为它们对 `SIGINT` 的默认行为是终止。

既然如此，和上一节一样，我们可以覆盖它：

```c
void handle_sigint(int signum) {
    play_cat_sound();          // 视频里：播放一段猫叫
}

int main(void) {
    signal(SIGINT, handle_sigint);
    ...
}
```

作者演示时每按一次 Ctrl+C，程序就叫一声，怎么按都不退出。

> 代码在作者的仓库里：https://github.com/jdvillal/program_a.git

## 9. 后台进程与「信号轮盘赌」

不是所有进程都跑在前台。

实际上系统里绝大多数进程都在后台运行，打开任务管理器就能看到几百个没有任何终端或窗口关联的进程。

设想其中有一个**坏进程（bad process）**：一个月前启动的服务器，现在开始作妖，内存泄漏，慢慢吃光你的 RAM。

你决定无论如何要干掉它。

它不在终端前台，Ctrl+C 用不上。

第一次尝试：用刚才那个 program B，把坏进程的 PID 传进去。

结果什么都没发生，进程还在。

**怀疑**：坏进程给 `SIGUSR1` 装了自定义处理函数。

于是写第三个程序，**program C**，更灵活一点，信号编号和目标 PID 都从命令行传：

```c
// program_c.c
#include <stdio.h>
#include <stdlib.h>
#include <signal.h>

int main(int argc, char *argv[]) {
    int sig   = atoi(argv[1]);
    pid_t pid = atoi(argv[2]);
    kill(pid, sig);
    printf("Signal %d sent to process %d\n", sig, pid);
    return 0;
}
```

这样就能一个个信号试过去，直到试出能把它干掉的那个。

**但这是个糟糕的主意，有两条理由：**

```text
信号轮盘赌的两个问题
│
├── ① 你只是在「祈祷」
│      祈祷坏进程没有为所有会导致终止的信号都装上处理函数
│
└── ② 试错本身有副作用
       就算最后试中了正确的那个，
       之前发出去的每一个信号都可能触发了意料之外的行为。
       如果程序不是你写的，谁知道那些信号绑了什么内部例程？
```

## 10. 不可拦截的两个信号：`SIGKILL` 与 `SIGSTOP`

好消息是这场赌博根本不必发生，因为我们担心的情况压根不可能出现。

包括 Linux 在内的大多数系统都规定了一批信号，**用户态进程无法拦截、阻塞或忽略**。

其中有两个是任何进程都覆盖不了的：

| 信号 | 编号 | 结果 |
| --- | --- | --- |
| `SIGKILL` | 9 | 立刻终止，没有 handler，没有清理，没有逃生 |
| `SIGSTOP` | 19 | 立刻暂停，同样无法拦截 |

所以对付坏进程，不用玩轮盘赌，直接发 9 号：

```text
./program_c 9 <bad_pid>
        │
        ▼
   坏进程消失，它占的内存全部释放
```

因为这个信号不能被捕获也不能被忽略，你可以确信进程一定会被强制终止。

## 11. `kill` 命令的真面目

到这里你大概想问：为什么不一开始就用 `kill` 命令？

对，你说得没错，而且从某种角度看，作者做的就是这件事。

> `kill` 命令并不是只为「杀进程」而存在的。
> 它是一个可以**把任意信号发给任意进程**的 Linux 工具，和 program C 一模一样。

它叫 `kill`，只是因为底层用的是 `kill` 函数。

```bash
kill -9 4217      # 发 SIGKILL 给 4217
kill -19 4217     # 发 SIGSTOP
kill -18 4217     # 发 SIGCONT
kill 4217         # 不带 - ，默认发 15（SIGTERM）
```

那个 `-` 是必须的：

```text
kill -9 4217                  kill 9 4217
       │                            │
  信号 9 → PID 4217          「9」被当成另一个 PID
                              于是给 9 和 4217 两个进程
                              都发默认信号 15
```

这也解释了一个日常现象：为什么有时候 `kill <pid>` 不管用，非得加 `-9` 才能强制终止。

因为 `kill <pid>` 发的是 `SIGTERM`（15），而 `SIGTERM` 是**可以被处理的**；`SIGKILL` 不行，发出去进程就必然结束。

```text
SIGTERM (15)                     SIGKILL (9)
───────────────                  ───────────────
「请你自己退出」                  「你现在就没了」
可捕获、可忽略                    不可捕获、不可忽略
程序可以做清理                    没有清理机会
→ 有可能没反应                    → 一定生效
```

## 12. 停止与继续：Ctrl+Z 和 `SIGCONT`

另一个不能被捕获、永远走默认处理函数的信号是 `SIGSTOP`。

作者不深入这一个信号，而是讲**共享同一种默认行为的那一组信号**。

这组信号的默认行为是：让进程**停止运行，但不终止它**。

进程被这样停住之后处于「冻结」状态，直到另一个信号叫它继续，通常是 `SIGCONT`（signal continue）。

在 Linux 上，终端里跑着程序时按 Ctrl+Z，就是告诉内核向该终端里运行的进程发送 `SIGTSTP`（terminal stop）。

遗憾的是，**`SIGCONT` 没有对应的键盘快捷键**，想让进程恢复只能手动发：

```bash
kill -18 <pid>    # 发 SIGCONT 让它继续
fg                # 把进程调回前台，这样才能继续看到它的输出
```

```text
运行中 ──Ctrl+Z (SIGTSTP)──► 已停止 ──kill -18 (SIGCONT)──► 运行中
                              （冻结，                        │
                               不占 CPU，               fg  ──┘
                               内存还在）           （调回前台看输出）
```

## 13. 进程组：一次发给一群进程

信号不止能发给一个进程。

就像每个进程有唯一的 PID 一样，进程也可以属于某个**进程组（process group）**，每个组有自己的组 ID。

```text
kill(4217, SIGTERM)       →  只发给 PID = 4217 的那一个进程

kill(-4217, SIGTERM)      →  发给「组 ID = 4217」的组里的所有进程
     └─ 负数！                  ┌───────┬───────┬───────┐
                                │ 4217  │ 4219  │ 4223  │  同一组
                                └───────┴───────┴───────┘
                                     全都收到 SIGTERM
```

调用 `kill` 时如果传入一个**负的 PID**，信号会发给组 ID 等于该负数**绝对值**的那一组里的所有进程。

（第 8 节说 Ctrl+C 发给「前台进程组」，正是这个机制。）

## 14. 系统级事件如何变成信号

收尾前作者要我们注意一件事：**大多数触发中断的事件其实都是系统级事件。**

```text
事件发生                 谁检测到                内核的反应
──────────────          ───────────────        ─────────────────
除以零           →      CPU 内部电路触发   →   向该进程发 SIGFPE
                        硬件中断                （floating point exception）

执行非法指令      →      CPU 捕获            →   向该进程发 SIGILL
（如用户态执行                                  （illegal instruction）
  特权指令）

访问不属于自己    →      专门的 CPU 硬件      →   向该进程发 SIGSEGV
的内存                  （MMU）检测到            （segmentation violation）
                                                       │
                                    默认处理函数：终止进程并 dump core
                                                       │
                                                       ▼
                                    "Segmentation fault (core dumped)"
```

那句你见过无数次的 `segmentation fault (core dumped)`，来源就在这里。

由此得到本期最反直觉的一句话：

> 我们常以为操作系统在必要时会自己把程序终止掉。
> 但实际上，它是**发信号指示进程自我终止**。

## 15. 为什么不该给 `SIGSEGV` 装处理函数

有人会想：`SIGSEGV` 是可以捕获的，那我装个 handler，程序不就不会因为段错误而死了吗？

技术上确实可以，但这是个坏主意。

作者在 Stack Overflow 上找到一个很好的回答，解释了这样做**制造的问题比解决的更多**。

屏幕上那段回答的原文是：

> 当你的信号处理函数返回时（前提是它没有调用 `exit`、`longjmp` 或其他阻止它真正返回的东西），代码会从信号发生的那个点继续，**重新执行同一条指令**。
> 而此刻内存保护并没有发生任何改变，于是它会再次抛出同一个信号，你又回到了信号处理函数里，如此形成一个无限循环。

把它和第 6 节那张「handler 执行完回到原处」的图连起来看，问题就一目了然：

```text
  非法访存的那条指令
        │
        ▼
  ┌──────────────┐   MMU 检测到越界   ┌──────────────┐
  │ mov eax,[ptr]│ ─────────────────► │ 内核发 SIGSEGV│
  └──────┬───────┘                    └──────┬───────┘
         ▲                                   │
         │                                   ▼
         │                          ┌──────────────────┐
         │   handler 返回，          │ 你的 SIGSEGV      │
         └── 回到「信号发生处」 ◄────┤ handler（打印日志…）│
             重新执行同一条指令       └──────────────────┘

         内存保护一点没变 → 再次越界 → 再次 SIGSEGV → 死循环
```

换句话说，`SIGSEGV` 的 handler 和 `SIGINT` 的 handler 有本质区别：

| | `SIGINT` | `SIGSEGV` |
| --- | --- | --- |
| 信号来源 | 外部事件（键盘） | **当前这条指令本身** |
| handler 返回后 | 回到被打断处，继续往下跑 | 回到并**重新执行**出错的那条指令 |
| 触发条件是否已消失 | 是 | 否，内存保护原样未动 |
| 结果 | 正常恢复 | 无限循环 |

想真正「处理」段错误，handler 就必须做一件让它不再返回的事（`exit`、`longjmp`），或者真的去修改内存映射把那次访问变成合法的 - 后者属于另一个层面的技术，超出本期范围。

## 16. 为什么信号很少被当作 IPC

回到开头那个问题：既然信号也是进程间的通信，为什么教材通常不这么归类？

> 因为信号携带的消息**不是通用数据**。
> 它是一个系统级或用户级的**事件**，目的在于打断进程、强迫它以某种方式作出反应。

所以信号更常被归到另一个类别下：**异常控制流（exceptional control flow）**。

```text
                  进程间通信
                       │
      ┌────────────────┼────────────────┐
      │                │                │
  共享内存          消息传递          （信号）
  传数据            传数据            传事件
      │                │                │
      └────────────────┘                └──► 通常归入「异常控制流」
        目的：交换内容                        目的：打断 + 触发反应
```

## 18. 核心总结

```text
信号：进程间通信的第三条路
│
├── 本质
│   ├── 一条很小的消息，通知「某事发生了」，不携带通用数据
│   ├── 像按喇叭：不含词句，但迫使对方检查状况并反应
│   └── 能力：打断（interrupt）任意进程，死循环也拦不住
│
├── 打断 ≠ 终止
│   ├── 每个信号在接收进程里都有一个默认处理函数
│   ├── 大多数信号的默认行为恰好是「终止」→ 造成了「信号=杀进程」的错觉
│   └── 装上自己的 handler 就能改写这个行为，handler 返回后回到原处继续跑
│
├── 两个方向的 API
│   ├── 发：kill(pid, sig)            ← kill 命令就是它的命令行包装
│   └── 收：signal(signum, handler)   ← 「安装处理函数」
│
├── Ctrl+C 的完整链路
│   ├── ASCII 前 32 个是不可打印控制码，Ctrl 键当年就是用来发它们的
│   ├── shell 把这些打不出来的字符重新利用为动作触发器
│   ├── 内核的终端驱动把 Ctrl+C 解释为：向前台进程组发 SIGINT
│   └── 程序死掉是因为 SIGINT 的默认行为是终止，而不是 Ctrl+C 本身会杀进程
│
├── 改不掉的两个
│   ├── SIGKILL (9)  不可捕获/阻塞/忽略 → 所以 kill -9 一定生效
│   ├── SIGSTOP (19) 同样不可覆盖，冻结进程，靠 SIGCONT (18) 唤醒
│   └── 有它们在，就不必玩「挨个试信号」的轮盘赌（每一发都可能有副作用）
│
├── 命令行对照
│   ├── kill <pid>      → 默认 15 (SIGTERM)，可被处理，所以可能没反应
│   ├── kill -9 <pid>   → SIGKILL，必然终止
│   ├── Ctrl+Z          → SIGTSTP 停住；kill -18 + fg 恢复
│   └── kill(-gid, sig) → 负 PID = 发给整个进程组
│
└── 系统事件也是信号
    ├── 除零 → SIGFPE ／ 非法指令 → SIGILL ／ 越界访存 → SIGSEGV
    ├── "Segmentation fault (core dumped)" 就是 SIGSEGV 的默认处理函数
    └── 操作系统不是自己动手杀进程，而是发信号让进程自我终止
```

> 信号不是用来传内容的，是用来**打断**的。
> 它把「系统里发生了某件事」变成一次强制的控制流转移，逼进程当场作出反应，所以它被归类为异常控制流而不是 IPC。
> 而 Ctrl+C 的全部魔力，不过是内核替你按了一下喇叭 - 至于程序听到喇叭后是去死还是学猫叫，从来都是程序自己说了算，除了 9 号和 19 号这两下它没得选。
