# 程序不是进程

> 视频来源：Core Dumped -《A PROGRAM is not a PROCESS.》
> https://www.youtube.com/watch?v=7ge7u5VUSbE

## 0. 这一期在讲什么

计算机科学里有一个反复出现的问题：CPU 正在做的那一堆事，到底该叫什么？

日常说话里我们会说「CPU 在跑程序」。
这个说法在计算机科学里是不准确的。
正确的术语是**进程（process）**。

这一期只做一件事：把**程序（program）**和**进程（process）**这两个概念分开。

作者也提前说明了本期的边界：
进程的技术定义（PCB、状态机、调度、上下文切换）**超出本期范围**，属于后面那期专门讲进程的视频。
编译器和解释器同样各自值得单开一期。
本期只负责把「程序 ≠ 进程」这件事讲清楚。

---

## 1. 先看术语是怎么演变过来的

这三个词不是同义词换着用，它们对应三个不同年代的计算机形态。

```text
早期批处理系统            分时操作系统                家用计算机
(batch systems)         (time-sharing OS)         (home computer)
      │                        │                        │
      ▼                        ▼                        ▼
   job（作业）            user program（用户程序）      process（进程）
      │                        │                        │
 一次提交一批活         CPU 要在多个用户之间分享     单个用户同时跑多个东西
 跑完一个再跑下一个       所以说「运行用户程序」       并发成了日常需求
```

分时系统那一步的背景，在并发那一期讲过：CPU 要被多个用户共享。
到了家用计算机时代，并发被普及成「一个用户同时开很多东西」。

而计算机科学在指称这些「同时跑着的东西」时，用的词不是 program，是 **process**。

---

## 2. 常见定义为什么不够用

教科书上最常见的非正式定义是：

> 进程就是执行中的程序（a program in execution）。

这个定义**技术上是正确的**。
作者的不满在于：它对一个只是随便读读的人来说，信息量几乎为零。
读完之后你并不知道进程到底是什么。

所以这一期换了个思路：**先确立进程「不是」什么**。

---

## 3. 程序是什么：一个被动的实体

先给程序下定义。

> **程序是一段指令序列，加上 CPU 完成某个特定任务所需要的数据。**

仔细看这句话，你会发现它同时也在描述另一样东西：**可执行文件（executable file）**。

这不是巧合。
可执行文件差不多就是程序本身。

```text
你的硬盘
┌─────────────────────────────────┐
│                                 │
│   editor.exe                    │
│   ┌───────────────────────┐     │
│   │ 指令序列              │     │
│   │ + 运行需要的数据      │     │
│   └───────────────────────┘     │
│                                 │
│   躺在那里，什么也没发生        │
│   等着你去双击它                │
└─────────────────────────────────┘
```

关键词是**被动（passive）**。

程序是一个**待在存储设备里的被动实体**，等着你点它，等着你告诉计算机去运行它。
在你点它之前，它不消耗 CPU，不占内存，什么都不做。

---

## 4. 装入内存之后：四个区域

要运行一个程序，第一步永远是把它**装入内存**，因为 CPU 只能从内存里取指令和数据。

装入内存时，可执行文件里的内容被拆到两个区域：

| 区域 | 装什么 |
| --- | --- |
| **text 段（text section）** | 可执行代码，也就是那串指令 |
| **data 段（data section）** | 全局变量、常量这类数据 |

但光有这两段跑不起来。
程序在运行时还会产生大量**运行期才存在的数据**：用户输入、临时结果、局部变量。
这些东西在编译时根本不知道有多少，所以需要额外的空间。

于是就有了我们已经很熟悉的**栈（stack）**和**堆（heap）**。

```text
                内存中的布局
        ┌───────────────────────────┐
   高地址│         stack             │  局部变量、函数调用
        │            │              │  向下增长
        │            ▼              │
        │                           │
        │      （空闲空间）         │
        │                           │
        │            ▲              │
        │            │              │  向上增长
        │          heap             │  运行时动态分配
        ├───────────────────────────┤
        │        data 段            │  全局变量、常量
        ├───────────────────────────┤
   低地址│        text 段            │  可执行代码
        └───────────────────────────┘
```

### 4.1 哪些会变，哪些不会

这四个区域的「可变性」并不一样，这一点是理解进程的关键。

| 区域 | 大小会变吗 | 内容会变吗 |
| --- | --- | --- |
| text | 不变 | 不变 |
| data | 不变 | **会变**，取决于程序正在做什么 |
| heap | **一直在变** | 会变 |
| stack | **一直在变** | 会变 |

栈和堆的大小时时刻刻都在涨和缩，这个前面几期已经讲透了。

**text 段是唯一一个大小和内容都不变的区域。**
它就是那串指令，装进来是什么样，跑完还是什么样。

data 段稍微微妙一点：它的**大小**不变（全局变量的数量在编译期就定死了），但它的**内容会变**，因为程序运行时会往里写值。

```text
装入的那一刻                运行了一会儿之后
─────────────────          ─────────────────
text: 指令 A B C           text: 指令 A B C      ← 完全一样
data: counter = 0          data: counter = 4711  ← 内容变了
heap: （空）               heap: 已经分配了一堆  ← 大小内容都变了
stack: （空）              stack: 几层函数调用   ← 大小内容都变了
```

## 5. 那一刻它就不再是程序了

看上面那张对比图。

一开始我们把「程序」装进了内存。
但运行起来之后，这个布局**还能叫程序吗**？

当然不能。
它已经变成了一个**进程**。

程序是硬盘上那个固定不变的文件。
而内存里这个东西正在长大、缩小、改写自己的数据，它是活的。

```text
   程序（program）                    进程（process）
   ─────────────────                  ─────────────────
   被动实体（passive）                主动实体（active）
   躺在存储设备里                     活在内存里
   内容固定不变                       状态时刻在变
   一份文件                           可以有很多份
```

### 5.1 一个必须澄清的点

作者在这里特意强调了一句，很容易被读者忽略：

> 上面画的那个四段布局，是**进程的内存布局**，而不是**进程本身**。

进程不等于它的内存布局。
内存布局只是进程的一部分。
进程还包含状态、寄存器快照、打开的文件、调度信息等等一大堆东西，那些**超出本期范围**，留给专门讲进程的那一期。

这也正是为什么「执行中的程序」这个定义只能算非正式定义：
**进程这个概念太复杂了，几个词根本装不下。**

## 6. 同一个程序，两个进程

这是本期最直观的例子。

想象操作系统自带的那个文本编辑器。
现在你有两个文件要读，你把两个都打开了。

操作系统会把这个文本编辑器**启动两次**，你得到两个窗口，各显示一个文件。

```text
             editor.exe          ← 硬盘上，只有一份
                  │
        ┌─────────┴─────────┐
        │  启动两次          │
        ▼                   ▼
   ┌─────────┐         ┌─────────┐
   │ 进程 1  │         │ 进程 2  │
   │ 窗口 A  │         │ 窗口 B  │
   │ 大文件  │         │ 小文件  │
   └─────────┘         └─────────┘
```

**同一个程序，两个完全不同的进程。**

每个进程有**自己的内存空间**。
两边的 text 段内容是**一模一样**的，因为它们本来就是同一个程序的代码。
但它们处理的数据完全不同。

```text
        进程 1（打开大文件）              进程 2（打开小文件）
   ┌───────────────────────┐        ┌───────────────────────┐
   │ stack                 │        │ stack                 │
   │   ...                 │        │   ...                 │
   │ heap                  │        │ heap                  │
   │   ████████████████    │        │   ██                  │
   │   ████████████████    │        │                       │
   │   （大文件内容）      │        │   （小文件内容）      │
   ├───────────────────────┤        ├───────────────────────┤
   │ data 段               │        │ data 段               │
   ├───────────────────────┤        ├───────────────────────┤
   │ text 段：编辑器代码   │  ===   │ text 段：编辑器代码   │
   └───────────────────────┘        └───────────────────────┘
        内存占用更大                     内存占用更小
```

视频里的例子是：第一个进程打开的文本文件比第二个大得多，所以它自然需要更多内存来管理自己的数据。

由此得到本期的核心表述：

> 两个进程可能关联到**同一个程序**，但它们依然是**两条互相独立的执行序列**
> （two separate execution sequences）。

## 7. 解释型语言的情况

上面所有讨论都建立在**编译型语言**上。

用 C 或 Rust 时，编译的产物就是一个可执行文件，那个文件就是程序本身。
这条链路很清晰。

但 Python、JavaScript 这类**解释型语言**呢？
它们根本没有编译这一步。

### 7.1 现在有两个被动实体

在 Python 里，每次想跑代码，你实际上要做两件事：

1. 让计算机运行**解释器**；
2. 让解释器去执行**你的代码**。

```text
   两个被动实体
   ┌─────────────────────┐        ┌─────────────────────┐
   │  python 解释器      │        │  your_script.py     │
   │  （可执行文件）     │        │  （纯文本文件）     │
   │                     │        │                     │
   │  这是一个「程序」   │        │  这不是「程序」     │
   └─────────────────────┘        └─────────────────────┘
```

这里作者要特别强调一件事：

> **Python 源文件不是程序。**

回忆一下程序的定义：指令序列 + 数据。
而源代码只是**文本**，计算机看不懂，也就无法执行。

所以在这种情况下，你真正要求计算机运行的那个程序，是**解释器**，不是你写的 Python 代码。

### 7.2 进程装起来之后长什么样

解释器进程被创建之后，它和任何别的进程一样：有 text 段、data 段、栈、堆。

关键在于，**text 段里装的是什么**。

```text
        python 解释器进程
   ┌───────────────────────────────────┐
   │ stack                             │
   │   解释器自己的函数调用            │
   ├───────────────────────────────────┤
   │ heap                              │
   │   ┌─────────────────────────┐     │
   │   │ your_script.py 的源代码 │ ◄───┼── 你的代码在这里
   │   │ （作为「数据」被读取）  │     │    它是被处理的对象
   │   └─────────────────────────┘     │
   ├───────────────────────────────────┤
   │ data 段                           │
   ├───────────────────────────────────┤
   │ text 段                           │
   │   解释器的可执行代码        ◄─────┼── 不是你的 Python 代码
   └───────────────────────────────────┘
```

一句话总结这张图：

| | 装在哪 | 身份 |
| --- | --- | --- |
| 解释器的可执行代码 | text 段 | 被执行的**指令** |
| 你写的 Python 源码 | data 区域，**最可能是堆** | 被读取的**数据** |

之所以最可能落在堆上，是因为源代码正是解释器要去读、去解释的那份**工作数据**，大小在运行前不确定，所以走动态分配。

编译型和解释型的对照：

```text
   C / Rust                          Python / JavaScript
   ─────────────────                 ─────────────────
   源码 ──编译──► 可执行文件         源码（文本，始终是数据）
                     │                        │
                     │ 装入                   │ 被读取
                     ▼                        ▼
              text 段 = 你的代码        text 段 = 解释器的代码
                                        heap  = 你的代码
```

## 9. 核心总结

```text
程序 ≠ 进程
│
├── 程序（program）：被动实体
│   ├── 定义：指令序列 + 完成任务所需的数据
│   ├── 等价物：硬盘上的可执行文件
│   ├── 状态：躺着不动，等你点它
│   └── 数量：一份
│
├── 进程（process）：主动实体
│   ├── 非正式定义：执行中的程序（正确但不够用）
│   ├── 内存布局：text / data / heap / stack
│   │   ├── text：大小不变，内容不变
│   │   ├── data：大小不变，内容会变
│   │   └── heap / stack：一直在涨缩
│   ├── 注意：内存布局是进程的布局，不是进程本身
│   └── 数量：同一个程序可以有任意多个进程
│
├── 一程序多进程
│   ├── 打开两个文本文件 -> 编辑器启动两次
│   ├── 各自独立的内存空间
│   ├── text 段内容相同（同一个程序）
│   ├── data / heap 完全不同（不同的文件）
│   └── 结论：两条互相独立的执行序列
│
└── 解释型语言
    ├── 两个被动实体：解释器（是程序）+ 源文件（不是程序）
    ├── 源代码只是文本，计算机看不懂，不能执行
    ├── 真正被运行的程序是解释器
    └── text 段 = 解释器代码；你的源码在堆里，是数据
```

> 硬盘上那个文件从来没有「跑起来」过。
> 跑起来的是内存里那份副本，而它一旦开始改写自己的栈和堆，就不再是当初那个文件了。
> 程序是名词，进程是动词。
> 同一个名词可以对应很多个正在进行的动词，它们彼此毫不相干。
