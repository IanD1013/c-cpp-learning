# 视频学习笔记

用户会提供两样东西：**视频链接** 和 **目标 Markdown 文件路径**。
产出是一份中文学习笔记，写到指定路径。

如果用户只给了链接没给路径，先问路径，不要自己猜。

## 1. 取字幕和元信息

```bash
.claude/skills/video-notes/scripts/fetch-transcript.sh <video-url> <work-dir>
```

`<work-dir>` 用 scratchpad 目录，不要污染用户仓库。

脚本会在 `<work-dir>` 下产出：

| 文件 | 内容 |
| --- | --- |
| `transcript.txt` | 带时间戳、已去重的逐字稿 |
| `meta.txt` | 标题 / 频道 / 时长 / 发布日期 / 章节 / 简介 |
| `raw.info.json` | yt-dlp 的完整元数据 |

脚本自己会把 yt-dlp 二进制缓存到 `~/.cache/claude-video-notes/`，超过 14 天自动更新，不需要预装任何东西。

失败时的处置：

* 报 `could not fetch video metadata` -> 加 `-u` 重跑一次（YouTube 经常改接口，刷新 yt-dlp 通常就好）；
* 还是失败 -> 视频可能是私有、区域限制或需要登录，告诉用户，别硬试。
* 报 `NO TRANSCRIPT` -> 该视频没有任何字幕轨。只能基于 `meta.txt` 写，并且要明确告诉用户笔记信息量有限。

**不要**手写 curl 去抓 YouTube 的 timedtext 接口，现在需要 PO token，一律返回空。

## 2. 读完再写

把 `transcript.txt` 整份读完，再动笔。
`meta.txt` 里的章节列表（如果有）是作者自己给的结构，是分节的最佳依据。

逐字稿是自动语音识别的产物，有两类噪声要修：

* **技术术语被听错**，例如 `byte` 写成 `bite`、`Vec` 写成 `vec`、`malloc` 写成 `mallock`。按上下文改回正确写法，不要照抄。
* **大小写混乱**，例如 `the Heap`、`rust`、`Concepts`。不作为术语依据。

另外，逐字稿只有旁白，**没有画面**。作者在屏幕上展示的代码和示意图需要你根据旁白重建出来，这部分往往是笔记里最有价值的内容。

## 3. 笔记怎么写

### 结构

```text
# 标题（中文，可带英文原术语）

> 视频来源：<频道> -《<原标题>》
> <URL>

## 0. 这一期在讲什么      ← 视频的定位和前置背景
## 1. 问题                 ← 先立问题，再给答案
## 2..N 逐个概念            ← 每节一个概念，配图配代码
## N+1 下一步               ← 如果视频预告了后续内容
## N+2 核心总结             ← 树状图 + 一句话收束
```

### 硬性要求

* 简体中文。代码、标识符、命令、路径、API 名保持原文。
* **不使用破折号（em dash）**，需要时用普通连字符。
* 长 Markdown 文件里**每个完整句子单独一行**，不要把多句挤在同一物理行。
* 关键术语首次出现时给出中英对照，例如「字节（byte）」。

### 内容要求

按重要性排序：

1. **重排，不要顺流而下。**
   视频是线性叙述，笔记是可检索的参考。按「问题 -> 前置知识 -> 主线 -> 推广」重组，而不是按时间轴照搬。

2. **补上具体数字。**
   视频常常只说「浪费很多内存」。笔记要把它算出来：`10,000 × 8 字节 = 80,000 字节 ≈ 78 KB`，对比 `10,000 × 1 字节 ≈ 9.8 KB`。
   具体数字是笔记比视频强的地方。

3. **重建画面里的代码。**
   旁白说「在 JavaScript 里你可以这样写」时，把那段代码补全写出来，并保留作者的对比意图。
   用视频里**它自己的例子**，不要换成你想出来的新例子。

4. **大量使用 ASCII 图。**
   所有示意图放在 ` ```text ` 围栏里。常用几种：

   内存布局（逐字节标注，标出浪费的部分）：

   ```text
    byte7    byte6   ...   byte0
   ┌────────┬────────┬─────┬────────┐
   │00000000│00000000│ ... │00011001│
   └────────┴────────┴─────┴────────┘
   └────── 永远为 0（浪费）──────┘ └─ 实际用到 ─┘
   ```

   流程与开销分解：

   ```text
         a + b
           │
           ├─ 读取 a 的标签  ->  花时间
           ├─ 执行真正的运算  <-  这一步才是你的代码
           └─ 写入结果标签    ->  花时间
   ```

   指针指向另一块内存：

   ```text
   ┌───────────────┐          ┌────┬────┬────┐
   │ ptr  ─────────┼─────────►│  1 │  2 │  3 │
   ├───────────────┤          └────┴────┴────┘
   │ len  = 3      │
   └───────────────┘
   ```

   两种方案对比（左右并排或上下对照表）：

   ```text
   动态类型                     静态类型
   ─────────────────           ─────────────────
   tag 初始化                   （无）
   实际运算                     实际运算
   ```

5. **可枚举的事实用表格。**
   类型宽度、位数与范围、命令参数、状态含义，都比散文好读。

6. **章节之间用 `---` 分隔。**

7. **收尾给树状总结 + 一句话。**

   ```text
   为什么 X 重要
   │
   ├── 空间
   │   └── ...
   └── 性能
       └── ...
   ```

   最后用一段引用把整期收束成一句话。

8. **视频没讲的别编。**
   作者说「超出本视频范围」的地方，照样写成「超出本期范围」，并说明它属于哪个后续话题。
   需要补充背景时可以补，但不要把你的推测混进作者的论述里。

## 4. 收尾

写完后向用户报告：

* 取字幕用的路径（哪条轨、多少行），以及过程中遇到的问题；
* 笔记的分节表格，让用户一眼看到覆盖了哪些内容；
* 都做了哪些 ASCII 图。

不要把笔记正文重复贴到终端里，用户直接看文件。
