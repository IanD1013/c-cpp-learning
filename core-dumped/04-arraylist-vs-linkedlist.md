## 0. 这一期在讲什么

数组是所有开发者的基础工具，但它在不同语言里的行为差别巨大。

| | 系统级语言（C / Rust / Go） | 脚本语言（Python / JavaScript） |
| --- | --- | --- |
| 声明时 | 必须指定元素**类型**和**长度** | 都不用 |
| 能不能追加元素 | 不能 | 能，无限加 |
| 能不能混装不同类型 | 不能 | 能 |

看起来脚本语言完胜。

这一期回答三个问题：

1. 为什么会有这个限制（底层的数组到底长什么样）；
2. 低级语言用什么数据结构绕过它（LinkedList 和 ArrayList，各自代价是什么）；
3. 脚本语言是怎么"作弊"的，以及**为什么 JavaScript 的数组根本不是数组**。

前置知识是前两期的[栈](02-why-is-the-stack-so-fast.md)和[堆](03-why-is-the-heap-so-slow.md)。

## 1. 底层的数组：一块没有名字的连续内存

### 1.1 为什么数组不能增长

数组的定义很简单：元素一个挨一个，每个占一个位置，位置编号叫**索引（index）**。

低层的实现思路是让**每个元素在内存里彼此相邻**。
问题就出在这里：内存里还放着别的值。

假设一个数组后面紧跟着两个变量 `a` 和 `b`，我们往数组里"追加"元素：

```text
追加前
┌────┬────┬────┬────┬────┬────┐
│ [0]│ [1]│ [2]│ a  │ b  │ .. │
└────┴────┴────┴────┴────┴────┘
                ▲    ▲
                └────┴── 后面的代码还要用这两个值

追加两个元素后
┌────┬────┬────┬────┬────┬────┐
│ [0]│ [1]│ [2]│ [3]│ [4]│ .. │
└────┴────┴────┴────┴────┴────┘
                ▲    ▲
                └────┴── a 和 b 被覆盖了
```

关键在于：**计算机不是按变量名访问值的，是按内存地址访问的**。

编译器生成机器码时，`a + b` 已经被翻译成"把地址 X 和地址 Y 上的数加起来"。
这个翻译在当时是对的，因为那就是 `a` 和 `b` 被存放的地方。
但现在那两个地址上装的是数组的第 4、5 个元素：

```text
        a + b
          │
          ├─ 读地址 X  ->  拿到的是 array[3]
          ├─ 读地址 Y  ->  拿到的是 array[4]
          └─ 相加      ->  结果完全错误，但程序不会报错
```

这个问题的通行解法非常粗暴：**干脆不允许程序员往数组里加元素**。

这就是为什么系统级语言的数组没有 `append` / `insert` / `push` 这些方法，
而 Python、JavaScript 里到处都是。
（另一个原因是：底层的数组根本不是对象。）

### 1.2 为什么必须写死类型和长度

声明数组时要给出两样东西，各有各的用处：

```text
   int16   arr[5]
     │        │
     │        └── 长度：5 个元素
     └── 类型：每个元素 2 字节
```

编译器把两者相乘，就得到这个数组需要的**精确内存大小**：

```text
2 字节 × 5 = 10 字节
```

这个数字是必需的：

| 数组放在哪 | 需要这个数字来做什么 |
| --- | --- |
| 栈（stack） | 决定栈指针要移动多少 |
| 堆（heap） | 向分配器申请多大的一块空间 |

**同一个数组不能装不同类型**，根源就在这里：类型不统一，就算不出每个元素占几个字节，也就算不出总大小。

### 1.3 索引是怎么工作的：base address + 偏移

图示里元素之间画着分隔线，但那只是示意。
在裸硬件上，它其实是这样的，而且我们**唯一掌握的信息只有数组起始的那个内存地址**，称为**基地址（base address）**：

```text
示意图（骗人的）
┌────┬────┬────┬────┬────┐
│ 25 │ 13 │ 78 │  4 │ 91 │
└────┴────┴────┴────┴────┘

真实内存（诚实的）
0x1000
  │
  ▼
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│00│19│00│0D│00│4E│00│04│00│5B│
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
 └──┬──┘
    └── 只有你知道这里两个字节是一个 int16
```

既然知道每个元素占几个字节，要访问第 `i` 个元素，地址就能直接算出来：

```text
元素地址 = 基地址 + 元素大小 × 索引
```

代入上面的例子（基地址 `0x1000`，元素 2 字节）：

| 索引 | 计算 | 地址 |
| --- | --- | --- |
| 0 | 0x1000 + 2 × 0 | 0x1000 |
| 1 | 0x1000 + 2 × 1 | 0x1002 |
| 2 | 0x1000 + 2 × 2 | 0x1004 |
| 4 | 0x1000 + 2 × 4 | 0x1008 |

**这就是索引从 0 开始的原因**：访问第一个元素时，指针根本不需要移动。

据作者所知，是 C 语言引入了这个语法糖，用来简化**指针运算（pointer arithmetic）**。
今天几乎所有主流语言都从 0 开始编号，是因为它们的语法都受 C 影响。

> 指针运算本身超出本期范围，作者说想以后单独做一期。

### 1.4 数组不知道自己有多长

这一节最重要的结论：**在这个抽象层次上，数组自身不携带长度信息**。

它就是一块内存，没有 `length` 这种属性可以用来校验索引合不合法。
所以只要不小心，就很容易访问到数组边界之外。

越界时会发生什么，取决于这块数组在进程内存里的位置，有两种情况：

```text
情况 A：数组靠近进程内存边界
┌─────────────── 进程可用内存 ───────────────┐
│                          ┌────┬────┬────┐ │
│                          │ [0]│ [1]│ [2]│ │ ← arr[5] 落在这里
└──────────────────────────┴────┴────┴────┴─┘ ▲
                                              └── 越界，操作系统发现
                                                  -> segmentation fault，进程被杀

情况 B：数组离边界还很远
┌─────────────── 进程可用内存 ───────────────┐
│  ┌────┬────┬────┐                          │
│  │ [0]│ [1]│ [2]│ ???? ???? ????           │ ← arr[5] 落在这里
│  └────┴────┴────┘  ▲                       │
└────────────────────┼───────────────────────┘
                     └── 仍在进程内，操作系统不管
                         这段内存里不管原本装的什么，
                         都会被当成数组元素的类型来解释，程序继续跑
```

情况 B 看起来是"好消息"，因为程序不会崩。

但作者让你停下来想一想：

> 是程序崩掉好，还是程序带着"这个数组确实有第 5 个元素"的错误假设继续跑下去好？

如果这个数组代表某个人的消费记录呢。

## 2. 缓存：后面所有权衡的基准

在讲两种数据结构之前，先建立评判标准。

**缓存（cache）是嵌在 CPU 内部的一小块极快的内存**，唯一职责是保存一小片内存区域的副本。

```text
      ┌──────── CPU ────────┐
      │  寄存器             │
      │    ▲                │
      │    │ 快到离谱        │
      │  ┌────────┐         │
      │  │ cache  │         │  ← 很小
      │  └────────┘         │
      └──────▲──────────────┘
             │ 相对 CPU 速度而言，慢得多
        ┌─────────┐
        │  内存   │           ← 很大
        └─────────┘
```

| 术语 | 含义 |
| --- | --- |
| **缓存命中（cache hit）** | CPU 要的数据正好在 cache 里，装载进寄存器可以快上几个数量级 |
| **缓存未命中（cache miss）** | 不在 cache 里，只能去内存取 |

因为 cache 容量很小，装不下整个内存，所以**我们的数据应该尽可能紧凑**，才更容易整块被塞进 cache，提高命中率。

这听起来像是个无关痛痒的细节，但针对缓存做过优化的程序，性能提升是巨大的。
而且在现代计算里，cache 不是可选特性，是常态。

> 所以：**cache miss 是本期后面所有讨论的核心指标。**

## 3. 方案一：链表（LinkedList）

### 3.1 结构

想要一个能动态增长的列表，最简单的办法是：**哪里有空位就把元素放哪里**。

为此定义一个自定义类型 **节点（node）**，它包含两样东西：

```text
┌─────────────────┐
│ item   : u8     │ ← 列表里的一个元素
├─────────────────┤
│ next   : *node  │ ← 指向下一个节点所在的内存地址
└─────────────────┘
```

我们只需要在栈上保留一个指向**第一个节点**的引用（head）。

追加元素时：找一块够大的空闲内存放新节点，然后把原来的最后一个节点的 `next` 指向它。

```text
栈
┌────────┐
│ head ──┼──┐
└────────┘  │
            ▼
  ┌───┬───┐    ┌───┬───┐    ┌───┬───┐
  │ 7 │ ●─┼───►│ 3 │ ●─┼───►│ 9 │ ∅ │
  └───┴───┘    └───┴───┘    └───┴───┘
   0x4A20       0x9C08       0x1F70
       └── 地址完全不连续，散落在内存各处
```

这样一来，"列表会不会长大"这件事就彻底不用担心了。

### 3.2 代价：对缓存极不友好

链表有一个致命缺点：

> 链表的元素散落在整个内存空间里，因此**极不可能被缓存**。

```text
链表                          数组
散落各处                       挤在一起
┌──┐    ┌──┐                 ┌──┬──┬──┬──┬──┐
│  │    │  │                 │  │  │  │  │  │
└──┘    └──┘                 └──┴──┴──┴──┴──┘
    ┌──┐      ┌──┐           └──── 一次就能整块进 cache ────┘
    │  │      │  │
    └──┘      └──┘
每访问一个节点几乎都是 cache miss
```

在这一点上，**数组是明确的赢家**。

但绕了一圈我们又回到原点：数组功能太受限了。

## 4. 方案二：ArrayList

### 4.1 思路

顾名思义，ArrayList **仍然用数组**，只是用得更聪明：不只持有一个数组的引用，而是造一个数据类型，把引用和一些额外信息打包在一起。

```text
┌──────────────────────┐        ┌────┬────┬────┬────┬────┐
│ ptr      ────────────┼───────►│    │    │    │    │    │
├──────────────────────┤        └────┴────┴────┴────┴────┘
│ capacity = 5         │        └──── 堆上分配的空数组 ────┘
├──────────────────────┤
│ length   = 0         │
└──────────────────────┘
```

| 属性 | 含义 |
| --- | --- |
| `ptr` | 指向底层数组的引用 |
| `capacity` | 这个数组**最多能装几个**元素 |
| `length` | 这个数组**当前装了几个**元素 |

刚创建时数组是空的，所以 `length = 0`。

这个类型的核心思想是：**让它替我们管好这个数组**，所以它自带一组方法。

### 4.2 push：追加元素

`push` 接受一个值并把它加进数组，每加一个，`length` 加一。

```text
push(25)          push(13)          push(78)
┌──┬──┬──┬──┬──┐  ┌──┬──┬──┬──┬──┐  ┌──┬──┬──┬──┬──┐
│25│  │  │  │  │  │25│13│  │  │  │  │25│13│78│  │  │
└──┴──┴──┴──┴──┘  └──┴──┴──┴──┴──┘  └──┴──┴──┴──┴──┘
len=1 cap=5       len=2 cap=5       len=3 cap=5
```

但数组迟早会被填满。
填满之后再 push，就会越出数组边界，这正是我们用这个数据结构想避免的事。

所以在加元素之前必须先检查数组满没满，判断条件非常简单：

```text
length == capacity ?
```

伪代码：

```c
void push(ArrayList *list, int16_t value) {
    if (list->length == list->capacity) {
        // 满了：扩容
        grow(list);
    }
    list->ptr[list->length] = value;
    list->length += 1;
}
```

### 4.3 扩容：满了怎么办

如果满了，就得分配一个更大的数组。
**通常的做法是分配一个长度为原来两倍的新数组**。

四步：

```text
① 分配新数组（容量翻倍），更新 capacity 和 ptr

   旧: cap=5   ┌──┬──┬──┬──┬──┐
               │25│13│78│04│91│
               └──┴──┴──┴──┴──┘

   新: cap=10  ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
               │  │  │  │  │  │  │  │  │  │  │
               └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘

② 把旧数组的所有值复制过来

               ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
               │25│13│78│04│91│  │  │  │  │  │
               └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘

③ 旧数组不再需要，释放它的内存

④ 新数组有空位了，写入新元素，更新 length

               ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
               │25│13│78│04│91│66│  │  │  │  │
               └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
               len=6 cap=10
```

到这里我们就有了一个**尺寸可以动态增长的列表**。

### 4.4 扩容的代价，以及 with_capacity

扩容并不免费，它有两笔开销：

```text
   数组满了，需要扩容
          │
          ├─ 一次堆分配（heap allocation）
          │     └─ 上一期讲过，这一步可能很慢
          │
          └─ 把所有旧元素复制到新数组
                └─ 内存复制同样消耗时间
```

所以有一条实用建议：

> 如果你大致或精确知道这个 ArrayList 会装多少元素，并且在意性能，
> 就**在创建时直接指定初始容量**。
> 更少的扩容 = 更少的分配 = 更好的性能。

这正是 Rust 里 `Vec`（ArrayList 的等价物）除了 `new` 之外还提供 `with_capacity` 的原因：

```rust
// 容量为 0，之后一路扩容
let mut v: Vec<i32> = Vec::new();

// 一次性要够 1000 个元素的空间，后续 push 不再触发重新分配
let mut v: Vec<i32> = Vec::with_capacity(1000);
```

### 4.5 常数时间访问 + 顺手解决越界问题

ArrayList 从数组那里继承了一个重要特性：**常数时间访问（constant time access）**。

因为元素在内部就是存在一个数组里的，按位置取元素只不过是对数组做一次索引，时间复杂度 O(1)。

更妙的是，因为 ArrayList **知道自己的 length**，我们可以在索引之前先做一次校验：

```c
int16_t *get(ArrayList *list, size_t index) {
    if (index >= list->length) {
        return NULL;   // 或者 None / 抛一个正经的错误
    }
    return &list->ptr[index];
}
```

这就彻底解决了 1.4 节里裸数组无法避免的越界未定义行为。
虽然多了一步检查，但**时间复杂度仍然是常数**。

### 4.6 对照：链表的访问是线性的

之所以要强调这点，是因为链表在这方面差得多。

链表**不提供按索引的直接访问**：元素散落在内存里，没有任何公式能算出第 `i` 个元素的地址。

要拿到第 `i` 个元素，只能**从头节点开始一个一个走过去**：

```text
访问 list[3]

head
 │
 ▼
┌───┬───┐  ┌───┬───┐  ┌───┬───┐  ┌───┬───┐
│ 7 │ ●─┼─►│ 3 │ ●─┼─►│ 9 │ ●─┼─►│ 5 │ ∅ │
└───┴───┘  └───┴───┘  └───┴───┘  └───┴───┘
   走1        走2        走3        到了

时间复杂度：O(n)，线性
```

而且时间复杂度还不是唯一的问题：

> 就算你要的那个元素恰好在 cache 里，**路上经过的那些节点通常不在**。
> 于是遍历过程会被 cache miss 拖得很慢。

### 4.7 删除操作的对比

**ArrayList 删除**：删掉一个元素之后，后面所有元素都得往前挪一位。

```text
remove(1)

前  ┌──┬──┬──┬──┬──┐
    │25│13│78│04│91│
    └──┴──┴──┴──┴──┘
        ✗  └──┬──┘
              └── 这 3 个都要往前搬

后  ┌──┬──┬──┬──┬──┐
    │25│78│04│91│  │
    └──┴──┴──┴──┴──┘
```

内存复制是消耗时间的，所以**删除位置决定了快慢**：

```text
删靠后的元素            删靠前的元素
┌──┬──┬──┬──┬──┐      ┌──┬──┬──┬──┬──┐
│  │  │  │  │✗ │      │✗ │  │  │  │  │
└──┴──┴──┴──┴──┘      └──┴──┴──┴──┴──┘
      要挪 0 个              要挪 4 个
        快                     慢
```

当然，具体影响还取决于列表里有多少元素。

**链表删除**：链表拥趸会说这里链表更快，而且确实是真的。
删一个节点只需要两步：

```text
删除中间那个节点

前  ┌───┬───┐  ┌───┬───┐  ┌───┬───┐
    │ 7 │ ●─┼─►│ 3 │ ●─┼─►│ 9 │ ∅ │
    └───┴───┘  └───┴───┘  └───┴───┘

①  把前一个节点的 next 改指向后一个节点
②  free 掉被删节点的内存

后  ┌───┬───┐             ┌───┬───┐
    │ 7 │ ●─┼────────────►│ 9 │ ∅ │
    └───┴───┘             └───┴───┘
```

不需要任何搬移，时间复杂度是**常数**。

但别忘了：**为了改这个节点，你得先在内存里找到它**。
而链表的查找因为缓存问题，效率并不好。

### 4.8 别急着给链表判死刑

作者在这里特意提醒（原话强调了"could"）：

> 和通常的说法相反，链表在某些场景下**仍然可能**是更好的选择。
> 不是所有架构的效率都建立在缓存或者数据搬移指令之上。

最终一句话：

> 选哪种数据结构取决于很多因素。
> 一旦进入低层世界，你通常会发现自己在给多个方案跑基准测试，
> 想把硬件的每一滴效率都榨出来。

### 4.9 小结对比表

| 操作 | ArrayList | LinkedList |
| --- | --- | --- |
| 按索引访问 | O(1)，且缓存友好 | O(n)，且一路 cache miss |
| 追加 | O(1)，偶尔触发扩容（分配 + 复制） | O(1)，但要找空位 |
| 删除（已定位） | O(n)，需要搬移后续元素 | O(1)，改个指针 |
| 删除（含查找） | 查找 O(1) + 搬移 | **查找 O(n) 且缓存不友好** |
| 缓存局部性 | 好，元素连续 | 差，元素散落 |
| 内存开销 | 可能有未使用的 capacity | 每个元素额外一个指针 |

## 5. 泛型：怎么不为每种类型写一遍

上面两个例子都是为**某一种具体元素类型**写的：

```text
ArrayList  ->  只能装 16 位有符号整数
LinkedList ->  只能装 8 位无符号整数
```

不想为每种类型复制一份代码，答案是**泛型（generics）**。

但泛型在不同语言里的实现方式**完全不同**，这直接决定了内存布局和缓存表现。

### 5.1 Rust：编译期单态化

在 Rust 里声明一个泛型类型时，编译器会：

```text
① 找到你用到这个泛型的每一处实例
② 为那个具体类型生成一份专门的源代码
③ 把泛型类型替换成生成出来的类型
```

整个过程在**编译期**完成，对我们不可见。

结果是：**内存里的数据结构和我们期待的一模一样**。

```text
Vec<i32>
┌────┬────┬────┬────┬────┐
│ 25 │ 13 │ 78 │ 04 │ 91 │   ← 值本身连续排列
└────┴────┴────┴────┴────┘
```

### 5.2 Java：非基本类型变成指针数组

Java 走的是另一条路。
**如果数组装的不是基本类型（primitive），虚拟机实际创建的不是值的数组，而是指针的数组**，每个指针指向元素真正所在的内存地址。

```text
Java: MyObject[] arr

┌────┬────┬────┬────┐
│ ●  │ ●  │ ●  │ ●  │   ← 数组里存的是地址，连续且等宽
└─┼──┴─┼──┴─┼──┴─┼──┘
  │    │    │    │
  │    │    │    └──────────────────────► ┌──────────┐
  │    │    │                             │ MyObject │
  │    │    └────────► ┌──────────┐       └──────────┘
  │    │               │ MyObject │
  │    └► ┌──────────┐ └──────────┘
  │       │ MyObject │
  └►      └──────────┘
     ┌──────────┐
     │ MyObject │        实际对象散落在堆上各处
     └──────────┘
```

语言把这些指针全部藏起来了，所以我们以为在操作值数组，实际上不是。

如果你觉得这对缓存不利，**没错**。
这正是 Java 被认为是一门相当快、但**仍然比系统级语言慢**的语言的原因之一。

### 5.3 最糟的组合，以及 C 里的初学者陷阱

把指针数组的思路套到链表上，情况会更糟：

```text
节点里不再是「元素 + 下个节点指针」，而是「元素的指针 + 下个节点的指针」

┌───┬───┐      ┌───┬───┐      ┌───┬───┐
│ ● │ ●─┼─────►│ ● │ ●─┼─────►│ ● │ ∅ │
└─┼─┴───┘      └─┼─┴───┘      └─┼─┴───┘
  │              │              │
  ▼              ▼              ▼
 值             值             值
（又在别处）    （又在别处）    （又在别处）

每取一个元素要跳两次内存 -> 缓存噩梦
```

作者说这很好笑的一点是：这种结构在 **C** 里非常常见。
因为 C 没有泛型，初学者很容易被诱导写出这种东西。

## 6. 脚本语言是怎么做的

首先要记住一个前提：

> 脚本语言通常**不会被编译成机器码**。
> 它们依赖一个专门的程序来解释脚本，从而**模拟**出期望的行为。
> 这类程序常被称为**解释器（interpreter）**或**虚拟机（virtual machine）**。

当然，这个模拟过程最终还是跑在真实硬件上。

所以当我们声明一个"数组"时，背后是解释器造了一个专门的数据结构来模拟数组。

### 6.1 Python：指针数组，但指向的是 object

Python 的官方解释器是开源的，可以直接去看实现。
里面有一个类型叫 **`PyListObject`**，这就是我们创建 Python list 时解释器生成的东西。

文档注释里写得很清楚：这个类型不过是**一个对象指针的数组**。

所以它和 Java 处理非基本类型的方式很像，都是"指向值的地址的数组"。

**但有一个关键区别：**

| | Java | Python |
| --- | --- | --- |
| 数组里的指针指向 | 全部是**同一类型**的值 | **object**，也就是可以指向不同类型的值 |

```text
my_list = [42, "hello", 3.14]

┌────┬────┬────┐
│ ●  │ ●  │ ●  │   ← 三个指针，大小完全相同
└─┼──┴─┼──┴─┼──┘
  │    │    │
  │    │    └───────────► ┌────────┐
  │    │                  │ float  │
  │    │                  └────────┘
  │    └────────► ┌────────┐
  │               │  str   │
  │               └────────┘
  └───► ┌────────┐
        │  int   │
        └────────┘
```

**这解释了为什么 Python 的 list 能装多种类型的元素：因为这些指针的大小都是一样的。**

索引一个 Python list 时，解释器分两步模拟：

```text
my_list[1]
    │
    ├─ ① 索引那个指针数组，拿到第 1 个指针
    └─ ② 顺着指针读出它指向的值
```

### 6.2 JavaScript：数组根本不是数组

简单说：

> **JavaScript 的数组不是数组，是哈希表（hashmap）。**

JavaScript 根本不关心内存里的数组。
声明一个 JS 数组时，引擎创建的是一个**哈希表，键就是索引**。

```text
const arr = [];
arr[0] = "a";
arr[1] = "b";

内部实际上是：
┌───────┬───────┐
│  key  │ value │
├───────┼───────┤
│  "0"  │  "a"  │
│  "1"  │  "b"  │
└───────┴───────┘

所以 arr[0] 只是「按键取值」的语法糖
```

作者给了一个可以自己动手验证的方法：

```javascript
const arr = [];
arr["hello"] = 123;   // 用一个非数字的键
console.log(arr);      // [ hello: 123 ]
console.log(arr.length); // 0
```

索引这个动作，本质上就是**按键从哈希表里取元素**的语法糖。

作者承认（虽然很多人说他不喜欢 JavaScript）这是个很怪但很聪明的方案。
最妙的地方在于：

```text
arr[1000000] = "x";

数组实现：需要分配一个能装 100 万个元素的数组   ← 灾难
哈希表实现：只是往表里再插一条键为 1000000 的记录 ← 无事发生

┌──────────┬───────┐
│   key    │ value │
├──────────┼───────┤
│   "0"    │  "a"  │
│   "1"    │  "b"  │
│ "1000000"│  "x"  │
└──────────┴───────┘
```

## 7. 核心总结

```text
为什么数组不能随便长大
│
├── 底层的数组只是一块连续内存
│   ├── 增长会覆盖后面还在用的值（CPU 只认地址，不认变量名）
│   ├── 必须知道 类型 × 长度 才能算出要占多少空间
│   ├── 索引 = 基地址 + 元素大小 × 索引  ->  所以从 0 开始
│   └── 它不知道自己多长  ->  越界要么 segfault，要么读到垃圾还继续跑
│
└── 两种补救方案
    │
    ├── LinkedList：哪有空位放哪
    │   ├── 增长完全自由
    │   ├── 删除（已定位）O(1)
    │   ├── 访问 O(n)
    │   └── 元素散落 -> cache miss 是常态  ← 主要败因
    │
    └── ArrayList：还是用数组，但包一层
        ├── ptr + capacity + length
        ├── 满了就分配两倍大的新数组、复制、释放旧的
        │   └── 一次堆分配 + 一次全量复制  ->  能预估就用 with_capacity
        ├── 访问 O(1) 且缓存友好，还能顺手做边界检查
        └── 删除要搬移后续元素，越靠前越慢

泛型让它们能装任意类型，但实现方式决定内存布局
├── Rust：编译期单态化  ->  值连续排列，最优
└── Java：非基本类型退化成指针数组  ->  缓存代价

脚本语言：干脆不用真数组
├── Python：PyListObject = 指向 object 的指针数组
│           指针等宽 -> 所以能混装不同类型
└── JavaScript：哈希表，键就是索引
                arr[1000000] 不会分配 100 万个格子
```

> 底层的数组是一块不知道自己有多长的连续内存。
> ArrayList 用「多存两个数字 + 满了就翻倍」把它变得能长大，同时保住了缓存局部性；
> LinkedList 用「哪有空位放哪」换来了增长自由，代价是把每一次访问都变成一次 cache miss。
> 而脚本语言的做法是：既然真数组这么麻烦，那就别用真数组。
