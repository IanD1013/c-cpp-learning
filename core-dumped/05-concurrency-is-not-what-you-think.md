# 并发不是你想的那样（Concurrency）

> 视频来源：Core Dumped -《CONCURRENCY IS NOT WHAT YOU THINK》

## 0. 这一期在讲什么

你的电脑能同时跑上千个程序，你大概会把功劳记在多核上。
这几年 CPU 厂商一直在暗示「核越多越快」，这个联想很自然。

但有个事实容易被忽略：**多任务（multitasking）在单 CPU 时代就已经存在了**。
80 年代中期的 Commodore Amiga 和 Apple Macintosh 只有一个处理器，照样能同时跑多个程序。

这一期讲的就是让它成立的那项技术：**并发（concurrency）**。
线索是这么一条：

```text
为什么需要并发（历史）
   -> 怎么造出「同时」的错觉（时间片交错）
      -> CPU 到底怎么执行指令（fetch-decode-execute）
         -> 操作系统凭什么能把 CPU 抢回来（中断 + 硬件定时器）
            -> 多核到底改变了什么（并发 vs 并行）
```

---

## 1. 起点：机器太贵，一秒都不能闲

早期计算机被称作**大型机（mainframe）**，一台占满整个房间。
贵到只有政府、大公司和少数大学买得起，而且就算是这些机构也买不起几台，何况还有运行和维护成本。

结果就是：**访问计算机需要预约，经常要提前几周排期。**

晶体管出现之后机器变小了，也变快了，但**操作**依然极其麻烦。

### 1.1 跑一个 Fortran 程序在当时是什么体验

现在写 Python 是「源码丢进去就跑」。
当时不是。程序存在磁带上，每一步都要人工挂带、等待加载：

```text
① 程序员挂上「编译器」磁带
      │
      └─► 等待编译器加载进主存 ................ CPU 空闲
② 输入 Fortran 源码
      │
      └─► 编译器输出汇编（Assembly）
③ 汇编还不能执行，先存起来（磁带 / 打孔卡）
④ 程序员卸下磁带，挂上「汇编器」磁带
      │
      └─► 等待汇编器加载进主存 ................ CPU 空闲
⑤ 汇编器把汇编翻译成机器码
⑥ 终于可以执行程序了
```

中间任何一步出错，可能就得整套流程重来。

### 1.2 真正的浪费：CPU 在等人

关键不在于程序员累，而在于：

* 挂磁带的时候，CPU 空转；
* 程序员敲命令的时候，CPU 空转；
* 而且**别的程序员还不能用**，因为机器被设计成一次只服务一个用户。

一台值几百万的机器，大部分时间在等一个人的手速。
拥有者当然不能接受，他们希望机器被用得越满越好。

早期操作系统就是在这个压力下诞生的（这段历史值得单独一期）。
对本期有用的结论只有一条：

> 研究者想到的办法是，让**多个用户同时连到同一台计算机**，由操作系统来仲裁谁能用硬件。

### 1.3 哑终端（dumb terminal）

每个用户通过一台 IO 设备接入，早期是电传打字机（teletype writer），70 年代后期主流是**哑终端**。

别被样子骗了，它看着像台老电脑，其实**只是一块屏幕加一个键盘**：把命令发给主机，把主机的输出显示出来。

```text
   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │ 哑终端 A │   │ 哑终端 B │   │ 哑终端 C │   ← 只有屏幕 + 键盘
   └────┬─────┘   └────┬─────┘   └────┬─────┘
        │              │              │
        └──────────────┼──────────────┘
                       ▼
              ┌──────────────────┐
              │  唯一的那台主机  │
              │  （操作系统仲裁）│
              └──────────────────┘
```

一旦和主机断开，它就完全没用了，「哑」这个名字由此而来。

顺带一提：你现在用来敲命令的那个小程序之所以叫 **terminal（终端）**，就是从这里来的。

这个安排让机器可以「在 A 跑程序的时候，B 正在加载、C 正在敲键盘」。

## 2. 核心技巧：把程序切碎，交错执行

上面的安排解决了「有人在等 IO」的情况。
但如果**多个用户同时都准备好要跑程序**呢？

只有一个处理单元，必须共享。

回忆一下程序的定义：**程序就是一串给 CPU 逐条执行的指令。**

最直接的做法是**顺序执行**：

```text
顺序执行（sequential）
┌────────────────────┬──────────────┬───────────────────┐
│      程序 A        │    程序 B    │      程序 C       │
└────────────────────┴──────────────┴───────────────────┘
 CPU 一直忙 ✔                      C 的用户等到天荒地老 ✘
```

CPU 利用率是满的，但用户要等很久才能看到自己程序的第一点结果。

改进办法是把程序拆成更小的片段，**交错（interleave）**执行：

```text
交错执行（concurrent）
┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐
│ A │ B │ C │ A │ B │ C │ A │ B │ C │ A │ B │ C │
└───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘
 时间 ───────────────────────────────────────────►
 三个用户几乎同时看到结果 ✔
```

你可能会说：这不还是一条一条顺序执行吗，有什么意义？

意义在于**速度差**。
计算机哪怕是早期的，做计算也比人快几千倍。
每个小片段执行得极快，快到人类感知不出切换，于是产生了「所有程序在同时运行」的**错觉**。

这类操作系统有个专门的名字：**分时系统（time-sharing system）**。
**Multics** 是历史上最早的分时操作系统之一。

### 2.1 个人电脑绕了一圈才补上这一课

70 年代末到 80 年代初，计算机进入家庭市场。
因为设计目标是一次给一个人用，它们得名**个人计算机（personal computer）**，这个名字沿用至今。

有意思的是，最早的个人电脑**一次只能跑一个程序，不支持多任务**。

但 Multics（以及受它启发而生的 Unix）当时早已存在，并发已经是成熟技术。
所以没过多久，PC 厂商就开始出货支持多任务的个人电脑。

区别只在用途：

| | 大型机时代 | 个人电脑时代 |
| --- | --- | --- |
| 并发用来做什么 | 让**多个用户**同时用一台机器 | 让**一个用户**同时跑多个程序 |

### 2.2 一个必须澄清的误解

**程序并不是真的被切开、拆散、混着装进内存的。**

那种「把 A 和 B 剁碎再交叉摆放」的动画，画的是**执行的先后顺序**，不是内存里的实际布局。

程序照常完整地加载进内存。
真正被切换的，是**下一条指令的地址**。

要看懂这句话，得先看 CPU 是怎么走指令的。

## 3. 前置知识：CPU 的 fetch-decode-execute 循环

CPU 内部有几个特殊寄存器，本期只关心两个：

| 寄存器 | 作用 |
| --- | --- |
| 地址寄存器（address register） | 存放**下一条**要执行的指令在内存中的位置 |
| 指令寄存器（instruction register） | 存放**当前**正在执行的这条指令本身 |

一轮循环是这样的：

```text
        ┌──────────────────────────────────────┐
        │                                      │
        ▼                                      │
  ① fetch（取指）                              │
     按地址寄存器指的位置，把指令读出来        │
     复制进指令寄存器                          │
        │                                      │
        ▼                                      │
  ② decode（译码）                             │
     搞清楚这条指令要干嘛：加法？减法？拷贝？  │
        │                                      │
        ▼                                      │
  ③ execute（执行）                            │
     真正做这件事                              │
        │                                      │
        ▼                                      │
  ④ 地址寄存器 +1，指向下一条指令 ─────────────┘
```

这就是 CPU 一步一步走完整个程序的方式：**取指、译码、执行**，无限重复。

### 3.1 跳转指令：地址寄存器是可以被改写的

还有一类**跳转指令（jump）**，它直接修改地址寄存器的值，让 CPU 跳到某条指定指令，而不是顺着往下走。

```text
正常流程                      跳转
addr: 100 ──► 101 ──► 102     addr: 100 ──► 101 ──┐
                                                  │  jump 40
                              addr: 40  ◄─────────┘
```

条件判断和循环就是靠它实现的。

### 3.2 于是切换进程变得非常廉价

既然地址寄存器可以被随意改写，那么：

> 程序照常完整加载进内存，操作系统只要**改一下地址寄存器的值**，CPU 就换去跑另一个程序了。

不需要搬内存，不需要切开程序。
「并发」在实现层面，本质上就是一场对地址寄存器的反复改写。

但这引出了本期真正的难题：

> **操作系统自己也是软件，它也需要 CPU 才能干活。那它是什么时候被执行的？**

## 4. 进程、就绪队列、调度器、分派器

一个程序跑起来之后，就被称为**进程（process）**。

操作系统用一个专门的数据结构保存每个运行中进程的信息（状态快照、下一条指令位置等）。
这些进程排成一个**队列**，由操作系统中一个叫**调度器（scheduler）**的部分负责管理。

CPU 空出来的时候，另一个组件**分派器（dispatcher）**登场：

```text
        就绪队列（queue）
   ┌──────┬──────┬──────┬──────┐
   │ P1   │ P2   │ P3   │ P4   │
   └──┬───┴──────┴──────┴──────┘
      │  ① 取出队首
      ▼
 ┌─────────────┐
 │ dispatcher  │  ② 读取该进程保存的信息
 └──────┬──────┘
        │  ③ 设置地址寄存器
        ▼
    ┌────────┐
    │  CPU   │  ──► 开始执行 P1 在内存中的代码
    └────────┘
```

这里省略了大量细节，实际的 CPU 调度复杂得多，作者说会单独做一期讲 **CPU 调度**。
本期只需要这个骨架。

## 5. 操作系统靠什么把 CPU 拿回来：中断

我们写程序时，从来没有写过「现在把 CPU 还给操作系统」这样的指令。
那操作系统是怎么重新获得控制权的？

答案是：**你其实一直在求它办事。**

程序离不开操作系统：

* 打开文件；
* 读写文件；
* 申请内存。

这些操作都不是程序自己能完成的，它们都是在**和操作系统交互**。
而这种交互在硬件层面是通过**中断（interruption）**发生的。

### 5.1 一次中断发生了什么

中断是发给 CPU 的信号。收到之后：

```text
  用户程序正在跑
        │
        │  发生中断（比如程序请求读文件）
        ▼
  ① CPU 暂停当前任务
  ② 给自己拍一张快照（保存寄存器等状态）存进内存
  ③ 跳到内存中一个预先约定好的位置
        │
        ▼
  ┌───────────────────────────────────────┐
  │ 中断服务例程                          │
  │ (interrupt service routine, ISR)      │
  │ 位于操作系统自己的那块内存区域        │
  └───────────────────────────────────────┘
        │
        ▼
  地址寄存器现在指着操作系统的代码
  ==> 操作系统重新拿到了 CPU
```

只有操作系统内核能和硬件打交道，所以程序做 IO 时会大量使用中断。

**这就是操作系统重获 CPU 控制权的方式。**

而一旦它拿回了 CPU，它做的就不止是处理这次中断，还会顺手去干别的活，**包括调度进程**。

### 5.2 完整的一轮切换

IO 操作往往很慢，所以：

```text
① 进程 P1 触发中断（请求 IO）
        │
② 操作系统接管
   ├─ 把 P1 当前的状态快照写回 P1 的进程信息里
   └─ 把 P1 放回队列（它要等硬件响应）
        │
③ dispatcher 从队列里挑出 P2，设置 CPU 去执行它
        │
④ P2 一直用 CPU，直到它也需要做 IO，于是又把控制权交回操作系统
        │
⑤ 循环往复 ......
        │
⑥ 轮到 P1 时，从队列取出它
   ├─ 读出之前保存的状态，恢复到 CPU 里
   └─ 跳回用户程序里正确的位置，从断点处继续
```

注意第 ⑥ 步：**恢复现场之后，程序完全感觉不到自己被中断过。**

这就是操作系统在多个进程之间轮换 CPU 的全过程。

## 6. 这个方案的致命漏洞：协作式调度

上面的机制有一个巨大的问题：

> 一旦 CPU 被分配给某个进程，它会**一直占着**，直到该进程**自愿**释放。

自愿释放只有两种方式：

1. 进程结束了；
2. 进程调用了操作系统，进入等待状态。

那么，考虑一个**死循环**：

```text
loop:
    ...          ← 循环体里没有任何 IO、没有任何系统调用
    jump loop
```

```text
  ┌──────────────────────────────┐
  │  CPU                         │
  │   ▲                          │
  │   └── 永远在这个循环里打转   │
  └──────────────────────────────┘
        没有中断
        ==> 操作系统永远拿不回 CPU
        ==> 其他所有程序饿死
```

如果一个进程有意或无意地**不触发任何中断**，操作系统就再也回不来了。

在现代语境下这是严重的**安全风险**：恶意程序可以靠这一手独占 CPU 资源，让别的程序完全没法运行。

这种依赖进程主动配合的调度方式叫做：

> **协作式调度（cooperative scheduling）**，也叫**非抢占式调度（non-preemptive scheduling）**。

---

## 7. 补丁只能来自硬件：定时器与抢占式调度

这个问题**没有软件层面的解法**。
道理很直接：操作系统本身也需要 CPU 才能执行，而它现在根本拿不到 CPU。

所以必须由硬件介入，办法是一个**硬件定时器（hardware timer）**。

它的逻辑非常朴素：

```text
  设定一个时间上限  ──►  开始倒计时  ──►  时间到  ──►  触发中断
                                                          │
                                                          ▼
                                              操作系统必然重获控制权
```

定时器通常**直接做在 CPU 内部**。

所以分派器在把 CPU 交给任何进程之前，会先用一条**特权指令（privileged instruction）**设置并启动定时器：

```text
 dispatcher
   ├─ ① 特权指令：设置定时器，启动倒计时   ← 新增的这一步是关键
   ├─ ② 设置地址寄存器
   └─ ③ 交出 CPU
                 │
                 ▼
       进程开始跑，两种结局：
       ├─ 它自己触发中断，主动交还 CPU（老路径，仍然有效）
       └─ 它赖着不放，定时器到点，强制中断 ← 兜底
```

这种机制叫**抢占式调度（preemptive scheduling）**，安全性大幅提升。

但有一个前提：**操作系统能不能用抢占式调度，取决于硬件支不支持。**

### 7.1 两种调度方式对比

| | 协作式 / 非抢占式 | 抢占式 |
| --- | --- | --- |
| 操作系统何时拿回 CPU | 进程自愿交还时 | 进程自愿交还，**或**定时器到点 |
| 死循环会怎样 | 整台机器卡死 | 到点被强制打断 |
| 依赖 | 进程的自觉 | 硬件定时器支持 |
| 安全性 | 可被恶意程序独占 | 有兜底 |

### 7.2 一段有意思的历史

* **Windows** 直到 **3.x** 都还在用协作式调度；从 **Windows 95** 开始才换成抢占式调度。
* **Multics** 从**一开始**就被设计成支持抢占式调度。

而 Multics 是 **1960 年代**的系统。
也就是说，这项技术比很多人以为的要古老得多，家用系统反而是后来才补上的课。

## 8. 那多核到底改变了什么

快速在进程之间切换可以制造「同时执行」的错觉。
但是：

> 运行的进程越多，每个进程**重新轮到 CPU** 的间隔就越长，卡顿就越明显。

```text
3 个进程                     30 个进程
A B C A B C A B C            A B C ... Z ... A
└─┬─┘                        └────────┬──────┘
 轮转很快，察觉不到           等一圈的时间变长 ==> 明显卡顿
```

解法分两路：

**软件侧**：设计更复杂的调度器，更高效地管理进程。
（作者说这会在未来一期展开。）

**硬件侧**：

1. 提高 CPU 主频，让每个进程更快轮到。
   受**物理限制**，这条路走不远。
2. 真正的突破：**在同一块芯片上放多个处理单元**，也就是**多核（multi-core）**。

多核之后，调度器可以把不同的程序分配到不同的处理器上，实现**真正的并行（parallelism）**，是名副其实的同时执行。

```text
单核（并发 / concurrency）
core0: │A│B│C│A│B│C│A│B│C│      ← 交错，制造「同时」的错觉

多核（并行 / parallelism）
core0: │ A A A A A A A A A │    ← 真的在同一时刻一起跑
core1: │ B B B B B B B B B │
core2: │ C C C C C C C C C │
```

但注意：

> 进程数**通常仍然多于核数**，所以多核系统里依然需要并发，用来把处理资源在众多进程之间高效分配。

**并发没有被多核取代，它是多核之上仍然生效的那一层。**

### 8.1 一句话区分

> **并发是同时“应付”很多件事，并行是同时“做”很多件事。**
>
> Concurrency is about dealing with lots of things at once,
> but parallelism is about doing lots of things at once.

## 10. 核心总结

```text
一个 CPU 怎么“同时”跑很多程序
│
├── 为什么需要它（历史）
│   ├── 大型机贵到要提前几周预约
│   ├── 挂磁带、敲命令的时候 CPU 全程空转
│   └── 而且一次只服务一个用户  ->  浪费无法接受
│       └── 解法：多用户接入，操作系统仲裁硬件（哑终端 / Multics）
│
├── 怎么造出“同时”的错觉
│   ├── 顺序执行：CPU 满载，但用户等太久
│   └── 切成小片交错执行 + 计算机比人快几千倍  ->  错觉成立
│       └── 程序并没有被真的切碎装进内存，被切换的只是“下一条指令的地址”
│
├── 底层机制
│   ├── fetch -> decode -> execute，地址寄存器每轮 +1
│   ├── jump 指令能改写地址寄存器  ->  切进程只是改一个值，极廉价
│   ├── 进程信息排成队列，scheduler 管队列，dispatcher 设地址寄存器
│   └── 操作系统靠“中断”重获 CPU
│       ├── 程序做 IO / 申请内存必须求助操作系统
│       └── 中断 = 存快照 -> 跳到 ISR（在操作系统内存区）-> OS 拿回 CPU
│
├── 漏洞与补丁
│   ├── 协作式调度：进程不自愿交还就永远占着
│   │   └── 死循环 + 无中断  ->  整机失控，安全风险
│   └── 抢占式调度：CPU 内的硬件定时器到点强制中断（特权指令启动）
│       └── Windows 3.x 之前协作式，Windows 95 起抢占式；Multics 从 1960 年代起就是抢占式
│
└── 多核改变了什么
    ├── 进程一多，轮转间隔变长  ->  卡顿
    ├── 提频有物理上限，于是把多个处理单元放进一块芯片
    ├── 多核 = 真并行，不同程序分到不同核
    └── 但进程数依然多于核数  ->  并发仍然必需
```

> 并发不是多核带来的新东西，它是 1960 年代为了不让昂贵的 CPU 空转而发明的技术。
> 它的全部秘密只有两件事：**改写地址寄存器**让 CPU 在程序之间跳来跳去，
> 以及用**中断和硬件定时器**保证操作系统总能把 CPU 拿回来。
> 多核带来的是并行，而并发是在核数不够时，依然让所有人都觉得「我的程序正在运行」的那层错觉。
