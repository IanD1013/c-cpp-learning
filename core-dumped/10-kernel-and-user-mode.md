# 内核态与用户态：一个比特如何守住操作系统的完整性

## 0. 这一期在讲什么

学操作系统时最先听到的一句话是：**操作系统是硬件和用户程序之间的中间人（intermediary）**。
用户程序不能绕过操作系统直接访问硬件资源。

但只要往下想一层，这句话就站不住了：

操作系统是软件，用户程序也是软件。
两者都是用编程语言写出来、编译成机器码的东西。
既然是同一类东西，**为什么用户程序不能反过来压制操作系统，夺走整台计算机的控制权？**

这一期的答案是：**光靠软件解决不了这个问题，必须要硬件配合**。
而硬件提供的核心机制，小到只有**一个比特**。

作者在开头有一段免责声明，需要保留：
本期内容为了便于理解做了大量简化，展示的实现和汇编代码**不对应任何真实平台或架构**。

本期的推理链：

```text
想让某个软件比别的软件权力更大
        │
        ▼
把指令集切成两半：普通指令 + 特权指令（privileged instructions）
        │
        ▼
用一个 1 比特寄存器（mode bit）决定当前能不能执行特权指令
        │
        ▼
谁能翻转这个比特？靠中断（interrupt）
        │
        ▼
中断跳到哪，谁就拿到内核态 -> 现代做法是把操作系统放在那里
        │
        ▼
用户程序想用硬件，只能主动中断自己（系统调用 system call）
        │
        ▼
如果程序死循环不肯中断自己？加一个硬件定时器（抢占式 preemptive）
```

## 1. 硬件的解法：把指令集切成两半

每个处理器都有一组它能执行的动作，叫**指令集（instruction set）**。

如果我们想让一个软件对系统的控制力**大于**另一个软件，办法很直接：
在指令集里划出一个**子集**，规定不是所有进程都能用这些指令。

很多架构定义了这类指令，称为**特权指令（privileged instructions）**。

要执行这个规定，硬件就必须支持不同的**运行模式（operational modes）**。
常见做法是使用一个特殊的**单比特寄存器**，里面只能是 1 或 0。

这个寄存器叫 **mode bit（模式位）**。

| mode bit | 模式名 | 能执行什么 |
| --- | --- | --- |
| `1` | 特权模式（privileged mode） | 指令集里的**任何**指令，包括特权指令 |
| `0` | 受限模式（restricted mode） | 只能执行普通指令，**不能**执行特权指令 |

```text
              ┌───┐
   mode bit   │ 1 │  ──►  特权模式：整个指令集都能用
              └───┘

              ┌───┐
   mode bit   │ 0 │  ──►  受限模式：特权指令被拒
              └───┘
```

### 它是怎么起作用的

CPU 内部用**组合逻辑电路（combinational logic circuits）**来译码进来的指令。

对**普通指令**来说，mode bit 几乎没有影响，因为它们在任何模式下都能跑。
但当译码器遇到**特权指令**时，mode bit 的值就决定了当前进程有没有资格执行它。

```text
        取到一条指令
              │
              ▼
        ┌──────────┐
        │  译码器   │
        └────┬─────┘
             │
   ┌─────────┴──────────┐
   │                    │
普通指令             特权指令
   │                    │
   ▼                    ▼
直接执行           检查 mode bit
（不看 mode bit）        │
                ┌───────┴───────┐
             = 1│               │= 0
                ▼               ▼
              执行            拒绝执行
```

于是结论成立：**特权指令只有在处理器处于特权模式时才能被执行。**

## 2. 最微妙的一环：谁能翻转 mode bit

这里立刻会冒出一个问题：**怎么翻、谁能翻这个 mode bit？**

这是整个机制**最精密（most delicate）**的部分。
因为如果任何用户进程都能自己切到特权模式，这个特性就完全没有意义了。

处理方式可以有好几种，但通常的实现是通过**中断（interrupt）**。

### 先补上中断是什么

暂时把 mode bit 放一边。

处理器运行程序时，地址寄存器指向**下一条要执行的指令**的内存地址。

**中断**是发给 CPU 的一个信号，通知它「有事件发生了」。
比如用户按下一个键、移动鼠标，都可以触发中断，让系统对事件作出反应。

信号被接收时，会导致处理器**暂停当前进程**，并**跳转到一个特定的内存位置**。
这个内存位置里存着 CPU 用来处理该中断的可执行代码。

这段例程（routine）可以拆成四步：

```text
   正在执行的进程
   ┌───────────────┐
   │ ...           │
   │ 指令 N        │ ◄── 中断信号到达
   │ 指令 N+1      │
   └───────────────┘
           │  暂停，跳转到中断处理位置
           ▼
   ┌────────────────────────────────────┐
   │ ① 保存被中断进程的状态              │
   │ ② 处理中断（例如调用打印字符串的例程）│
   │ ③ 恢复被中断进程的状态              │
   │ ④ 执行 interrupt return 指令        │
   └────────────────┬───────────────────┘
                    │  跳回去
                    ▼
   ┌───────────────┐
   │ 指令 N+1      │ ◄── 从这里继续执行
   └───────────────┘
```

第四步的 `interrupt return` 是一条专门的指令，作用是跳回被中断的进程并让它恢复执行。

这就是中断的基本流程：**临时挂起当前进程，把控制权转交给另一段例程。**

### 把两件事接起来

现在回到 mode bit。

中断不仅能让 CPU 的程序计数器跳转，**还能自动把 mode bit 翻成 1**。

这意味着：**位于那个内存位置的代码，不但拿到了 CPU 的控制权，而且是以特权模式拿到的。**

```text
   中断触发
       │
       ├──►  程序计数器 跳到固定内存位置
       └──►  mode bit 自动置 1

                   ▼
        住在那块内存里的代码
        ＝ 拿到 CPU ＋ 拿到特权模式
```

作者在这里特意强调了一句要说清楚的话：

**任何可执行实体都可以被加载进这块内存区域。**
一个网页浏览器、一个文本编辑器，什么都行。

这就是为什么必须极端小心：
一旦某个实体拿到了特权模式，它在这台计算机里**几乎可以做任何事**，
其中就包括「确保没有别的进程能拿到特权模式」。

**现代的做法是保证操作系统被加载在那里**，这样它就能用特权指令维持对整个系统的完全控制。

## 3. 于是有了内核态和用户态

支持运行模式的处理器就是**专门为此设计**的。

* **特权模式**本来就是留给操作系统**内核（kernel）**用的，所以通常叫做**内核态（kernel mode）**。
* **受限模式**本来就是留给用户程序的，用来防止它们压制操作系统，所以通常叫做**用户态（user mode）**。

### 内核态能做、用户态不能做的事

**① 直接操作 IO 设备**

网卡、显卡、硬盘，以及显示器、键盘这类外设。
直接操纵这些设备需要特权指令，也就是说 CPU 只有在内核态才能做。

**② 操作内存管理单元（MMU, memory management unit）**

MMU 是一个特殊的硬件部件，负责**限制 CPU 能访问哪些物理内存区域**。

特权指令允许操纵 MMU。
**掌握 MMU 就等于掌握内存的完全控制权**，这就是操作系统能读写物理内存**任何位置**的原因，包括用户程序的地址空间。

```text
                 ┌──────────┐
       CPU ─────►│   MMU    │─────► 物理内存
                 └────┬─────┘
                      │ 谁能配置我？
                      ▼
              只有特权指令（内核态）

  结果：操作系统能读写整个物理内存
        ┌──────┬──────┬──────┬──────┐
        │ 内核 │ 进程A│ 进程B│ 进程C│
        └──────┴──────┴──────┴──────┘
        ◄───── 操作系统全都能碰 ─────►
```

**③ 重定义中断的处理方式**

前面说过，中断会让 CPU 跳到一个特定的内存位置去取处理例程。

问题在于：**内存不会永远以同一种方式被使用**，处理某个中断的代码也不一定永远被加载在同一个位置。

而且回想第 2 节的警告：如果一次中断让 CPU 切到内核态、却落在了**某个用户进程的地址空间**里，那是极度危险的。

所以特权指令在这里很有用：它们允许操作系统**指定**中断触发时 CPU 必须跳转到的确切内存位置。

**④ 用 MMU 反过来保护中断处理程序**

因为 MMU 只能通过特权指令操纵，操作系统就用它来确保
**用户进程无法访问存放中断处理程序的那些内存位置**。

这就阻止了恶意进程覆写中断处理程序、试图在内核态夺取系统控制权。

```text
   恶意进程想改中断处理程序
              │
              ▼
   ┌────────────────────────┐
   │  MMU 拦住：这块内存你   │
   │  的地址空间里没有       │
   └────────────────────────┘
              │
              ▼
        改不到 -> 夺不了权
```

在内核态里，我们对 CPU 的**整个中断流**拥有完全控制。

作者在这里点出一个贯穿全片的观点：

> **硬件只提供工具，最终仍然要靠软件（也就是操作系统）正确地使用这些工具，才能维持对系统的控制。**

### 用户态能做什么

用户态并不是什么都不能干，用户程序仍然可以使用**相当广泛**的一批指令：

| 类别 | 例子 |
| --- | --- |
| 数据搬运 | 移动、复制数据 |
| 算术运算 | 整数运算 |
| 浮点运算 | floating point |
| 位运算 | bitwise operations |
| 控制流 | 判断条件、跑循环 |

但反过来想：如果程序连**读文件**、**在屏幕上显示文字**、**通过网络发消息**这些基本事情都做不到，它就没什么用了。

用户程序终究需要以某种方式访问硬件。
**那它们是怎么做到的？**

## 4. 系统调用：把自己中断掉

答案是**系统调用（system calls）**。

为了让用户程序能访问硬件资源，操作系统以**库（library）**的形式提供一组函数。
这些函数就叫系统调用，它们对用户程序是必需的。

比如一个用户程序要处理文件：

```text
open()   ── 系统调用，打开文件
  │
read()   ── 每次读，都要系统调用
write()  ── 每次写，都要系统调用
  │
close()  ── 系统调用，工作做完后关闭文件
```

### 一个看起来矛盾的地方

系统调用**仍然是函数**，这意味着它们必须有内部实现，最终会被编译成机器码。

但这里就开始显得奇怪了：

因为这些函数属于一个库，我们写用户程序时调用它们，它们就成了我们**源代码的一部分**；
编译之后，它们也就成了我们**用户程序的一部分**。

可这对不上：我们刚刚才确认**用户程序运行在用户态**，因此**不能**使用操纵硬件所需的特权指令。

到底发生了什么？

### 真相：函数里藏了一条 int 指令

仔细看这些系统调用函数，会发现在某个位置有一条**触发中断的指令**。

**中断不只能由硬件触发，也能通过软件触发。**

这里就是 `int` 指令，它让程序触发一次中断，从而让程序计数器跳到**操作系统地址空间**里的一段例程。

而中断发生时，**CPU 会切到内核态**，于是这段例程就能执行所有必需的特权指令，去操纵硬件、完成这次系统调用。

```text
        用户程序（用户态）
   ┌──────────────────────────┐
   │  ...                     │
   │  call read()             │
   │    ┌────────────────┐    │
   │    │ 参数准备        │    │  ← 这部分在用户程序的地址空间
   │    │ int  <n>       │────┼──────┐
   │    └────────────────┘    │      │  mode bit: 0 -> 1
   └──────────────────────────┘      │
                                     ▼
                          操作系统地址空间（内核态）
                    ┌──────────────────────────────┐
                    │ 保存用户进程状态              │
                    │ 执行特权指令，真正读硬盘       │
                    │ 恢复用户进程状态              │
                    │ interrupt return  ───────────┼──┐
                    └──────────────────────────────┘  │
                                     mode bit: 1 -> 0 │
   ┌──────────────────────────┐                       │
   │  read() 返回后继续       │ ◄─────────────────────┘
   └──────────────────────────┘
```

特权指令执行完之后，必须把控制权交回被中断的进程，
并且**确保 mode bit 被设回 0**，让程序按预期在用户态继续执行。

这一步怎么做**因架构而异**：

| 做法 | 说明 |
| --- | --- |
| 由 `interrupt return` 一并完成 | 本视频例子采用的方式 |
| 单独一条专用指令切换模式 | 另一些架构需要额外指令 |
| 显式覆写 mode bit + 另一条返回指令 | 两步分开做 |

还有一种理解方式：

> **一个系统调用函数，一部分住在用户程序的地址空间、跑在用户态；
> 另一部分住在操作系统的地址空间、跑在内核态。**

## 5. 系统调用的优点和缺点

作者本来打算单独做一期讲系统调用，这里直接把利弊一并讲完了。

### 优点

**① 硬件抽象（hardware abstraction）** - 最重要的一条

很多人根本不知道直接操纵硬件有多难、多复杂。
既然系统调用替我们处理了和硬件的交互，我们需要硬件资源时只要调用它们就行。

> 系统调用极其有用，因为它让我们**用代码去思考，而不是用晶体管去思考**。

**② 安全性**

这一条和硬件抽象紧密相关。
直接操纵硬件**很容易出错**，而错误会导致漏洞和系统故障。

从 Python 或 JavaScript 转向低级编程的人常问一个问题：**我会不会把电脑烧了？**

答案永远是**不会**。
因为硬件是由操作系统替我们管理的。
即使我们写了一个非常糟糕的 C 程序，我们也没法以能损坏计算机的方式直接操纵硬件。

**③ 可移植性（portability）**

如果多个平台都遵循某些规范，同一份源代码就能在不同系统上编译。

### 缺点

**① 性能开销（performance overhead）**

这一条同样和硬件抽象有关。

系统调用依赖的**中断在性能上并不便宜**：
它需要额外步骤，比如**上下文切换（context switching）**；
而现代架构上的缓存等特性会**进一步放大**这个性能代价。

```text
   一次系统调用真正花掉的时间
   │
   ├─ 触发中断              -> 开销
   ├─ 保存当前进程状态       -> 开销
   ├─ 真正操纵硬件           <- 这一步才是你要的
   ├─ 恢复进程状态           -> 开销
   ├─ 切回用户态并返回       -> 开销
   └─ 缓存被搅乱后的连带损失  -> 开销
```

**② 没有及时性保证**

当程序发起一次系统调用，它实际上是**中断了自己**，把控制权交给操作系统。

而一旦操作系统拿到控制权，**没有任何保证它会立刻处理这次系统调用**。
操作系统可能借这个机会去做别的事，比如运行 CPU 调度器（CPU scheduler）、管理其他系统资源。

这次系统调用最终**会**被处理，但对用户程序来说，**没有任何保证它会很快发生**。

作者给了一个很妙的视角：

> **从某种角度看，系统调用可以被视为陷阱（traps）。
> 硬件抽象是诱饵，把用户程序引诱到「把控制权交回操作系统」这件事上。**

**③ 平台依赖**

这一条和前面说的「可移植性」优点是**互相矛盾**的。

虽然很多平台都力求兼容，但确实存在一些奇怪的差异。
（作者在这里念了一句「Microsoft，okay，okay」。）

## 6. 模式切换机制小结

整个 CPU 运行模式的机制其实很简单，是一组对称的交易：

```text
   用户程序                                    操作系统
   ────────────                                ────────────
   可以用中断让 CPU 切到内核态
        代价：中断了自己
              把 CPU 控制权交给操作系统  ───►   拿到控制权

                                               可以用一条特权指令
                                               恢复被中断的进程
   继续运行  ◄─────────────────────────────    但强制它在用户态继续
```

* 用户程序**能**让 CPU 进内核态，但**代价**是中断自己、把 CPU 交出去。
* 操作系统**能**恢复一个被中断的进程，但会**强制**它继续运行在用户态。

系统调用这个概念太成功了，以至于一些架构干脆提供了**专用指令**来简化调用，不再需要手动设置中断。

因此在很多架构上可以看到这一对：

| 指令 | 性质 | 作用 |
| --- | --- | --- |
| `syscall` | 普通指令 | 用户程序发起系统调用 |
| `sysret` | 特权指令 | 内核返回用户态 |

它们也让汇编代码更易读。

## 7. 合作式操作系统的致命缺陷

当一个操作系统**依赖用户程序的合作**才能重新拿回控制权、去执行管理任务时，
它被归类为**非抢占式（non-preemptive）**或**合作式（cooperative）**操作系统。

这类通用操作系统**已经不再被使用**了，因为它们有一个大问题。

想一个程序，里面有一个**不含任何系统调用的死循环**：

```text
   while (true) {
       x = x + 1;     // 全是普通指令
   }                  // 一次系统调用都不发
```

CPU 会**无限期地**卡在这个循环里执行。

```text
   进程 A（死循环，不调系统调用）
   ┌────────────────────────────┐
   │  ██████████████████████... │  永远占着 CPU
   └────────────────────────────┘

   操作系统   ── 等一次中断 ── 永远等不到
   进程 B     ── 饿死
   进程 C     ── 饿死
```

如果一个进程**有意或无意地**避开系统调用，CPU 就**永远不会**把控制权还给操作系统，
从而**饿死（starving）**所有其他进程。

## 8. 抢占式操作系统：再一次靠硬件

又一次，**光靠软件解决不了这个问题，必须要硬件支持**。

解法是使用一个**定时器（timer）**。
定时器到期时会触发一次**硬件中断**。

这个定时器**内建在 CPU 里**，并且**只能通过特权指令控制**。

流程是：

```text
   操作系统把 CPU 分配给某个用户进程之前
        │
        ├──►  先设置定时器（特权指令）
        │
        ▼
   进程开始运行，定时器同时在倒数
        │
   ┌────┴─────────────────────────┐
   │                              │
   ▼                              ▼
进程自愿发系统调用             进程迟迟不发系统调用
（主动交回控制权）                    │
                                     ▼
                            定时器到期 -> 硬件中断
                                     │
                                     ▼
                          强制停下进程，控制权回到操作系统
```

* 用户进程**仍然可以**通过系统调用自愿交回控制权。
* 但如果一个进程**太久不发系统调用**，定时器保证**最终**会触发一次中断，强制它停下，把控制权还给操作系统。

这个机制让**内核态得以完全控制每个进程能用多少 CPU 时间**。

### 还有一层：非法指令也会被硬件抓住

此外，当一个 CPU 支持运行模式时，硬件还必须能对「用户程序试图直接操纵硬件」这件事作出反应。

如果处理器正运行在用户态、却遇到一条特权指令，
硬件可以被配置为**立即触发一次中断**，把控制权交给操作系统，
让它处理这个用户程序的可疑行为，**通常是直接终止它的执行**。

```text
   用户态 + 遇到特权指令
              │
              ▼
        硬件立刻触发中断
              │
              ▼
        操作系统接手判断
              │
              ▼
        大概率：杀掉这个进程
```

中断是 CPU 的一个**根本特性**，所以更准确的说法是：

> **内核态授予的是对「CPU 如何被使用」的完全控制。**

当硬件架构支持这些特性、并且操作系统真的利用了它们时，我们说的就是**抢占式操作系统（preemptive operating systems）**。

---

## 9. 回头看那句「操作系统在中间」

把上面的东西都装进脑子后，应该能理解：
**用户程序和操作系统都只是软件。**

由于用户程序被限制在用户态，它们**不能**直接和硬件交互；
它们必须**把控制权交给操作系统**，由操作系统代表它们去操纵硬件。

所以第 0 节那句「操作系统永远在中间」的说法，
**只是对真实情况的一个非常高层的抽象**。

```text
   教科书里的图（高层抽象）
   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │ 用户程序 │──►│操作系统  │──►│  硬件    │
   └──────────┘   └──────────┘   └──────────┘

   真实发生的事
   ┌──────────┐
   │ 用户程序 │  int / syscall（中断自己，交出 CPU）
   └────┬─────┘
        │  mode bit 0 -> 1
        ▼
   ┌──────────┐  特权指令
   │操作系统  │──────────────►  硬件
   └────┬─────┘
        │  sysret / iret，mode bit 1 -> 0
        ▼
   ┌──────────┐
   │ 用户程序 │  继续跑在用户态
   └──────────┘
```

不是「操作系统站在中间挡着」，而是**用户程序只能通过交出 CPU 来换取服务**。

## 10. 内核态里不只有操作系统：驱动

很多人会好奇：**除了操作系统，其他软件能在内核态运行吗？**

**答案是可以。**

举个例子：一张新显卡发布时，操作系统可能根本不知道怎么控制它，因为操作系统是在这张卡存在之前就开发出来的。
操作系统开发者**不可能**为世上每一个硬件设备都写代码，所以这项工作通常留给硬件厂商。

解法就是**驱动（drivers）**：为控制特定硬件而设计的软件。

由于控制硬件需要特权指令，**驱动必须运行在内核态**。
当用户程序需要某个硬件时，操作系统就使用相应的驱动。

### 严重的代价：内核态共享同一个地址空间

但这个技术有一个严重的缺点。

任何运行在内核态的代码都能使用特权指令，这使得操作系统**不可能**把它和其他进程、甚至和操作系统自身完全隔离开。

结果就是：**所有运行在内核态的代码共享同一个地址空间。**

```text
   内核态（一个共享地址空间，没有隔离）
   ┌──────────────────────────────────────────────┐
   │  操作系统核心数据                             │
   │  显卡驱动    网卡驱动    某厂商的驱动          │
   └──────────────────────────────────────────────┘
        │
        │  某个驱动写错了地址
        ▼
   操作系统的关键数据被破坏
        │
        ▼
   驱动崩溃 = 操作系统崩溃 = 所有用户程序无法运行
        │
        ▼
   整个系统倒下（Windows 上的蓝屏 BSOD）
```

* 如果一个驱动**误写到错误的内存地址**，它可能破坏对操作系统至关重要的数据。
* 如果一个驱动**崩溃**，它会把**整个操作系统**一起带下去。
* 没有操作系统，用户程序无法运行，整个系统就都倒了。

这就是为什么**有 bug 的驱动经常导致 Windows 的蓝屏死机（blue screen of death）**。

## 11. 内核级软件：反作弊与杀毒

尽管有风险，允许代码在内核态运行是**必需**的，因为驱动是必需的。
再说一次：操作系统开发者几乎不可能为世上每一个硬件设备都写代码。

但「第三方代码可以在内核态运行」这个事实，导致它被用在了**设备驱动之外**的用途上，
其中包括**游戏反作弊系统**和**恶意软件检测软件**。

为什么会这样？

**第一个原因：内核态的软件不依赖系统调用**，因此它比运行在用户态时**快得多**。

**第二个原因：只有内核态才能看到它们要看的东西。**

### 例子一：反作弊

想象一个游戏禁用手柄，以防止手柄玩家对鼠标键盘玩家造成不公平优势。
一个玩家可能通过第三方程序把手柄映射成键盘输入来作弊。

```text
   用户态视角（游戏能看到的）
   ┌──────────────┐
   │  收到按键：W  │   ← 游戏分不清这到底来自哪里
   └──────────────┘

   内核态视角（反作弊能看到的）
   ┌──────────────────────────────────────┐
   │  USB 设备枚举：检测到手柄            │
   │  硬件活动：输入实际来自手柄           │
   └──────────────────────────────────────┘
```

因为游戏运行在用户态，它**无法判断**输入是否真的来自键盘。
而运行在内核态的反作弊软件可以**直接监控硬件活动**，检测出输入其实来自手柄。

### 例子二：恶意软件检测

对恶意软件检测来说，内核态让软件可以：

| 能力 | 说明 |
| --- | --- |
| 扫描网卡等设备 | 监控网络流量 |
| 检查运行中进程的地址空间 | 排查可疑行为，例如监视私人数据并发往不可信端点 |

到这里就说得通了：**这类软件为什么必须运行在内核态**。
如果它们运行在用户态，就根本做不到它们要做的事。

## 12. 两个真实的代价：CrowdStrike 和 Vanguard

但「什么都塞进内核态」并不总是好主意。

### CrowdStrike

CrowdStrike 是一款恶意软件检测软件，安装在全世界数百万台企业设备上。

事故链条：

```text
   一次更新损坏了一个配置文件，把它填满了零
        │
        ▼
   文件损坏 -> 软件崩溃
        │
        ▼
   软件在内核态 -> 操作系统一起崩溃
        │
        ▼
   全球范围的混乱
   ├── 数千台设备显示蓝屏死机
   └── 数十亿美元的商业损失
```

这正是第 10 节那条结论的现实版本：
**内核态没有隔离，所以内核态里任何一处崩溃都是全系统崩溃。**

（作者在片中说事故发生在「九月」；实际这次全球性事故发生在 2024 年 7 月 19 日，视频发布于同年 10 月。这一条是补充背景，不影响论述。）

### Vanguard

另一个例子是 Vanguard，Riot Games 的反作弊软件，用在《英雄联盟》《无畏契约》这类热门游戏上。

刚发布时，它**给数百名玩家造成了蓝屏死机**。

但更可怕的部分是它和**腾讯**的关系，腾讯是拥有 Riot Games 的中国公司。

事情是这样的：

* 你**不装 Vanguard 就没法玩 Riot 的游戏**，这从反作弊角度看是合理的。
* 让人不适的地方在于：**Vanguard 即使在你没有玩游戏的时候也运行在内核态**，
  意味着它**能够**监控你在这台计算机上做的一切。

虽然**没有证据**表明它真的这么做，但腾讯是一家中国公司、很可能受政府监管这一事实引发了隐私担忧。
考虑到 Vanguard 运行在全球数百万台计算机上，这件事就相当令人不安。

## 14. 核心总结

```text
一个比特如何守住操作系统
│
├── 硬件提供的机制
│   ├── 特权指令（privileged instructions）：指令集的一个子集
│   ├── mode bit：1 比特寄存器
│   │   ├── 1 = 内核态（kernel mode），整个指令集可用
│   │   └── 0 = 用户态（user mode），特权指令被拒
│   ├── 中断：跳转 + 自动把 mode bit 置 1
│   ├── CPU 内建定时器：只能用特权指令控制
│   └── 用户态执行特权指令时立即触发中断
│
├── 软件必须正确使用这些工具
│   ├── 把操作系统装进中断跳转的那块内存
│   │   └── 否则任何实体（浏览器、编辑器）拿到内核态都能为所欲为
│   ├── 用特权指令重定义中断处理程序的位置
│   └── 用 MMU 保护中断处理程序不被用户进程覆写
│
├── 内核态独有的能力
│   ├── 直接操作 IO 设备（网卡 / 显卡 / 硬盘 / 显示器 / 键盘）
│   ├── 操控 MMU -> 掌握整个物理内存
│   ├── 重定义中断处理方式
│   └── 控制 CPU 定时器
│
├── 用户程序访问硬件的唯一通路：系统调用
│   ├── 实现里藏着一条 int 指令 -> 中断自己
│   ├── 函数一半在用户态地址空间，一半在操作系统地址空间
│   ├── 返回时必须把 mode bit 设回 0
│   ├── 优点：硬件抽象 / 安全（烧不了电脑）/ 可移植
│   ├── 缺点：中断开销（上下文切换 + 缓存）/ 无及时性保证 / 平台差异
│   └── 本质：抽象是诱饵，系统调用是陷阱
│
├── 合作式 vs 抢占式
│   ├── 合作式（non-preemptive）：靠程序自愿调系统调用
│   │   └── 死循环 + 无系统调用 = CPU 永久被占，其他进程饿死
│   └── 抢占式（preemptive）：定时器到期强制中断
│       └── 内核态因此完全控制「CPU 如何被使用」
│
└── 内核态里的第三方代码
    ├── 驱动：厂商写，必须在内核态
    ├── 代价：内核态共享同一地址空间，零隔离
    │   ├── 写错地址 -> 破坏操作系统数据
    │   └── 驱动崩溃 -> 蓝屏，整机倒下
    └── 被扩展到非驱动用途
        ├── 反作弊：用户态分不清键盘/手柄，内核态能看硬件活动
        ├── 杀毒：扫网卡流量 + 查进程地址空间
        ├── CrowdStrike：配置文件被填零 -> 全球蓝屏 + 数十亿美元损失
        └── Vanguard：不玩游戏时也在内核态运行 -> 隐私担忧
```

> 用户程序和操作系统本是同类，都只是软件。
> 让它们分出高下的，不是代码本身，而是处理器里那一个比特。
> 这个比特只能由中断翻转，中断只能跳到操作系统事先指定的地方，那块地方又被 MMU 锁住不许用户进程碰。
> 于是「操作系统在中间」这句话有了真正的含义：用户程序想要硬件，唯一的办法是中断自己、交出 CPU，然后祈祷操作系统尽快回头处理它。
> 而当我们把第三方代码放进内核态时，我们放弃的正是这个比特带来的全部保护，CrowdStrike 和 Vanguard 就是账单。
