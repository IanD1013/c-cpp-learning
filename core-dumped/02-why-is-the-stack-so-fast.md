# 栈为什么这么快（The Stack）

> 视频来源：Core Dumped -《WHY IS THE STACK SO FAST?》
> https://www.youtube.com/watch?v=N3o5yHYLviQ

## 0. 这一期在讲什么

上一期（[变量的大小为什么重要](01-the-size-of-your-variables-matters.md)）的结论是：系统级语言要求你显式说明每个值占多少内存。
那一期结尾留了一个疑问：如果我希望类型在运行时动态增长或收缩呢？

在低级语言里这件事做不到，编译器会直接报错：

```rust
// 不给长度 -> 编译不过
struct Buffer {
    data: [u8],
}

// 给了长度 -> 可以，但这个长度是整个程序生命周期里都固定的
struct Buffer {
    data: [u8; 64],
}
```

本期要回答的就是：**这条限制到底是从哪来的。**

答案藏在「栈」这个内存区域里。
所有人都告诉你「栈很快，尽量把数据放栈上」，但几乎没人告诉你为什么快。

要讲清楚这件事，需要先铺三层前置知识：操作系统怎么分内存、虚拟内存是什么、缓存是什么。

---

## 1. 前置：栈这个数据结构

栈（stack）是遵循 **后进先出（LIFO，last in first out）** 的数据结构：最后放进去的元素最先被取出。

```text
        push                        pop
          │                          ▲
          ▼                          │
      ┌───────┐                  ┌───────┐
      │   C   │ ← 栈顶            │   C   │ ← 最先出去
      ├───────┤                  ├───────┤
      │   B   │                  │   B   │
      ├───────┤                  ├───────┤
      │   A   │ ← 最先进来        │   A   │
      └───────┘                  └───────┘
```

它的容量通常是有限的。
压入太多元素、空间用完了，就是**栈溢出（stack overflow）**，这个词你应该很熟。

需要区分清楚：本期讲的不是软件里那个通用的栈数据结构，而是**执行栈（execution stack）**，也叫程序栈（program stack）或硬件栈（hardware stack）。
两者有关系，但不是一回事。

---

## 2. 操作系统怎么给程序分内存

理论上程序运行时可以往内存的任何地方写值。
但实际不行，因为**操作系统是程序和硬件之间的中间人**，内存也不例外。

流程是这样的：

```text
   程序                    操作系统                  物理内存
    │                        │                    ┌──────────┐
    │ ① 我要一块内存          │                    │ 别的程序  │
    ├───────────────────────►│                    ├──────────┤
    │                        │ ② 找空闲区域        │  空闲     │
    │                        ├───────────────────►├──────────┤
    │ ③ 给你这块，随便读写     │                    │ 别的程序  │
    │◄───────────────────────┤                    └──────────┘
    ▼
```

如果你去读写一个操作系统**没有分配给你**的地址，程序会被立刻终止。
这就是那个著名的错误，也是这个频道名字的来源：

```text
Segmentation fault (core dumped)
```

这里有个关键细节：

> 操作系统**不会**按你需要的精确字节数分配，它给你的是一整块内存区域（chunk），你在里面自由读写。

---

## 3. 为什么必须把数据排好：外部碎片

既然给的是一整块，那在块里乱放行不行？
不行，会出现这种情况：

```text
乱放（外部碎片）
┌────┬──┬────┬──┬────┬──┬────┐
│数据│空│数据│空│数据│空│数据│   ← 空闲总量够，但没有一段连续的
└────┴──┴────┴──┴────┴──┴────┘
                 ▲
      要存一个稍大的值 -> 放不进去

排好（无碎片）
┌────┬────┬────┬────┬──────────┐
│数据│数据│数据│数据│   连续空闲  │   ← 直接放得下
└────┴────┴────┴────┴──────────┘
```

明明还有足够的空闲内存，却因为**缺少连续空间**而存不下数据，这个问题叫**外部碎片（external fragmentation）**。

碎片化之后唯一的出路就是**再向操作系统申请一块内存**。
而如果一开始就把数据组织好，这次额外申请根本不需要发生。

> 向操作系统要内存在性能上是相当昂贵的操作。
> 这也是为什么很多人建议尽量少用堆（heap）。堆的细节留给下一期。

还有一层浪费：操作系统分配内存给你之后，**不会追踪你到底用了没用**。
它只知道「这块区域属于这个程序」。

```text
        我们程序拿到的 chunk
┌──────┬───────────────────────────┐
│ 用了 │      申请了但一直没用        │
└──────┴───────────────────────────┘
                    ▲
        别的程序需要内存时也不能碰这里
        只能去别处找 -> 整机内存被白占
```

---

## 4. 虚拟内存：内存不够了怎么办

如果所有物理内存都被别的程序占满了呢？
答案还是在操作系统这里。

现代操作系统在内存不足时，会**把存储设备当成额外的内存来用**。

```text
   程序看到的（虚拟）              实际落在哪里
┌────────────────────┐        ┌──────────────┐
│                    │───────►│     RAM       │  快
│   一大片连续内存      │        ├──────────────┤
│   （看起来无限）      │───────►│ 磁盘 / swap   │  慢几千倍
└────────────────────┘        └──────────────┘
```

Linux 里那个叫 `swap` 的分区，干的就是这件事。

这就是**虚拟内存（virtual memory）**。它有两个好处：

1. 造出「内存比实际多得多」的假象；
2. 造出「直接写物理内存」的假象，程序员不用关心底层细节。

虚拟内存本身够讲三十分钟，超出本期范围。
但有一点必须记住：

> 用存储来扩充主内存是**双刃剑**。存储比 RAM 慢几千倍，这个特性要谨慎使用。

上一期有人评论说：现在内存几乎无限，数据大小不重要了。
内存对程序员来说确实**看起来**无限，但**性能**这一关始终在。

## 5. 缓存：为什么数据要紧凑

CPU 速度极快，但**从内存取数据本身就有明显开销**，内存反而成了瓶颈。

厂商的解法是在芯片里集成**缓存（cache）**：处理器内部一小块专用内存，存放某段内存区域的副本。

```text
   ┌─────────────────────── CPU ───────────────────────┐
   │                                                    │
   │   ┌────────┐        ┌───────────────┐              │
   │   │ 运算单元 │◄──────►│ cache（小、极快）│             │
   │   └────────┘        └───────┬───────┘              │
   └────────────────────────────┼──────────────────────┘
                                │  慢
                        ┌───────▼───────┐
                        │  主内存（RAM）  │
                        └───────────────┘
```

| 情况 | 名称 | 后果 |
| --- | --- | --- |
| 需要的数据在 cache 里 | 缓存命中（cache hit） | 立刻拿到 |
| 需要的数据不在 cache 里 | 缓存未命中（cache miss） | CPU 必须等它从主内存取回，额外耗时 |

这件事对程序员同样是不可见的。
而且注意：决定「哪段内存留在 cache 里」的是**硬件**，不是操作系统。

那我们能做什么？

> 如果在意性能，我们能做的最好的事就是**让数据尽可能紧凑**。
> 越紧凑，越有可能整体装进 cache，缓存命中的概率就越高。

这种「让数据尽可能靠近 CPU」的思路，低级程序员称之为**局部性（locality）**。

这就是数据要紧凑的**第二个理由：性能**（第一个理由是省空间 / 避免碎片）。

---

## 6. 于是：用栈来组织数据

要让数据紧凑，一个好办法就是用栈来组织。

第一步优化是**程序启动时预先分配（pre-allocate）一块内存**。
这样每次要存值，地方已经准备好了，不必临时向操作系统申请。

既然目标是避免运行时申请内存，这块预分配区域的大小就**在整个程序生命周期里固定**。
所以它多大要仔细权衡：

```text
分太大                          分太小
─────────────────              ─────────────────
程序只用几个变量                 稍微多点数据就装不下
大片空间永远用不到                -> stack overflow
操作系统替你占着不放
-> 别的程序用不了 = 浪费
```

因此这块区域**通常都很小**。
具体大小取决于编译器，但一般不会超过几个 MB。

乍看好像不够用，但算一下就知道够了：

```text
1 MB = 1,048,576 字节
一个 64 位整数 = 8 字节

1,048,576 ÷ 8 = 131,072 个 64 位整数
```

**1 MB 就能放十三万多个 64 位整数。**

## 7. 栈原点与栈指针

程序启动时，`main` 函数是入口。
每遇到一个新变量，它的值就被压（stack）进这块预分配区域。
这就是「the stack」这个名字的由来。

```text
                  高地址
              ┌───────────┐
              │   未使用    │
              │           │
  stack ptr ─►├───────────┤ ← 当前栈顶
              │  变量 c    │
              ├───────────┤
              │  变量 b    │
              ├───────────┤
              │  变量 a    │
stack origin ─►└───────────┘ ← 栈的起始地址
                  低地址
```

| 名称 | 含义 |
| --- | --- |
| 栈原点（stack origin） | 标记栈起始位置的内存地址 |
| 栈指针（stack pointer） | 指向栈上当前最顶端的数据 |

栈指针本身也要存起来。
它可以放在内存里，但**现代架构专门用一个 CPU 寄存器来存栈指针**。

```text
┌──────── CPU ────────┐
│  ┌───────────────┐   │
│  │ SP 寄存器      │   │  ← 直接在 CPU 里
│  └───────────────┘   │     不用等内存，甚至不用等 cache
└─────────────────────┘
```

于是分配内存这件事变得极其便宜：

```text
栈上分配                              堆上分配（下一期）
────────────────────                 ────────────────────────────
① 读栈指针（在寄存器里）                ① 向操作系统申请内存
② 加上要占的大小                       ② 等它找到可用空间
③ 得到可写地址，写入                    ③ 系统给的量不精确，还要用
   完了                                   各种策略避免碎片
                                       ④ 才能写入
= 几条指令                             = 一堆额外步骤，慢
```

> 栈上分配之所以高效，核心就在于栈指针一直明确指着「下一个能写的位置」。

## 8. 栈帧与返回链接

函数被调用时，它的所有局部值都被压到栈上。
但必须记住这些局部值**从哪里开始**，因为函数结束时要把栈指针**重置回调用前的位置**。

这些划分出来的子区域叫**栈帧（stack frame）**。

```text
              ┌───────────────┐
              │  被调函数局部值 3│ ┐
              ├───────────────┤ │
              │  被调函数局部值 2│ │ callee 的栈帧
              ├───────────────┤ │
              │  被调函数局部值 1│ ┘
              ├───────────────┤
              │  caller 局部值 │ ┐
              │      ...      │ ┘ caller 的栈帧
              └───────────────┘

函数返回 -> 栈指针直接退回 callee 栈帧之前的位置，整帧一次性作废
```

如果被调函数**有返回值**，会先分出一块专门的空间叫**返回链接（return link）**，然后才开始压局部值：

```text
调用中                                 返回后
┌────────────────┐                   ┌────────────────┐
│ 局部值 2        │ ┐                  │                │
├────────────────┤ │ callee 栈帧      │   （已释放）     │
│ 局部值 1        │ ┘                  │                │
├────────────────┤                   ├────────────────┤
│ return link    │ ← 返回值写这里       │  返回值         │ ← 并入 caller 栈帧
├────────────────┤                   ├────────────────┤
│ caller 栈帧     │                   │ caller 栈帧     │
└────────────────┘                   └────────────────┘
```

被调函数结束时，返回值被直接写进 return link；
随后 callee 的栈帧被移除，**只剩返回值，并且它现在归属于 caller 的栈帧**。

这里推出一个语言设计上的结论：

> 编译器要生成高效的机器码，就必须知道 return link 的**确切大小**。
> 这就是系统级编程语言强制你写**返回类型**的原因。

```rust
fn add(a: i32, b: i32) -> i32 {  // -> i32 就是在告诉编译器 return link 多大
    a + b
}
```

## 9. 栈的限制（本期最初的问题在这里收口）

### 9.1 栈上的数组不能变长

看这个例子：先在栈上写一个数字，再写一个数组，然后又写了几个数字。

```text
   栈指针 ─►┌───────────┐
            │  数字 z    │
            ├───────────┤
            │  数字 y    │
            ├───────────┤
            │           │
            │   数组     │
            │           │
            ├───────────┤
            │  数字 x    │
            └───────────┘
```

现在我们想往数组里加几个元素。问题就出来了：

```text
            ┌───────────┐
            │  数字 z    │  ✗ 会被覆盖
            ├───────────┤
            │  数字 y    │  ✗ 会被覆盖
            ├─ ─ ─ ─ ─ ─┤
            │  新元素 ↑  │  ← 数组只能往上长
            │   数组     │
            ├───────────┤
            │  数字 x    │
            └───────────┘
```

> 给栈上的数组加元素，意味着可能会**覆盖掉后面那些之后还要用的值**。

这正是上一期讲的那件事的根源：
编译器坚持要你写清数组长度，即使这个数组是自定义类型的成员。

```rust
struct Foo {
    data: [u8],       // ✗ 大小未知，编译器不知道要在栈上留多少空间
}

struct Foo {
    data: [u8; 32],   // ✓ 大小确定，栈上留 32 字节
}
```

因为你写明长度之后，编译器才能**精确知道这个值在栈上要占多少空间**。

### 9.2 栈溢出与递归

即使大小都写明了，**栈的总容量仍然是有限的**。
超出这个上限，程序崩溃，报 stack overflow。

递归是最容易踩到这一点的场景：函数每调用自己一次，就压入一个新的栈帧。

```text
factorial(5)  ┌──────────────┐ ← 快撑到栈顶了
factorial(4)  ├──────────────┤
factorial(3)  ├──────────────┤
factorial(2)  ├──────────────┤
factorial(1)  ├──────────────┤
   main       └──────────────┘

没有 base case  -> 一直压，直到溢出
有 base case    -> 但如果在触到 base case 之前就压满了，照样溢出
```

所以有些场合**迭代方案优于递归方案**。

### 9.3 一个必要的说明

栈的具体行为**取决于编程语言和它的编译器**。
本期看到的模型不一定精确对应每种语言的实现，作者的目的是简化概念、方便理解。

## 10. 下一步：堆

本期总结出的栈的三个限制：

| 限制 | 说明 |
| --- | --- |
| 大小有上限 | 通常只有几 MB |
| 类型不能动态增减 | 大小必须编译期确定 |
| 单线程实体 | 多线程时每个线程各有自己的栈，线程间共享内存受限 |

这三个问题有一个共同的解法，就是**堆（heap）**。

## 11. 核心总结

```text
栈为什么这么快
│
├── 前置：内存不是随便写的
│   ├── 操作系统是中间人，越界访问 -> segmentation fault (core dumped)
│   ├── 分配是「一整块 chunk」，不是精确字节数
│   ├── 块里乱放 -> 外部碎片：空闲够但不连续，只能再申请（贵）
│   └── 申请了不用，操作系统也替你占着 -> 别的程序用不了
│
├── 前置：虚拟内存
│   ├── 内存不够时拿存储当内存（Linux 的 swap）
│   ├── 造出「内存无限」+「直写物理内存」两个假象
│   └── 双刃剑：存储比 RAM 慢几千倍
│
├── 前置：缓存与局部性
│   ├── CPU 再快，取内存也有明显开销
│   ├── cache hit 立刻拿到 / cache miss 要等主内存
│   ├── 由硬件决定谁留在 cache，程序员管不着
│   └── 唯一能做的：数据尽量紧凑 -> 更可能整体装进 cache = locality
│
├── 栈的机制
│   ├── 启动时预分配一块固定大小区域（一般不超过几 MB）
│   │   └── 1 MB 就能放 131,072 个 64 位整数，够用
│   ├── stack origin 标起点，stack pointer 标当前栈顶
│   ├── 栈指针放在 CPU 专用寄存器里，不用等内存也不用等 cache
│   ├── 分配 = 读栈指针 + 加大小 + 写入，就这三步（这才是「快」的来源）
│   ├── 栈帧：函数的局部值成组管理，返回时栈指针整帧退回
│   └── return link：返回值的预留位 -> 所以必须写返回类型
│
└── 栈的限制
    ├── 栈上数组长不了：往上长会覆盖后面还要用的值
    │   └── 所以编译器强制你写数组长度（上一期那条限制的根源）
    ├── 容量有限：递归压帧过多 -> stack overflow，有时该改成迭代
    └── 单线程：每个线程各一个栈，跨线程共享内存受限
```

一句话：

> 栈快，不是因为它用了什么魔法，而是因为「后进先出」这个约束让分配退化成一次寄存器加法。
> 代价就是：所有大小必须在编译期说清楚，而且只能按顺序进出。
> 你上一期被编译器逼着写的那些尺寸，买的就是这份速度。
